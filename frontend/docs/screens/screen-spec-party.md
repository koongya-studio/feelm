# Screen Spec — 파티 (5.1 ~ 5.7)

업무 `S15P21E106-304` 산출물 · 에픽 `S15P21E106-301`
(실제 API 연동은 업무 `S15P21E106-393`에서 이어졌습니다. 그때 달라진 것은 4·5장에 있습니다)

기준 자료는 `Feelm UI Wireframe Final.html` 67프레임 중 5.1 ~ 5.7입니다. 같은 절의
**5.8 파티원 팝콘 · 5.9 파티 팝콘 섞기는 에픽 266에서 이미 구현**되어
[`screen-spec.md`](./screen-spec.md) 7장에 있습니다. 표기 규칙과 공통 사항은 그 문서
2·3장을, 문서를 나누어 두는 이유는 [`screen-spec-auth.md`](./screen-spec-auth.md)
머리말을 따릅니다.

## 4. 계약과 다른 점

### `[!]` 정원이 4명인데 화면은 6명을 말한다

계약은 여러 곳에서 **4**를 못 박습니다.

| 근거 | 값 |
| --- | --- |
| API-049 처리 규칙 | `파티는 파티장 포함 최대 4명` |
| API-049 응답 | `maxMembers: 4` |
| API-051 오류 | 멤버 + 대기 초대가 4명이면 `PARTY_FULL` |

와이어프레임 5.2는 `2인` ~ `6인`을 고르게 하고 5.3은 `1/6명 · 최대 6명까지`라고
적었습니다. 계약을 기준으로 **2~4인**만 고르게 하고 표시도 4로 맞췄습니다
(`screen-spec.md` 2장). 5인·6인을 살리려면 계약을 먼저 바꿔야 합니다.

### `[!]` 고른 인원을 보낼 곳이 없다

API-049 요청 본문은 `{ name }`뿐입니다. 정원은 서버가 정해 응답으로 내려줍니다. 5.2에서
고른 인원은 요청에 넣지 않고 5.3의 대기 자리 수를 그리는 데만 씁니다.

### `[!]` `일치 94%`에 해당하는 계약 값이 없다

API-058이 주는 것은 `reason.memberFit[]` — **사용자별** 점수(0~1)입니다. 와이어프레임은
카드마다 퍼센트 **하나**를 보여줍니다. 파티 추천이 "모두에게 맞는 영화"를 고르는 일이므로
파티원 점수의 평균으로 읽었고, 목업 값이 와이어프레임의 94 · 87 · 81과 맞습니다
(`PartyRecommendationPage/fit.ts`). 계약이 대표값을 정해 주면 그 계산은 사라집니다.

### `[?]` 초대 링크와 QR이 계약에 없다

API-051은 닉네임 검색(API-019)으로 찾은 `userId`를 받습니다. 링크나 QR로 참여하는 경로는
여전히 정의되어 있지 않습니다. 업무 -304는 와이어프레임의 두 버튼을 자리만 두고 잠가
두었고, 업무 -393에서 **그 자리를 닉네임 검색으로 바꿨습니다.** 계약에 있는 경로가 하나뿐인데
계약에 없는 두 경로가 자리를 차지하고 있을 이유가 없습니다.

검색 결과에는 **`PRIVATE` 사용자도 나옵니다.** 가입 기본값이 `PRIVATE`라 빼면 닉네임
초대가 사실상 막히기 때문입니다(API-019 처리 규칙). `visibility`로 노출 수위를 정하라는
계약에 따라 `비공개 프로필`만 덧붙이고 다른 정보는 보여주지 않습니다.

`[?]` **초대는 파티를 만든 다음에만 보낼 수 있습니다.** API-051이 `partyId`를 경로로 받기
때문입니다. 그래서 5.3은 사람을 고르기만 하고 `파티 시작하기`에서 생성 → 초대 순으로
보냅니다. **일부 초대만 실패하면** 파티는 이미 만들어진 뒤라 되돌릴 계약이 없어(API-056
종료뿐입니다) 다시 누르면 같은 이름의 파티가 하나 더 생깁니다. 실패한 사람만 알리고
버튼을 `파티로 이동`으로 바꿉니다.

### `[?]` 초대의 `2인`이 나를 세는지 알 수 없다

API-052 `memberCount`는 **지금 참여 중인 사람 수**입니다. 5.6이 보여 주는 `2인`을 그대로
읽으면 내가 수락한 뒤 세 명이 되어, 5.7의 `김난다 × 무비버디`(두 사람)와 어긋납니다.
그래서 `memberCount + 1` — **나까지 세었을 때의 파티 인원**으로 읽었습니다.

### `[?]` 누가 수락했는지 알려 주는 계약이 없다

5.7은 초대한 사람에게 `OOO 님이 초대를 수락했어요!`를 보여줘야 하는데, API-053은 수락한
본인에게 응답하고 초대한 사람에게는 파티 정보가 폴링으로 갱신된다고만 되어 있습니다.
지금은 API-050의 파티원 중 나를 뺀 마지막 사람으로 읽습니다. 알림 계약(8.1)이 정해지면
그 값을 써야 합니다.

### `[?]` 5.5의 공통 키워드가 API-058에 없다

5.9 팝콘 섞기가 쓰는 `getPartyMix`(계약 없음, CR-17)에 같은 성격의 값이 있어 그것을
씁니다. 그 값은 자리표시자라 **누구의 값인지 뜻이 없어** 실제 파티원에게 앞에서부터
차례로 붙입니다(업무 -393). 그러지 않으면 목업의 사용자 번호와 실제 파티원이 달라 5.9의
비율과 태그가 모두 빕니다.

### `[!]` 나가기 · 종료 · 내보내기에 진입점이 없다 (업무 -393)

계약에는 파티 나가기(API-055) · 종료(API-056) · 멤버 강퇴(API-069)가 모두 있는데
와이어프레임 5.1 ~ 5.9 어디에도 누를 자리가 없습니다. 파티 하나의 문맥과 파티원 목록이
함께 있는 화면이 **5.8뿐**이라 그곳에 `파티 관리` 영역을 두기로 했습니다(사용자 결정
2026-09-16). 5.1은 목록만 보여줍니다.

- `파티 종료하기`와 멤버 카드의 `내보내기`는 **파티장에게만** 보입니다. 계약도 파티장이
  아닌 요청을 `403 FORBIDDEN`으로 거절합니다
- 셋 다 되돌릴 계약이 없어 누르면 바로 보내지 않고 확인을 한 번 받습니다. API-069는
  `클라이언트는 실행 전에 대상 닉네임과 강퇴 사실을 확인시킨다`고 처리 규칙에 적고 있습니다
- 브라우저 확인 다이얼로그(`confirm`)를 쓰지 않고 화면 안에서 묻습니다

### `[!]` API-057이 맛을 하나도 주지 않는다 (업무 -393)

계약은 `8개 맛을 항상 모두 포함`한다고 적고 있지만 실제 응답은 `flavors: []`입니다. 맛
기준정보(API-044)가 아직 적재되지 않았기 때문이며 5.8의 `대표 맛`과 5.9의 통이 함께
빕니다. **화면을 빈 응답에 맞춰 고치지 않았습니다** — 적재 뒤 다시 보는 것이 맞습니다
(`verification/S15P21E106-393.md`).

### `[!]` 2.1의 `새 팝콘 N개`가 사라졌다 (업무 -393)

홈 2.1은 `멤버 4명 · 새 팝콘 2개`를 보여줬는데 **`새 팝콘` 수를 주는 계약이 없습니다.**
API-050은 이름 · 상태 · 멤버 · 정원만 줍니다. 목업일 때는 지어낼 수 있었지만 실제 연동으로
채울 값이 사라져 멤버 수만 적습니다(`types/unspecified.ts`).

## 5. 아직 구현하지 않은 것

업무 -304가 미뤄 둔 것 중 **실제 초대 보내기(API-051) · 나가기(API-055) ·
종료(API-056)는 업무 -393에서 붙였습니다.** 멤버 강퇴(API-069)도 함께 넣었습니다.
남은 것은 다음과 같습니다.

- **파티 영화 추천(API-058).** 백엔드에 아직 없어(`404`) 5.4 · 5.5가 목업입니다.
  `getPartyRecommendations` · `getPartyRecommendationReasons`가 그 자리입니다
- **5.9 팝콘 섞기의 수치(CR-17).** 참여자별 취향 비율과 공통 취향 일치도를 내려주는
  계약이 없습니다
- **폴링.** 초대 수락이 파티원 전원에게 반영되는 갱신 방식이 `폴링 가정`으로만 적혀 있어
  주기와 대상이 정해지지 않았습니다. 지금은 화면을 다시 열어야 바뀝니다
- **초대 목록 이어 받기.** API-052의 첫 장(`size=50`)만 읽습니다. 받은 초대를 펼치는
  화면(8.1 알림)이 아직 없어 이어 받을 자리가 없습니다
- **초대 단건 조회.** 계약이 없어 5.6은 목록에서 번호로 고릅니다. 이미 답한 초대는
  목록에 없어 찾지 못한 상태가 됩니다
