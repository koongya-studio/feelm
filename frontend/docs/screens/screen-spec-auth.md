# Screen Spec — 가입·로그인 (0.1 ~ 0.7-A)

업무 `S15P21E106-302` 산출물 · 에픽 `S15P21E106-301`

기준 자료는 `Feelm UI Wireframe Final.html` 67프레임 중 0.x 여덟 장입니다. 표기 규칙
(`[W]` `[C]` `[?]` `[!]`)과 공통 사항은 [`screen-spec.md`](./screen-spec.md) 2·3장을
따릅니다.

**[`screen-spec.md`](./screen-spec.md)와 나누어 두는 이유.** 그 문서는 에픽
`S15P21E106-266`의 15개 화면으로 범위를 못 박고 있습니다(1장). 범위를 넓히면 그 에픽의
완료 기준이 흐려지므로, 에픽 301의 화면은 여기에 쌓습니다.

**깊이가 얕은 이유.** 이 여덟 화면에는 대응하는 API 계약이 아직 없습니다. 인증 방식은
ADR-0009가 토큰 전달만 정했고 가입·로그인 요청·응답은 확정되지 않았습니다. 그래서
`screen-spec.md`가 화면마다 갖는 **연동 API**·**상태** 절을 두지 않고, 와이어프레임에서
읽히는 요소와 이동만 적었습니다. 계약이 나오면 그때 채웁니다.

### 0.3-A 소셜 가입 정보 입력

**요소** `[C]` (CR-23, 업무 S15P21E106-499)

| 요소 | 내용 |
| --- | --- |
| 제목 | 조금만 더 알려 주세요 |
| 안내 | `{제공자}` 계정으로 가입해요. 이메일과 비밀번호는 필요하지 않아요. |
| 입력 | 닉네임(제안값이 채워져 있음) + `중복 확인` · 생년월일 · 성별 |
| 주 버튼 | 가입하기 |

**연동 API** API-008 소셜 회원가입 완료 · API-016 닉네임 사용 가능 확인

API-008이 `nickname` · `birthDate` · `gender`를 필수로 받는데 이동표에는 받을 자리가
없었습니다. 이메일과 제공자 식별자는 `signupToken` 안에 있어 묻지 않습니다. 0.4와 같은
종이·타자기 구성이고(`SignupPaper`) 이메일·비밀번호 줄이 없어 세 줄로 끝납니다.

`signupToken`은 유효기간이 짧고 새로고침하면 사라지는 값이라 Router state로만 전달합니다.
토큰 없이 주소로 직접 들어오면 0.2로 돌려보냅니다.

| 실패 | 안내 |
| --- | --- |
| `SIGNUP_TOKEN_INVALID` | 가입 시간이 지났어요. 소셜 로그인부터 다시 해 주세요 |
| `EMAIL_DUPLICATED` | 이메일로 로그인한 뒤 소셜 계정을 연결해 주세요 (API-009) |
| `NICKNAME_DUPLICATED` | 중복 확인을 풀어 다시 고르게 합니다 |
| `OAUTH_ACCOUNT_ALREADY_LINKED` | 이미 다른 계정에 연결된 소셜 계정입니다 |

### 소셜 로그인 콜백 (화면 번호 없음)

제공자 동의 화면에서 돌아오는 자리입니다(`/oauth/callback`). 인가 코드를 제공자와
교환하는 것은 백엔드이므로(API-007 처리 규칙) 여기서는 주소의 `code`를 넘기고 결과에
따라 보내기만 합니다.

| 결과 | 이동 |
| --- | --- |
| 연결된 계정 있음 · `onboardingCompleted=false` | 1.1 취향 초기 설정 |
| 연결된 계정 있음 · `onboardingCompleted=true` | 2.1 홈 |
| `signupRequired` | 0.3-A (가입 토큰을 함께 넘김) |
| 동의 취소 · `state` 불일치 · 오류 | 안내 후 `로그인 화면으로` |

`state`는 이 앱이 시작한 요청인지 확인하는 값입니다. 맞지 않으면 남이 만든 인가 코드일
수 있으므로 백엔드에 넘기지 않습니다. 인가 코드는 1회용이라 StrictMode의 두 번째 실행이
같은 코드를 다시 보내지 않도록 막습니다(0.8과 같은 자리, S15P21E106-366).

### 0.4 이메일 회원가입 정보 입력

**요소** `[W]`

| 순서 | 요소 |
| --- | --- |
| 1 | 닉네임 + `중복 확인` |
| 2 | 생년월일 (`YYYY-MM-DD`) |
| 3 | 성별 — 여성 · 남성 · 선택 안 함 |
| 4 | 이메일 |
| 5 | 비밀번호 |
| 6 | 비밀번호 재확인 |
| 7 | 가입하기 (`소셜 계정으로 가입`은 종이 제목 아래로 옮김) |

`[!]` **와이어프레임의 `인증요청`·`인증번호 6자리`·`확인`은 삭제 대상입니다**(CR-19).
인증번호를 확인하는 API가 계약에 없고, API-002는 인증 메일 링크에 실린 1회용 토큰을
받습니다. 가입 화면은 인증을 다루지 않고 0.8이 맡습니다. `나이`도 `생년월일`로 바뀝니다
(CR-20, API-001 `birthDate`). 팀 합의 2026-09-11.

성별 표시 문구는 그대로 두고 각각 계약의 `FEMALE` · `MALE` · `OTHER`에 대응시킵니다.

**타자기 종이** (팀 결정 2026-09-14, S15P21E106-319). 화면 아래에 코드로 그린 타자기가
붙고, 입력 칸은 롤러에서 올라오는 종이 위에 있습니다. 참고 시안은 와인색 배경·세리프
제목이었지만 **확정 톤(밝은 쿨그레이 벽, 무채색 UI)을 유지하고 연출만 가져왔습니다**
(`design-concept.md` 3장).

| 동작 | 내용 |
| --- | --- |
| 처음 | 종이 제목(`CREATE YOUR FEELM` · `지금 당신의 필름을 시작하세요` · `소셜 계정으로 가입`)과 닉네임 줄만 나와 있음 |
| 줄 나옴 | 한 줄에 입력하면 다음 줄이 롤러에서 밀려 나옴. 순서는 위 표와 같고 마지막은 `가입하기` |
| 되돌림 없음 | 입력을 지워도 나온 줄은 들어가지 않음 |
| 타자 | 글자를 칠 때마다 종이가 3px 튀고 타자기 키 하나가 눌림 (장식이며 누를 수 없음) |
| 나오지 않은 줄 | 높이 0 · `inert`라 초점이 가지 않음 |
| 움직임 줄이기 | `prefers-reduced-motion`이면 튀는 움직임을 끄고 줄은 곧바로 열림 |

`소셜 계정으로 가입`은 입력과 무관한 이동이라 줄을 기다리지 않도록 종이 제목 아래에 둡니다.

**닉네임 중복 확인** (팀 결정 2026-09-14, S15P21E106-319). 닉네임 칸 안 오른쪽의
`중복 확인`이 API-016을 부릅니다. 자동 확인이 아니라 누르는 방식입니다.

| 상태 | 표시 |
| --- | --- |
| 확인 전 | 칸 아래 규칙 `한글·영문·숫자·_ 2~10자` |
| 확인 중 | 버튼 문구 `확인 중…`, 버튼 비활성 |
| 사용 가능 | 칸 아래 `사용할 수 있는 닉네임이에요.`, 버튼 비활성 |
| 중복 (`DUPLICATED`) | 테두리 오류 + `이미 사용 중인 닉네임이에요.` |
| 형식 위반 | 서버를 부르지 않고 테두리 오류 + 규칙 안내 |
| 확인 실패 | 테두리 오류 + `확인하지 못했어요. 잠시 후 다시 시도해 주세요.` |

사용 가능을 받지 않았거나 받은 뒤 닉네임을 고쳤으면 `가입하기`가 요청을 보내지 않고
`닉네임 중복 확인을 해 주세요.`를 띄웁니다. 확인은 예약이 아니므로(API-016) 가입에서
`409 NICKNAME_DUPLICATED`가 오면 확인을 풀고 중복으로 표시합니다.

`[!]` **와이어프레임 0.4만 이전 팔레트로 그려져 있습니다.** 옥스블러드(`#4A0D0D`)
테두리와 원형 소셜 표식은 폐기된 이전 방향의 잔재입니다(`design-concept.md` 4장).
화면 아래쪽은 벡터가 아니라 이미지 한 장이라 제출 버튼이 그 안에 들어 있습니다. 구성과
문구는 그대로 두고 표현만 확정 방향으로 옮겼으며, 제출 버튼 문구는 이동표의
`이메일 회원가입 완료`를 근거로 `가입하기`로 두었습니다.

### 0.5 회원가입 완료

**요소** `[W]` 제목 `회원가입 완료!` · 문구 `첫 취향 필름을 만들어볼까요?` · 주 버튼 `시작하기`

**빨간 봉투의 초대장** (팀 결정 2026-09-14, S15P21E106-319). 첫 장면은 봉인된 빨간 편지
사진이고, 봉인이 한 번 눌린 뒤 열린 빨간 봉투 그림으로 바뀌며 초대장이 봉투 안에서
올라옵니다. 초대장 문구(`FEELM` · `Welcome!` ·
`회원가입 완료 되었습니다` · `WELCOME TO FEELM`)는 그림 안에 있으므로 제목(h1)
`회원가입이 완료되었습니다`는 화면에 보이지 않게 두어 보조기술만 읽습니다.

- 첫 장면은 받은 봉인된 빨간 편지 사진(1672×941)을 WebP로 옮긴
  `src/assets/signup/feelm-sealed-envelope.webp`(1080×608, 29KB)입니다. 모서리는
  사진 그대로 각지게 두고 그림자만 줍니다
- 열린 봉투는 받은 누끼 PNG(1536×1024, 투명 배경)를 WebP로 옮긴
  `src/assets/signup/feelm-welcome-envelope.webp`(1080×720, 74KB)입니다
- 두 그림은 구도가 달라 이어 붙일 수 없어 겹쳐서 넘깁니다. 봉인 위치를 맞춰 겹치고
  (봉인된 편지를 폭의 19.47%만큼 내림), 봉인을 축으로 봉인된 편지는 줄어들며 사라지고
  열린 봉투는 커진 채 나타나 제 크기로 돌아옵니다. 그래서 봉인이 제자리에 머뭅니다
- 그림 한 장을 같은 자리에 네 번 깔고 봉투 뒷면 · 초대장 · 앞 주머니 · 봉인으로 오립니다.
  끝 상태에서는 원래 그림과 똑같습니다. 좌표는 그림에서 잰 값입니다 — 초대장 가로
  13.7% ~ 86.5% · 윗변 14.8%, 앞 주머니 V선 (9.4%, 43%) → (50%, 77.1%), 봉인 중심
  (49.5%, 73.7%)
- 초대장이 비운 자리(봉투 안쪽)만 코드로 칠합니다
- 봉투와 봉인의 빨강은 아트워크 안의 색입니다

| 시점 | 움직임 |
| --- | --- |
| 0 ~ 0.33초 | 봉인된 빨간 편지가 떠오르며 나타남 |
| 0.65 ~ 1.03초 | 봉인이 한 번 눌림 |
| 1.19 ~ 1.81초 | 봉인된 편지가 줄어들며 사라지고 열린 봉투가 나타남. 초대장은 앞 주머니 뒤에 숨어 있음 |
| 1.72 ~ 2.62초 | 초대장이 봉투 안에서 올라옴 |
| 2.55초 ~ | 아래 안내 문구와 버튼이 나타남 |

`prefers-reduced-motion`이면 움직이지 않고 끝 상태로 곧바로 그립니다.

`[!]` **인증 메일 발송 안내와 재발송 경로가 필요합니다**(CR-19). 가입 직후 계정은
`PENDING_VERIFICATION`이며 인증을 마쳐야 로그인할 수 있으므로(API-001), 이 화면이 곧바로
`시작하기`로 이어지면 사용자는 로그인에서 막힙니다. 메일을 보냈다는 사실과 재발송(API-003)을
함께 둡니다. 재발송은 계정 존재 여부를 알려주지 않으므로 성공·실패를 나누지 않습니다.

### 0.7 비밀번호 찾기

**요소** `[C]` (CR-21 · CR-25, 업무 S15P21E106-391 · -455)

| 요소 | 내용 |
| --- | --- |
| 안내 | 가입할 때 사용한 이메일로 / 비밀번호 재설정 링크를 보내드려요 |
| 입력 | 이메일 |
| 주 버튼 | 재설정 링크 받기 (보낸 뒤에는 `메일 다시 보내기`) |
| 안내(보낸 뒤) | 가입된 계정이 있다면 재설정 링크를 보냈어요. 메일함을 확인해 주세요 |
| 하단 | 로그인으로 돌아가기 |

**와이어프레임의 인증번호 요소는 쓰지 않습니다**(CR-21, 업무 S15P21E106-391). 계약에
인증번호를 확인하는 API가 없어 API-010이 재설정 메일을 보내는 형태로 바꿨습니다. 그래서
`이메일 + 인증번호 요청` · `인증번호` · 남은 시간 `02:47` · `다시 보내기` · `확인`이
모두 빠졌습니다.

**보냈다고 단정하지 않습니다.** 계약이 계정 유무와 무관하게 `202`로 답하는 이유가
가입 여부를 숨기는 것인데(API-010 처리 규칙), 화면이 단정하면 응답이 숨긴 것을 화면이
드러냅니다. `429 RATE_LIMITED`만 따로 안내합니다.

**연동 API** `[C]` API-010 비밀번호 재설정 요청

**아이디 찾기 탭을 없앴습니다** (CR-25, 팀 결정 2026-09-17, 업무 S15P21E106-455).

| 항목 | 내용 |
| --- | --- |
| 화면 | 탭 줄이 사라지고 비밀번호 찾기 하나만 남습니다. 화면 이름도 `계정 찾기`에서 `비밀번호 찾기`로 바꿉니다 |
| 진입 | 0.6의 `아이디 찾기` 링크와 7.8-A의 `아이디 찾기` 줄을 함께 지웁니다 |
| 유지 | 경로 `/account/find`와 화면 번호 0.7은 그대로입니다. 들어오는 링크가 여럿이라 경로를 바꾸면 변경 범위만 넓어집니다 |

근거는 셋입니다. **아이디가 곧 이메일입니다** — 로그인 식별자가 이메일이고(API-004),
이메일을 입력해 아이디를 돌려받는 흐름은 순환입니다. **계약에 대응 API가 없습니다** —
`docs/api/users.md`의 API-001 ~ API-022 어디에도 인증번호 요청·확인도, 찾은 아이디를
돌려주는 경로도 없습니다. **요구사항에도 근거가 없습니다** — FR-01 인수 조건은 가입·인증·
중복 검사만 정하고 아이디 찾기를 요구하지 않습니다.

계약에 추가하는 쪽은 택하지 않았습니다. API 신설과 시도 제한 설계가 따라오는데, 그렇게
얻는 것이 이미 비밀번호 재설정 메일이 하고 있는 일(가입 이메일 확인)과 겹칩니다. 가입에
쓴 이메일을 잊은 사용자는 어느 쪽 경로로도 그 이메일을 특정할 수 없습니다.

7.8-A는 로그인한 사용자의 화면이라 근거가 하나 더 있습니다. 그 화면은 헤더에 계정
이메일을 이미 띄우고 있습니다(API-014).

### 0.7-A 비밀번호 재설정

**요소** `[W]`

| 요소 | 내용 |
| --- | --- |
| 안내 | 이메일 인증이 완료됐어요 / 새 비밀번호를 설정해 주세요 |
| 입력 | 새 비밀번호 · 새 비밀번호 확인 |
| 규칙 | 8~64자, 영문·숫자·특수문자 포함 |
| 주 버튼 | 비밀번호 변경 |
| 하단 | 로그인으로 돌아가기 |

규칙은 계약(`docs/api/users.md`)을 따릅니다. 와이어프레임은 `8자 이상, 영문과 숫자 포함`이라
적었지만 계약보다 느슨해 화면 안내대로 입력해도 서버가 거절했습니다(S15P21E106-448). 문구와
검사를 한 곳(`src/pages/auth/password.ts`)에서 가져다 써서 둘이 어긋나지 않게 했고, 가입
화면(0.4)도 같은 규칙을 씁니다.

**재설정 메일의 링크로 열립니다**(CR-21, 업무 S15P21E106-391). 주소의 `token`을 그대로
API-011에 넘깁니다 — 0.8과 같이 서버가 발급한 불투명 문자열이라 해석하지 않습니다. 링크
주소는 백엔드 설정값(`feelm.mail.password-reset-url`)과 같아야 합니다. 와이어프레임의
`이메일 인증이 완료됐어요`가 오히려 이 상태와 맞습니다.

| 상태 | 계약 | 화면이 할 일 |
| --- | --- | --- |
| 성공 | `204` | 전 기기 로그아웃을 알리고 0.6으로 보냅니다 |
| 토큰 없음 | — | 주소에 `token`이 없습니다. 아래 위조와 같이 다룹니다 |
| 위조·소진 | `400 RESET_TOKEN_INVALID` | 입력을 감추고 0.7에서 다시 받게 합니다 |
| 만료 | `410 RESET_TOKEN_EXPIRED` | 위와 같습니다. 문구만 만료로 가릅니다 |
| 정책 위반 | `400 VALIDATION_FAILED` | 입력을 그대로 두고 서버 문구를 보여줍니다 |

성공하면 서버가 모든 Refresh Token을 폐기합니다(API-011 처리 규칙). 다른 기기도 로그인이
풀리므로 그 사실을 알립니다.

### 0.8 이메일 인증

CR-19로 새로 생기는 화면입니다. 와이어프레임에 없으므로 표시는 0.5와 같은 전환·완료 형태를
따릅니다.

인증 메일의 링크로 열리며 주소의 `token`으로 API-002를 호출합니다. 토큰은 서버가 발급한
불투명 문자열이므로 클라이언트는 해석하지 않고 그대로 넘깁니다.

| 상태 | 계약 | 화면이 할 일 |
| --- | --- | --- |
| 성공 | `200` 계정이 `ACTIVE` | **0.8-A로 넘깁니다** (`replace`) |
| 토큰 위조·형식 오류 | `400 VERIFICATION_TOKEN_INVALID` | 링크가 올바르지 않다고 알립니다 |
| 만료 | `410 VERIFICATION_TOKEN_EXPIRED` | 만료를 알리고 **재발송(API-003) 경로를 줍니다** |
| 이미 인증됨 | `409 ALREADY_VERIFIED` | 이미 인증됐다고 알리고 0.6으로 보냅니다 |

네 상태를 한 문구로 뭉뚱그리면 사용자가 다음에 무엇을 할지 알 수 없습니다. 만료만 재발송이
필요하고 나머지는 아닙니다.

`[!]` **백엔드가 보내는 링크 주소와 이 화면의 경로가 일치해야 합니다.** 현재 설정값은
`{FRONTEND_BASE_URL}/verify-email`인데 프론트엔드는 Vite base가 `/app/`이라 실제 주소가
다릅니다. 경로 정정은 S15P21E106-367에서 다룹니다.
