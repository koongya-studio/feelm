## 1.1 OTT 추천에서 다시 정한 것 (2026-09-19)

1장이 `와이어프레임대로`로 둔 OTT 값들을 **화면에서 뺐다**(업무 S15P21E106-563 ·
지시서 CR-28). 2026-09-13에는 계약이 침묵하는 값으로 봤지만, API-068 처리 규칙이
`Redis 점수는 상대 순위만 보장하므로 similarity나 취향 일치 확률로 응답하지 않는다`고,
FR-40 인수 조건이 `점수를 유사도·확률로 표시하지 않는다`고 이미 정하고 있다. 계약이
**주지 않기로 정한 값**이므로 계약 우선 원칙을 그대로 적용한다.

| 화면 | 뺀 것 | 대신 쓰는 것 |
| --- | --- | --- |
| EXT-01 | 본 영화 · 선호 장르 · 자주 본 배우 | `평가 N개`(API-014 `stats.ratingCount`) · OTT 배지(API-025) |
| EXT-03 | 1위 카드의 일치도 % · 한 줄 요약, 목록 줄의 일치도 % · 장르 요약 | `좋아할 만한 작품 N편`(`matchCount`) |
| EXT-04 | 일치도 링 · `잘 맞는 이유` · `취향 항목별 일치도` | `좋아할 만한 영화 N편`과 `topMovies` 3편 |
| EXT-05 | `현재 진행도 N/10` 막대와 기준 평가 수 | 안내 문구와 버튼 둘 |

EXT-05는 EXT-01에서 평가 수로 미리 가르지 않고 **API-068이 `insufficientData: true`를 주거나
`items`가 비어 있을 때** 보여준다. 기준 평가 수가 계약에 없고, 계약은 현재 Candidate가 있으면
취향 입력이 0건이어도 `insufficientData`를 `false`로 준다.

`OttRecommendationItemView` · `OttAnalysisBasis` · `OttRecommendationView`는 이 결정으로
필요가 없어져 `types/unspecified.ts`에서 지운다. EXT-04 단건은 계약에 단건 조회가 없어
목록에서 찾는 방식을 유지한다. `503 RECOMMENDATION_UNAVAILABLE`은 2.2-A와 같이 장애가 아니라
**준비 중**으로 안내한다. 화면 반영은 업무 S15P21E106-564다.

## 1.2 K=0 OTT 집계 표시 (2026-09-21)

업무 S15P21E106-565에서 취향 입력 0건(K=0)의 현재 동작을 확인했다. Consumer는 서비스 가능한
영화를 `0.0` 동점 TASTE 후보로 게시하고, API-068은 개인화 사용자와 같은 방식으로 평가·관심없음·
활성 감상 영화를 제외한 뒤 OTT별 작품 수를 집계한다. Candidate가 있으면 K=0이어도
`insufficientData: false`이며 응답 모양과 정렬 계약도 바뀌지 않는다.

화면은 API-014 `stats.ratingCount`로 K=0을 판정한다. 0이면 `취향 일치`, `좋아할 만한 작품`,
`인기순`을 주장하지 않는다. 대신 `아직 취향을 알아가는 중`으로 개인화 전 상태를, `지금 볼 수
있는 작품 수`로 정렬 근거를 명시한다. `영화를 평가하면 내 취향에 맞춘 결과로 바뀐다`는 개인화
전환 조건도 함께 안내한다. 첫 평가가 저장돼 `ratingCount`가 1 이상이 되면 기존 개인 추천 문구로
전환한다. 분석 중 화면도 이 판정값을 전달받아 K=0에는 OTT별 작품 확인·제외·집계 단계를, 평가가
있으면 장르·별점 기반 취향 비교 단계를 보여준다. 주소로 직접 접근해 판정값이 없으면 API-014로
복원하며, 조회에 실패해 상태를 확인하지 못한 분석·결과·상세 화면은 어느 상태도 단정하지 않는
중립 문구를 사용한다.

K=0 후보 공급원, 인기순 재정렬과 개인화 점수 정책은 이 결정에 포함하지 않는다. API-068 응답 필드와
Consumer Candidate 계약도 변경하지 않는다.

### 리포트의 모양 — 취향 4컷 인화지

**길게 이어진 검정 인화지 안에 같은 크기의 사진 네 컷이 세로로 놓인다**(사용자 시안 2026-09-15,

| 자리 | 내용 |
| --- | --- |
| 머리 | `{닉네임}의 취향 4컷`(API-014, 못 불러오면 `나의`) · 인화한 달 `SEPTEMBER 2026` |
| 01 장르 | 흑백 사진 · 굵고 좁은 빨간 영문(Anton). 누끼면 글자가 인물 뒤로 들어간다 |
| 02 감독 | 빨간 바탕 · 오른쪽 흑백 인물 · 왼쪽 위 대표작 · 흰 세리프 이탤릭 대문자 |
| 03 배우 | 흑백 인물을 크게 자름 · 흰 이탤릭 + 마지막 단어만 빨간 대문자(Playfair Display) · 별표 |
| 04 캐릭터 | 컬러 사진 · 흰 세리프 이탤릭 · 빨간 밑줄. 고정 16종의 저장소 에셋을 `characterCard.code`로 짝지어 쓴다 |
| 발 | Feelm 로고 · `2026.09` |

3.3 · 3.4 · 7.4가 같은 `components/ReportFourCut`을 쓴다.

- **데이터는 사진 · 이름 · 날짜뿐이다.** 칸 크기 · 색 · 서체 · 간격 · 글자 상자는 고정이다. 모든 길이가
  인화지 폭의 비율(시안 폭 385 기준)이라 폭만 바뀌어도 모양이 같다
- 머리 · 라벨 · 한글 이름 · 날짜는 폭에 비례하되 최소 크기(11 ~ 14px) 아래로 줄지 않는다. 3.3 인화기 속
  4컷만 연출이라 최소 크기를 끈다. 3.4 · 7.4 상세의 4컷 폭은 248px이다
- 이름은 글자 상자 안에서 최대 두 줄로 작아진다. 한 단어가 길면 줄을 바꾸지 않고 작아지고,
  가장 작게 해도 넘치면 그때만 단어 중간에서 바꾼다
- 사진은 `url`(원본) · `cutoutUrl`(누끼) · `position` · `zoom`을 받는다. 누끼가 있으면 단색 바탕 위에
  인물을 올리고, 원본만 있으면 원래 배경에 어두운 그라데이션을 깐다. **화면이 누끼를 만들지 않는다**
- 사진이 없거나 못 불러오면 칸은 그대로 두고 이름을 크게 쓴다. 누끼 → 원본 → 없음 순으로 넘어간다
- `[!]` 인화지 안의 빨강은 콘텐츠다. 앱 UI의 무채색 규칙(`design-concept.md` 3장)은 인화지 바깥에만 적용한다
- `[!]` 01 ~ 03의 사진 · 누끼 · 영문 이름 · 감독 대표작은 API-060에 없다(`types/unspecified.ts` `ReportFourCutView`).
  목업 사진은 시안 이미지에서 잘라 낸 자리표시자다(`mocks/images/reports/`)
- **04 캐릭터 칸은 예외다.** 캐릭터 카드가 고정 16종이므로(API-060, 업무 -618) 그림 파일을 저장소가
  갖고 화면이 `characterCard.code`로 짝짓는다. `PopcornBucket/sprites.ts`가 같은 이유로 이미 이 구조다.

### 7.3 취향 4컷 목록

**모눈 노트에 반기마다 받은 4컷을 빨간 테이프로 붙여 모아 둔 장면이다**(사용자 시안 2026-09-15, 업무 -446).
처음의 필름 칸 목록(2026-09-13)을 바꿨다.

- 머리는 가운데 `취향 4컷` · `차곡차곡 모아둔 나의 영화 취향`, 오른쪽에 공유다
- 연도마다 손글씨 연도(Caveat)와 가로줄을 긋고, 그 아래 두 반기의 4컷을 나란히 붙인다. 연도는 최신이
  위, **한 해 안에서는 최근 반기가 왼쪽**이다(시안). 4컷 아래에 인화한 날짜(`2026.07`)를 적는다
- **두 해 네 장이 스크롤 없이 한 화면에 들어온다**(사용자 요청 2026-09-15). 4컷 크기를 화면 높이에서 거꾸로
  구한다(412 × 892에서 폭 88px). 화면이 너무 낮으면 72px에서 멈추고 스크롤된다
- 4컷은 `ReportFourCut`을 머리 없이(`head={false}`) 쓴다. 작은 글자의 최소 크기는 끈다.
  조금씩 기울이고 윗변에 테이프를 붙인다. 누르면 7.4다
- 만드는 중(`GENERATING`)인 반기는 빗금 친 빈 인화지에 `인화 중`을 적고 누를 수 없다. 4컷 한 장을 못
  불러오면 그 자리만 빈 인화지로 두고 7.4로는 갈 수 있다. 리포트가 없으면 `아직 인화된 취향 4컷이 없어요`다
- 벽은 앱 공통 벽이고 그 위에 옅은 모눈(22px)만 긋는다. 시안 종이는 조금 따뜻하지만 벽 색은 바꾸지 않았다
- `[!]` API-059 목록에 4컷 값이 없어 반기마다 API-060을 한 번씩 더 부른다. 연동 때 목록에 4컷 요약을 넣을지 정해야 한다
- `[?]` 공유가 무엇을 공유하는지 시안에 없다. 기기 공유 메뉴가 있을 때만 버튼을 두고 이 화면 주소를 넘긴다

### 3.3 새 취향 리포트 발급

**버건디 벽에 박힌 4컷 인화기에서 4컷이 내려오는 장면이다**(팀 결정 2026-09-14, 업무 -321).

- 인화기는 받은 사진 `4컷리포트_기계.png`(1024 × 1536)를 WebP로 옮긴
  `src/assets/reports/report-printer.webp`(68KB)다. 화면에 420 × 630으로 둔다
- 4컷 인화지가 아래 롤러 밑(사진 높이 29.3%)에서 실제 인화기처럼 **끝부터 한 컷씩** 밀려 나와 금속
  판을 타고 받침대 앞턱 **위로** 넘어 인화기 밖까지 내려온다(시안). 로고 + 04 → 03 → 02 → 01 → 머리
  순서로 칸 경계에서 0.45초씩 멈추고, 전체 5.6초다. 나온 칸은 빈 인화지에서 1.6초 동안 사진으로
  현상된다. 롤러 위로는 보이지 않는다
- 인화지가 나오는 동안 머리 오른쪽에 `건너뛰기`(글자 버튼)가 있다. 누르면 다 나온 모습으로 바로 넘어가고,
  다 나오거나 움직임 줄이기면 보이지 않는다
- 인화지 폭은 사진 폭의 32.7%(시안에서 금속 틀 폭의 48%)다. 공용 `ReportFourCut`에 폭만 준다
- `[!]` **이 화면만 배경이 버건디다.** 앱은 한 벽을 쓰지만(`design-concept.md` 2.1) 사진의
  벽과 이어지도록 예외로 둔다. 색은 사진 네 귀퉁이에서 잰 값이다. 글자와 요약 테두리는 어두운 면
  색이고, `리포트 보기`는 흰 알약이다. 불러오지 못한 상태는 인화기가 없으니 공통 벽이다

### 3.4 · 7.4 취향 리포트 상세

한 컴포넌트(`ReportDetailPage`)가 `from`으로 `저장`의 목적지만 가른다.
벽은 앱 공통 벽이다. 버건디는 인화기가 있는 3.3에만 쓴다(사용자 결정 2026-09-15). 맨 위가 4컷이다. 비교의 빼기는 흐리게 쓰고 색으로 가르지 않는다.

### 3.5 공유

Web Share API로 기기 공유 메뉴를 연다. `이미지로 저장`은 API-061로 이미지 카드를 만들고
안내만 한다 — 목업에 실제 이미지가 없다.

### 8.1 알림

API-070 ~ 074를 서버 정본으로 사용합니다(업무 S15P21E106-537). `WATCH_CONFIRM` ·
`PARTY_INVITE` · `PARTY_INVITE_ACCEPTED`의 **세 가지 알림 유형을 종류 구분 없이 최신순 단일
목록으로 표시**합니다. 각 알림의 `targetType`과 `targetId`에 따라 감상 확인은 2.4-A, 파티 초대는
5.6, 파티 초대 수락은 5.8로 이어집니다. 읽음 · 모두 읽음 · 목록 삭제는 서버에 저장되어 새로고침
뒤에도 유지됩니다. 8.2 잠금화면 예시는 같은 목록 중 가장 최근 감상 확인 알림을 사용합니다.

읽지 않음은 빨간 점이다(`design-concept.md` 2.2). 시각은 상대 시각이다 — 3.1은 절대 날짜로
정했지만(2026-09-07) 알림은 언제 왔는지가 내용이다. 이틀이 지나면 날짜로 바꾼다.

- API-070 목록은 `hasNext=false`까지 읽고, 각 항목은 서버가 준 `notificationId`로 식별한다
- API-072로 개별 읽음, API-073으로 모두 읽음을 처리한다. 알림이 있으면 `모두 읽음`을 항상 두되,
  읽지 않은 알림이 없으면 비활성화한다
- 화면에는 `삭제`로 표시하지만 API-074는 원본 파티 초대·감상 기록을 지우지 않고 알림 목록에서만
  숨기는 소프트 삭제다
- 감상 확인은 확인 시 목록에서 사라지고 OTT 이동 후 최대 7일, 파티 초대는 응답 시 사라지고 최대
  90일, 파티 초대 수락은 90일까지 보관된다는 안내를 각 알림의 상대 시각 옆에 표시한다
- API-070이 실패하면 전체 오류와 다시 시도를 보이고, 읽음·삭제 동작이 실패하면 목록을 유지한 채
  동작 오류를 알린다
- 동시에 시작한 목록 요청은 진행 중인 요청을 공유한다

### EXT-02 분석 중

시간으로 둔다. 서버 진행과 이어진 값이 아니다.
