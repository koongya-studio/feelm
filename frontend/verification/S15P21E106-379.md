# 온보딩·OTT 연동 검증 기록

2026-09-15, 실제 백엔드를 띄우고 계약 응답을 직접 확인한 결과입니다. 대상은 온보딩 초기
취향과 구독 OTT 연동(S15P21E106-379, API-023 ~ API-027)입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 확인하지 못한
것은 4장에 있습니다.

인증 세션과 가입 흐름은 [S15P21E106-376.md](./S15P21E106-376.md)에 있습니다.

## 1. 왜 남기는가

이 연동에서 화면이 의존하는 것은 **응답의 모양**입니다. 목업 시절 세 함수가 모두
`Ott[]`를 돌려주었는데 계약은 API-025만 목록이고 API-026 · API-027은 식별자 배열입니다.
모양이 어긋나면 화면은 오류 없이 그려지면서 값만 비는 형태로 실패하므로, 자동 테스트로
고정한 것과 별개로 실제 응답을 한 번은 눈으로 봐야 합니다.

`ottId`는 적재 결과로 정해지는 값이라 더 그렇습니다. 화면도 목업도 이 값을 지어낼 수
없고, seed가 실제로 무엇을 넣는지 확인해야 목업 기준표(`src/mocks/otts.ts`)를 맞출 수
있습니다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | `local` 프로파일, `MAIL_MODE=log` |
| DB | `infra/compose`의 로컬 PostgreSQL. `otts` 5행, **`movies` 0행** |
| 계정 | 가입(API-001) 후 로컬 DB에서 `status='ACTIVE'`로 바꾼 확인용 계정 |

메일 링크 흐름은 이 업무의 대상이 아니라(S15P21E106-366에서 확인) 계정 활성만 DB에서
처리했습니다.

## 3. 확인한 것

### API-025 OTT 목록 조회

`GET /api/v1/otts` (토큰 없이)

```json
{ "items": [ { "ottId": 1, "code": "NETFLIX", "name": "넷플릭스",
  "logoUrl": "https://image.tmdb.org/t/p/original/rK1KljqmbvO9HQa1PBFLILWah72.png" }, ... ] }
```

- 확정 5종이 `ottId` 오름차순으로 왔습니다 — 1 넷플릭스 · 2 디즈니+ · 3 왓챠 · 4 웨이브 · 5 티빙
- `logoUrl`은 TMDb 절대 주소입니다. 배지가 이 값을 씁니다
- `Cache-Control: max-age=86400, public`

새 환경의 seed(`V202609142240__seed_approved_ott_catalog.sql`)가 실제로 넣는 식별자가
이 순서였습니다. `src/mocks/otts.ts`의 기준표를 여기에 맞췄습니다. 다만 적재는 기존
환경의 식별자를 보존하므로 **어디서나 이 순서라고 가정하면 안 됩니다**(API-025 처리 규칙).

### API-026 · API-027 구독 OTT

| 요청 | 응답 |
| --- | --- |
| `GET /users/me/otts` (설정 전) | `{"ottIds":[]}` |
| `PUT /users/me/otts` `{"ottIds":[5,1,1,3]}` | `{"ottIds":[1,3,5]}` |
| `GET /users/me/otts` | `{"ottIds":[1,3,5]}` |
| `PUT /users/me/otts` `{"ottIds":[]}` | `{"ottIds":[]}` |

- **설정한 적이 없으면 빈 배열**입니다. 목업이 돌려주던 기준값 `[1,2,3,4]`는 계약에
  없습니다. 6.1은 이제 구독 중 묶음 없이 다섯 개를 모두 미구독으로 보여줍니다
- 중복은 제거되고 오름차순으로 정렬돼 돌아옵니다. 보낸 값과 받은 값이 다르므로 화면은
  **받은 값**을 반영합니다(1.2의 `completeOtt`)

### API-023 · API-024 온보딩

| 요청 | 응답 |
| --- | --- |
| `GET /onboarding/cards?size=10` | `200` `{"items":[]}` |
| `GET /onboarding/cards?size=41` | `400 VALIDATION_FAILED` (`size`는 40 이하) |
| `POST /onboarding/preferences` `{"preferences":[],"skipped":true}` | `200` `{"onboardingCompleted":true,"savedCount":0,"skipped":true}` |
| 같은 요청 재시도 | `409 ONBOARDING_ALREADY_COMPLETED` |
| `GET /onboarding/cards` (마친 사용자) | `409 ONBOARDING_ALREADY_COMPLETED` |
| `POST /onboarding/preferences` `{"skipped":true}` | `400` `details.errors[].field = "preferences"` |

- 오류 코드 문자열이 화면이 분기하는 값과 같습니다. 1.1은 `409`를 실패 안내가 아니라
  **홈으로 보내는 신호**로 씁니다
- **카드가 0장인 것은 결함이 아닙니다.** 로컬 DB에 영화가 없습니다. 대표 맛이 배정된
  영화가 있어야 카드가 만들어집니다(API-023 처리 규칙 · ADR-0015)

## 4. 확인하지 못한 것

| 항목 | 이유 |
| --- | --- |
| 카드가 실제로 그려지는 모습 | 로컬 DB에 영화가 없어 `items`가 빈 배열입니다. 적재된 환경에서 다시 봐야 합니다 |
| 카드 10장의 배치가 겹치지 않는지 | 위와 같은 이유입니다. 좌표는 서로 겹치지 않게 잡았지만 실제 화면에서 보지 못했습니다 |
| 로고 배지의 모습 | 브라우저 확인을 하지 못했습니다. 로고를 불러오지 못하면 글자로 떨어지는 경로는 자동 테스트가 아니라 `onError`에 기대고 있습니다 |
| 배포 환경 | 로컬만 확인했습니다 |

자동으로 고정한 것은 `src/api/otts.test.ts` · `src/api/onboarding.test.ts`(응답 모양과
요청 본문)와 `src/pages/onboarding/OnboardingFlow.test.tsx` ·
`src/pages/otts/OttManagePage/OttManagePage.test.tsx`(화면 거동)에 있습니다.
