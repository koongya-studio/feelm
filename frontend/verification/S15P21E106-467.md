# 1.1 취향 초기 설정 카드 노출 재확인 기록

2026-09-17, 대표 맛 배정(S15P21E106-466) 이후 배포 환경에서 1.1 화면을 다시 확인한
결과입니다. 앞선 확인은 [S15P21E106-449 검증 기록](./S15P21E106-449.md)에 있습니다.

**결론부터 — 재확인이 끝나지 않았습니다.** 466은 병합되어 배포에 반영됐지만 **영화에
배정된 대표 맛은 배포 DB에 아직 없습니다.** 카드가 실제로 뜨는 모습은 여전히 볼 수
없습니다. 다만 이번에 카드 배치와 제출 이동은 배포본에서 확인했습니다.

| Jira 완료 조건 | 판정 |
| --- | --- |
| 배포 환경에서 로그인하면 1.1에 영화 카드가 원 주변에 배치된다 | **보류** — 1.1까지는 실제로 들어가지지만 대표 맛이 배정된 영화가 0편이라 카드가 없습니다 |
| 모바일 폭에서 카드 10장이 서로 겹치지 않는다 | **통과**(초기 배치). 다만 값 선택 후에는 겹칩니다 — 5장 참고 |
| 카드를 골라 제출하면 1.2로 이동한다 | **부분 통과** — 배포본 화면은 이동합니다. 서버 제출은 확인 못 했습니다 |

## 1. 466은 어디까지 반영됐나

배포본 자체는 최신입니다. 코드가 낡아서 생긴 문제가 아닙니다.

| 확인 | 결과 |
| --- | --- |
| 466 병합 | `eca07bd` → `origin/develop` · `origin/main` 모두 포함 |
| 맛 시드 마이그레이션 | 반영됨. `GET /api/v1/popcorn-flavors` → `200`, 8종 |
| 표시명 · 색 | `-510`판까지 반영(`FLAVOR_B` = `다크초코` `#3C2418`) |
| 온보딩 카드 경로 `main ↔ develop` diff | 없음(`frontend/src/pages/onboarding` · `frontend/src/api/onboarding.ts` · `backend/.../domain/onboarding` · `db/migration`) |

즉 공개 맛 8종은 서비스에 올라와 있습니다. 비어 있는 것은 **영화 쪽 배정**입니다.

## 2. 대표 맛은 아직 배정돼 있지 않다

실제 계정으로 로그인해 받은 Access Token으로 `GET /api/v1/movies/{id}`를 호출했습니다.
`movieId`는 1~238,052 범위에서 고정 시드로 뽑은 무작위 120건입니다.

| 확인 | 결과 |
| --- | --- |
| 응답 성공 | 120건 / 120건 |
| `flavorCode`가 채워진 영화 | **0건** |
| `posterUrl`이 채워진 영화 | 109건 |

449 때의 15건 표본과 같은 결과이며, 표본을 8배로 늘려도 하나도 없습니다. 배정률이
466 설명대로 87%였다면 120건 전수가 `null`일 수 없습니다.

카드 질의는 `movies.representative_flavor_id = f.id`로 조인하므로(`OnboardingCardRepository`)
대표 맛이 없는 영화는 카드가 되지 않습니다. 배포 DB는 지금도 449와 같은 상태입니다.

**원인은 466의 반영 단계가 마이그레이션이 아니기 때문입니다.** `V202609161115`는
`popcorn_flavors` 8행만 넣고, 영화별 배정은 `pipeline/consumer/tools/apply_popcorn_flavors.py`가
439 번들을 읽어 씁니다. 이 도구는 기본이 rollback-only dry-run이라 운영자가 승인된 실행
창에서 `--apply`로 따로 돌려야 합니다(`pipeline/consumer/README.md`). 그 실행이 서비스
DB에 아직 반영되지 않았습니다. 배포를 다시 해도 채워지지 않습니다.

## 3. 계정 제약과 온보딩 리셋

확인에 쓴 배포 계정은 이미 온보딩을 마친 계정이라(`GET /users/me` → `onboardingCompleted: true`)
`GET /api/v1/onboarding/cards`가 `409 ONBOARDING_ALREADY_COMPLETED`였습니다. 계약대로의
동작이며, 그 상태로는 1.1에 머무를 수 없습니다.

그래서 백엔드 담당자가 배포 DB에서 해당 계정의 온보딩을 되돌렸습니다. 플래그만 내리면
재제출이 `uk_onboarding_preferences_user_id_movie_id`에 걸리므로 선택 행도 함께 지웁니다
(`OnboardingSubmitService`가 저장과 완료 전이를 한 트랜잭션에 두기 때문입니다).

```sql
DELETE FROM onboarding_preferences WHERE user_id = <id>;
DELETE FROM user_otts WHERE user_id = <id>;   -- 1.2까지 다시 보려면
UPDATE users SET onboarding_completed = false WHERE id = <id>;
```

실행 결과 `onboarding_preferences` 0행(이미 건너뛴 계정), `user_otts` 1행 삭제,
`users.onboarding_completed`가 `f`가 됐습니다. `status`는 `ACTIVE` 그대로입니다.

## 4. 리셋 후 실제 응답으로 본 1.1

| 확인 | 리셋 전 | 리셋 후 |
| --- | --- | --- |
| `GET /onboarding/cards?size=10` | `409 ONBOARDING_ALREADY_COMPLETED` | `200` `{"items":[]}` |
| `GET /onboarding/cards?size=40` | `409` | `200` `{"items":[]}` |
| `GET /users/me` | `onboardingCompleted: true` | `onboardingCompleted: false` |

브라우저에서도 같습니다. 로그인하면 곧바로 `/app/onboarding/taste`로 들어가고, 449가
만든 빈 목록 화면이 실제 응답으로 섭니다 — `지금은 보여드릴 영화가 없어요` ·
`잠시 후 다시 시도해 주세요` · `다시 시도` · `차차 찾아갈래요 (건너뛰기)`. 449는 이
화면을 스텁으로만 확인했고, 배포 응답으로 선 것은 이번이 처음입니다.

**건너뛰기는 누르지 않았습니다.** 누르면 API-024가 완료로 전이시켜 리셋이 풀리고,
대표 맛이 들어온 뒤의 재확인을 다시 막습니다. 계정은 온보딩 미완료 상태로 남겨 뒀습니다.

## 5. 배포본 화면에서 확인한 것

데이터와 계정이 막혀 있어, 배포된 번들을 그대로 쓰되 `GET /onboarding/cards` 응답만
브라우저에서 스텁으로 바꿔 화면을 확인했습니다. 스텁의 10장은 **배포 DB의 실제 영화**
(`movieId` 5 · 20 · 33 · 50 · 77 · 100 · 300 · 404 · 500 · 550)이며 `posterUrl`도 배포
API가 준 실제 값입니다. 449에서 못 본 **실제 포스터가 붙은 카드**를 여기서 처음 확인했습니다.

- 카드 10장 모두 포스터 이미지 로드 성공(`naturalWidth: 500`), 카드 크기 58×82px
- 자리표시자 없이 포스터가 그려지고, 카드마다 `⊖` 제거 버튼이 붙습니다

겹침은 카드 요소의 경계 상자를 모두 비교해 판정했습니다(45쌍 전수).

| 배치 영역 폭 | 카드 수 | 겹치는 쌍 |
| --- | --- | --- |
| 412px(기본) | 10 | **0** |
| 390px | 10 | **0** |
| 360px | 10 | **0** |
| 320px | 10 | **0** |

배치 영역은 뷰포트가 1440px일 때도 412px로 제한돼 있어, 이 화면의 배치는 창 폭이 아니라
배치 영역 폭이 정합니다. 그래서 폭은 배치 영역에 직접 걸어 확인했습니다. 창 자체를
모바일 크기로 줄여 미디어 쿼리까지 바꾼 확인은 아닙니다.

**값을 고른 뒤에는 겹칩니다.** 10장 중 3장에 `가까이` · `멀리` · `안 봤어요`를 주자
3쌍이 겹쳤고(최대 56×28px, 카드 넓이의 약 2/3) 배치 영역 폭을 320~412px로 바꿔도 겹침
크기가 같았습니다. 버튼으로 고른 카드는 `positionForValue`가 카드 순서에 따른 각도와
값에 따른 반지름으로 원 위에 올려놓는데, 그 자리가 아직 움직이지 않은 카드와 부딪힙니다.
초기 배치의 겹침을 막은 449의 범위 밖이고, Jira 완료 조건이 말하는 초기 배치는 아니지만,
사용자가 카드를 고르는 동안 실제로 보이는 모습이라 후속으로 남깁니다.

제출은 스텁 `200`으로 받았고, 화면은 `취향 설정 완료 (3개)` → **1.2 `구독 중인 OTT가
있으신가요?`** 로 이동했습니다. 1.2의 OTT 5종은 실제 API 응답입니다. 서버가 제출을
실제로 저장하는지는 이 확인에 포함되지 않습니다. 이 확인은 3장의 리셋 전에 했고, 그때는
실제 제출이 `409`였습니다.

확인 중 배포 DB에 쓴 값은 없습니다. 카드 조회와 제출 두 요청만 스텁으로 가로챘습니다.

## 6. 확인하지 못한 것

| 항목 | 이유 |

| 실제 응답으로 1.1에 카드가 뜨는 모습 | 대표 맛이 배정된 영화가 0편 |

## 7. 남은 일

1. **466 적재**: 서비스 DB에 `apply_popcorn_flavors.py --apply` 실행. 439 번들 URI와 승인된
   `mapping_revision`은 저장소에 없는 운영 값이라 466 담당자가 가지고 있습니다. 이것이
   되기 전에는 1.1 카드가 뜨지 않습니다.
2. 적재되면 이 문서의 1·3번 완료 조건을 실제 응답으로 다시 판정합니다. 계정은 온보딩
   미완료 상태로 남겨 뒀습니다.
