# 추천 기록 연동 검증 기록

2026-09-16, 로컬 백엔드를 띄우고 MY의 `추천 기록` 탭을 실제 응답으로 걸어 본 결과입니다.
대상은 추천 이력 조회(S15P21E106-478, API-048)입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 확인하지 못한
것은 5장에 있습니다.

`[!]` 이 업무를 하는 도중 S15P21E106-495가 **7.5 추천 기록 화면을 지우고** MY 탭으로
옮겼습니다. 아래는 옮겨진 뒤의 화면(`MyDashboardPage`의 `추천 기록` 탭)을 확인한 것입니다.

## 1. 왜 남기는가

**추천 이력은 아직 아무도 만들지 않습니다.** 이력은 API-045가 추천 세트를 만들 때
쌓이는데 백엔드에 세트 생성(Candidate v4 소비)이 없고, 2.2 오늘의 추천은 목업이라
이력을 남기지 않습니다. 그래서 앱을 아무리 눌러도 이 탭은 빈 목록입니다 — **화면이 실제
응답을 제대로 그리는지 확인하려면 데이터를 직접 넣는 수밖에 없습니다.**

그리고 이번에 붙인 `더 보기`는 **한 장(20세트)을 넘겨야만** 드러납니다. 자동 테스트는
두 장을 흉내 낼 뿐, 서버가 준 커서를 그대로 돌려줬을 때 다음 장이 정말 이어지는지는
실제 응답으로 봐야 합니다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | 이 작업 브랜치 소스, `local` 프로파일, `MAIL_MODE=log`, `AUTH_MOCK_ENABLED=true` |
| 백엔드 포트 | **8082**. 8080을 다른 작업이 쓰고 있어 비켜 띄웠습니다 |
| DB | **별도 데이터베이스 `feelm_478`**. 같은 로컬 PostgreSQL 컨테이너 안에 새로 만들었습니다 |
| Redis | `infra/compose`의 로컬 Redis(공용) |
| 프론트 | Vite dev 서버 **5175**, `VITE_API_PROXY_TARGET=http://localhost:8082` |
| 데이터 | 아래 3장의 임시 시드. 확인 뒤 `DROP DATABASE feelm_478`로 지웠습니다 |

DB를 따로 만든 이유는 [S15P21E106-477.md](./S15P21E106-477.md) 2장과 같습니다 — 공용
`feelm`을 다른 작업의 백엔드가 쓰고 있었습니다.

`AUTH_MOCK_ENABLED=true`는 API-048이 회원 전용이기 때문입니다. 계정을 가르는 확인이
아니라 고정 사용자 하나(`AUTH_MOCK_USER_ID=1`)로 충분합니다.

`[!]` `docker exec ... psql -f /tmp/seed.sql`은 Git Bash에서 **`MSYS_NO_PATHCONV=1`**을
붙이지 않으면 경로가 Windows 경로로 바뀌어 파일을 찾지 못합니다.

## 3. 시드 데이터

`recommendation_sets` · `recommendation_items`에 직접 넣었습니다(1장).

- 사용자 1명(`id=1`), 영화 22편(`9001~9022`, 세 편에 한 번꼴로 `poster_url`이 `NULL`)
- **노출된 세트 22개** — 2026-09-15부터 하루씩 거슬러 2026-08-25까지. 한 장(20세트)을
  넘깁니다. 세트마다 영화 한 줄, 세 번에 한 번은 `DISCOVERY`
- **노출되지 않은 버퍼 항목 1건**(`exposed_at IS NULL`) — 이력에 나오면 안 되는 줄
- `9001`은 관심없음(`user_movie_dismissals`), `9002`는 평가(`ratings`),
  `9003`은 감상 기록(`watch_records.status='WATCHED_UNRATED'`)

## 4. 확인한 것

### 계약 응답으로 확인한 것

| 요청 | 응답 |
| --- | --- |
| `GET /recommendations/history?size=2` | `200` · 세트 2개(최신순 7001 → 7002) · `hasNext: true` · `nextCursor` 있음 |
| 같은 응답의 `dismissed` · `watchStatus` | 9001 `dismissed: true` · 9002 `watchStatus: "RATED"` — **스냅샷이 아니라 지금 상태**가 옵니다 |
| 버퍼 항목(`exposed_at IS NULL`) | 응답에 없습니다 |

### 화면으로 확인한 것

| 화면 | 결과 |
| --- | --- |
| MY `추천 기록` 탭 첫 장 | 포스터 20칸. 칸마다 출처(`취향 맞춤` · `새로운 맛 발견`)와 날짜(`9. 15`)를 적습니다 |
| 같은 탭의 `더 보기` | 눌러 두 칸(`8. 26` · `8. 25`)이 이어 붙어 22칸이 되고, 마지막 장이라 버튼이 사라졌습니다 |
| 관심없음 항목 | 관심없음 처리한 9001도 격자에 남습니다(계약 처리 규칙). 화면에 표시는 없습니다 |
| 빈 목록 | 세트를 모두 지우면 `아직 추천받은 기록이 없어요` |
| `?tab=recommendations` | 주소로 바로 이 탭을 열 수 있습니다(업무 -495) |

`더 보기`가 **직전 응답의 `nextCursor`를 그대로** 싣는 것, 다음 장 실패가 격자를 지우지
않는 것, 나머지 두 탭에는 버튼이 없는 것은 `MyDashboardPage.test.tsx`가 고정합니다.
조회 실패 화면은 같은 파일의 기존 시험(`빈 목록과 조회 실패를 구분한다`)이 잡습니다.

## 5. 확인하지 못한 것

- **실제 추천 흐름으로 쌓인 이력은 못 봤습니다.** API-045 세트 생성이 없어 이력을 직접
  넣었습니다. 세트 생성이 들어오면 `generatedAt` · `type` 구성과 세트당 3편(TASTE 2 +
  DISCOVERY 1)이 격자에서 어떻게 보이는지 다시 봐야 합니다
- **파티 추천 세트는 볼 수 없습니다.** API-048 구현이 개인 세트(`user_id`)만 조회합니다
  (6장)
- **배포 환경 확인은 하지 않았습니다.** 로컬 프록시와 Nginx 경로 구조가 같다는 것에
  기대고 있습니다
- 한 사용자 계정으로만 확인했습니다. 남의 이력이 섞이지 않는 것은 백엔드 계약
  테스트(T1)가 고정합니다

## 6. 계약과 구현의 차이

- **`파티 추천`은 계약에만 있습니다.** API-048 처리 규칙은 개인 · 파티를 세트의
  `user_id` · `party_id`로 구분한다고 적지만, 구현은 `WHERE s.user_id = :userId`라
  파티 세트를 아예 제외합니다(백엔드 계약 테스트 T1이 그렇게 고정). 화면 문구를 지우지
  않은 것은 계약이 `RecommendationType`에 `PARTY`를 그대로 두고 있기 때문입니다 —
  **계약과 구현 중 어느 쪽을 고칠지는 S15P21E106-501에서 정합니다**
- `reason`은 백엔드가 저장된 JSON을 그대로 내려줍니다(`JsonNode`). 계약 예시는
  `{ "summary": ... }`이고 화면은 이유를 그리지 않아 이번 범위에서는 문제가 되지
  않았습니다. 응답 모양은 S15P21E106-502에서 확정합니다
