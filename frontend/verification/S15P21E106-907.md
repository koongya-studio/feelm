# S15P21E106-907 로컬 캡처 검증 (2026-09-25)

## 조건

- Windows 로컬 Vite 개발 서버, Chromium 기반 Codex 인앱 브라우저
- 실제 `ReportFourCut` 컴포넌트와 `captureReportImage` 사용
- 같은 출처의 저장소 캐릭터 WebP와 TMDb 문서의 외부 이미지 URL을 각각 01~03 사진에 배치
- 초기 브라우저 검증용 임시 페이지는 제거. iPhone 재현용 격리 DB와 샘플 사진은 로컬에 유지

## 결과

| 사진 출처 | 화면 | 1080 × 3268 PNG |
| --- | --- | --- |
| 같은 출처 WebP | 네 칸 모두 보임 | 네 칸 모두 포함됨. 1,668,468바이트 PNG를 화면에서 확인 |
| `image.tmdb.org` 외부 이미지 | 네 칸 모두 보임 | 캡처용 `fetch`가 `Failed to fetch`로 실패. PNG 생성 중단 |

같은 출처 사진의 최초 구현은 화면 밖 복제본을 캡처해 검은 PNG를 만들었다. 실제 브라우저에서
확인한 뒤 원본 DOM의 사진 주소를 일시적으로 데이터 URL로 바꿔 캡처하고 복원하도록 수정했다.

외부 사진은 `<img>`로 표시되더라도 브라우저 스크립트가 파일 내용을 읽을 수 없다. 현재
수정은 글자만 있는 파일을 성공으로 저장·공유하지 않도록 막는다. 사진이 포함된 실제 사용자
리포트 다운로드는 아직 복구되지 않았다. 외부 사진의 PNG 포함 권한과 같은 출처로 사진을
제공할 API 계약·서비스 경계에 대한 팀 합의가 필요하다.

## iPhone Safari 재확인

- 격리된 로컬 DB의 테스트 계정과 샘플 리포트를 `172.30.1.22:5177`에서 열었다.
- 외부 TMDb 사진의 같은 출처 복사본을 샘플 리포트에 연결했다.
- iPhone Safari에서 저장을 눌러 PNG가 다운로드되고 네 칸 모두 사진이 포함된 것을 사용자와 확인했다.
- Safari는 다운로드 시 빈 탭을 추가로 열었지만 파일은 정상 저장됐다.
- 캡처 중 무한 대기를 막기 위해 프로필 조회 5초, 저장 전체 75초의 제한과 단계별 진행 문구를 추가했다.
- iOS에서는 캡처 시 동적 서브셋 웹폰트 재삽입을 생략한다. 이 환경에서 저장 성공을 확인했다.

## 간헐적 재저장 실패 조사

- 이후 Safari에서 `Load failed`가 다시 발생했다. 캡처의 SVG 로딩 실패는 한 번 재시도하도록 했다.
- 단계별 상태를 확인해 재저장 실패가 `upload: Load failed`임을 확인했다.
- 기존 이미지가 있는 경우 Backend가 업로드 본문을 읽기 전에 응답하던 흐름을 수정했다.
  본문을 8KiB씩 끝까지 읽고 버리므로 메모리에 전체 PNG를 올리거나 기존 파일을 덮어쓰지 않는다.
- 로컬 서버에서 기존 2.3MB PNG 재업로드가 같은 `imageId`로 성공했다.
- `ReportImageApiContractTest`, 프런트 캡처 테스트 11개, 타입 검사와 정적 검사가 통과했다.
- 수정한 로컬 서버에서 iPhone Safari의 저장 버튼을 두 번 연속 눌렀을 때 모두 사진이
  포함된 PNG가 다운로드되는 것을 사용자와 확인했다.

이 검증은 같은 출처로 제공한 샘플 사진에 한정된다. 외부 TMDb URL을 그대로 받은 실제
리포트의 저장과 Safari 공유하기는 아직 검증되지 않았다.

## 저장 이미지의 뒤집기 표시

- 화면에서 카드를 뒤집는 버튼은 그대로 사용하고, PNG 캡처에서는 해당 버튼을 제외했다.
- 캡처 필터 단위 테스트와 타입 검사, 정적 검사가 통과했다.
- iPhone 홈 화면 웹앱의 파일 저장 방식은 변경하지 않았다.
- 새 샘플 리포트 `3`에서 PNG를 생성해 서버 저장 파일을 직접 확인했다. 네 칸의
  사진은 포함됐고 뒤집기 표시는 없었다. 기존 리포트 `2`는 API-061의 이미지
  재사용 계약에 따라 먼저 저장된 PNG가 계속 내려온다.
