# 알림 설정·차단 연동 검증 기록

2026-09-16, 로컬 백엔드를 띄우고 실제 응답으로 화면을 확인한 결과입니다. 대상은 7.8-C
알림 설정과 7.8-D · 7.2-B 차단(S15P21E106-394, API-017 · API-018 · API-020 ~ API-022)입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 확인하지 못한
것은 5장에 있습니다.

취향 필름·팝콘은 [S15P21E106-392.md](./S15P21E106-392.md), 계정 부가 기능은
[S15P21E106-391.md](./S15P21E106-391.md)에 있습니다.

## 1. 왜 남기는가

이 연동에는 자동 테스트가 잡지 못하는 자리가 둘 있습니다.

첫째, **7.8-C는 화면의 토글 다섯 중 셋만 서버로 갑니다.** 계약에 없는 두 토글이 섞여
나가면 백엔드는 모르는 키를 받고, 반대로 세 키 중 하나가 빠지면 `400`입니다. 실제 요청
본문을 눈으로 봐야 확인되는 것입니다.

둘째, **7.2-B는 프로필이 목업인데 차단만 실제 API입니다.** 화면이 넘기는 `userId`가
서버에 있는 번호인지는 화면 코드가 알 수 없습니다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | `local` 프로파일, 8081, **mock 인증 없이 실제 로그인** |
| DB · Redis | `infra/compose`의 로컬 PostgreSQL · Redis |
| 프론트 | Vite dev 서버 5180 (`/api` → `localhost:8081`) |
| 계정 | 가입 API로 만든 `qa394@example.com`(사용자 16). DB에서 `ACTIVE`로 바꿔 인증 메일을 건너뛰었습니다 |
| 데이터 | 차단 대상으로 **목업 프로필과 같은 번호(2048)의 사용자**를 직접 넣었습니다. 확인 뒤 지웠습니다 |

`local` 프로파일의 `CORS_ALLOWED_ORIGINS` 기본값은 `http://localhost:5173`입니다. 다른
포트에서 dev 서버를 띄우면 dev proxy가 Origin을 그대로 넘기므로 `PUT` · `POST`가
`403 Invalid CORS request`가 됩니다. 5173이 아닌 포트를 쓸 때는 백엔드의
`feelm.auth.allowed-origins`에 그 포트를 넣어야 합니다.

## 3. 확인한 것

### 3.1 계약 응답 (curl)

| 호출 | 응답 |
| --- | --- |
| `GET /users/me/notification-settings` | `200` `{"RATING":true,"RECOMMENDATION":true,"MARKETING":false}` |
| `PUT` 세 키 | `200`, 보낸 값 그대로 |
| `PUT` 키 누락 | `400 VALIDATION_FAILED` |
| `POST /users/{id}/block` | `201` `{"blockedUserId":…,"blockedAt":…}` |
| 같은 대상 다시 | `409 ALREADY_BLOCKED` |
| 자기 자신 | `400 CANNOT_BLOCK_SELF` |
| 없는 사용자 · 미인증 계정 | `404 RESOURCE_NOT_FOUND` |
| `DELETE /users/{id}/block` | `204`. 차단 관계가 없어도 `204` |
| `GET /users/me/blocks?size=50` | `200` `{"items":[…],"nextCursor":null,"hasNext":false}` |
| `size=51` | `400 VALIDATION_FAILED` |

### 3.2 7.8-C 알림 설정

- 화면이 처음 그리는 값이 DB 행과 같습니다. 계약의 셋은 서버에서 오고, 계약에 없는
  `파티 초대` · `리포트 발급`은 와이어프레임 기본값(둘 다 켬)으로 시작합니다
- **마케팅을 켜고 파티 초대를 끈 뒤 나간 요청은 둘 다** 다음과 같았습니다.

  ```
  PUT /api/v1/users/me/notification-settings
  {"RATING":true,"RECOMMENDATION":true,"MARKETING":true}
  ```

  계약에 없는 두 키는 본문에 없습니다. 파티 초대만 바꿔도 같은 요청이 나갑니다 —
  API-018이 전체 교체이고 멱등이기 때문입니다
- **새로고침 뒤** 마케팅은 켬 그대로였고(DB `marketing_enabled = t`), 파티 초대는 기본값인
  켬으로 돌아왔습니다. 결정한 대로입니다(screen-spec-my.md 8.5)
- 저장이 실패하면 누르기 전 값으로 되돌아가고 `저장하지 못했어요. 잠시 후 다시 시도해
  주세요`가 나옵니다. CORS로 `PUT`이 막힌 상태에서 실제로 확인했습니다
- 조회가 실패하면 `알림 설정을 불러오지 못했어요` + `다시 시도`입니다

### 3.3 7.2-B → 7.8-D 차단

| 단계 | 확인한 것 |
| --- | --- |
| 7.2-B `사용자 차단` | 확인 창에 `함께 있는 파티에서는 나가게 돼요`(API-020 처리 규칙) |
| `차단` | `POST /users/2048/block` → `201`, 7.8-D로 `replace` 이동 |
| 7.8-D | `1명 차단 중`과 그 사람 한 줄 |
| 다시 7.2-B | `프로필을 불러오지 못했어요` — 차단한 사람의 프로필은 감춥니다 |
| `차단 해제` | `DELETE` → `204`, 목록에서 빠지고 `… 님의 차단을 해제했어요` |
| 해제 뒤 7.2-B | 프로필이 다시 보입니다 |

**목록의 닉네임은 서버 값입니다.** 목업 프로필은 `무비버디`인데 7.8-D에는 DB에 넣은
`moviebuddy`가 나옵니다. 프로필이 목업이고 목록이 실제이기 때문이며, API-062가 열리면
사라지는 차이입니다.

## 4. 계약과 다른 것

1. **`400 VALIDATION_FAILED`의 `details.errors[].field`가 자바 필드 이름입니다.**
   본문 키는 `MARKETING`인데 `field`는 `marketing`으로 옵니다. 화면이 아직 `details`를
   쓰지 않아(S15P21E106-454) 지금은 영향이 없습니다
2. **없는 사용자와 미인증 계정의 `404` 문구가 `요청한 리소스를 찾을 수 없습니다.`입니다.**
   7.2-B는 이 문구를 그대로 보여줍니다. 사용자에게는 무엇을 못 찾았는지 분명하지 않습니다

## 5. 확인하지 못한 것

- **배포 환경.** 로컬에서만 확인했습니다
- **7.2-B의 실제 진입 경로.** 지금 7.2-B로 들어오는 곳은 5.8 파티원 카드(목업)뿐이라
  실제로는 서버에 없는 번호가 넘어갑니다. 확인용으로 목업과 같은 번호의 사용자를 DB에
  넣어 대신했습니다. 파티 연동(S15P21E106-393)과 API-062가 열린 뒤 다시 봐야 합니다
- **차단이 파티에 미치는 영향.** 공동 파티 탈퇴 · 초대 무효화는 백엔드에 아직 없습니다
  (API-020 처리 규칙). 확인 창은 그렇게 된다고 안내하지만 실제로 일어나지 않습니다
- **차단 목록 두 번째 페이지.** 51명 이상을 차단한 상태를 만들지 않았습니다. `hasNext`일 때
  `N명 차단 중`을 감추는 것은 자동 테스트로만 확인했습니다
- **7.8-B 공개 범위 · 7.8-A-1 회원 탈퇴.** 목업으로 남습니다(screen-spec-my.md 8.5)

## 6. 정리

확인용으로 넣은 계정 둘(사용자 16 · 2048)과 그 차단 관계는 모두 지웠습니다. 확인 전부터
있던 차단 행 하나는 그대로 두었습니다.
