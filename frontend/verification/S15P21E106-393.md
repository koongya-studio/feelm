# 파티 화면 연동 검증 기록

2026-09-16, 로컬 백엔드를 띄우고 **계정 두 개**로 초대부터 수락·내보내기·나가기·종료까지
직접 돌려 본 결과입니다. 대상은 파티 화면 전체(S15P21E106-393, API-049 ~ API-057 ·
API-069 · API-019)입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 확인하지 못한
것은 5장에 있습니다.

인증 세션과 가입 흐름은 [S15P21E106-376.md](./S15P21E106-376.md)에 있습니다.

## 1. 왜 남기는가

파티는 **두 사람이 있어야 성립하는 유일한 도메인**입니다. 초대를 보낸 쪽과 받은 쪽이
서로 다른 계정이라 한 계정으로는 흐름의 절반도 확인할 수 없고, 자동 테스트는 두 계정을
동시에 세울 수 없어 "보낸 초대가 상대에게 실제로 보이는가"를 고정하지 못합니다.

권한도 그렇습니다. 파티 종료(API-056)와 멤버 강퇴(API-069)는 **파티장만** 부를 수 있는데,
화면을 열어 보는 것만으로는 파티장이 아닌 사람에게 그 버튼이 보이는지 알 수 없습니다.
파티장으로도, 일반 멤버로도 같은 화면을 열어 봐야 드러납니다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | 이 작업 브랜치 소스, `local` 프로파일, `MAIL_MODE=log`, **`AUTH_MOCK_ENABLED=false`** |
| 백엔드 포트 | **8081**. 다른 작업의 백엔드가 8080을 쓰고 있어 비켜 띄웠습니다 |
| DB · Redis | `infra/compose`의 로컬 PostgreSQL · Redis |
| 프론트 | Vite dev 서버 **5174**(5173도 사용 중), `frontend/.env`의 `VITE_API_PROXY_TARGET=http://localhost:8081` |
| 계정 | `partyqa1`(파티장) · `partyqa2`(초대받는 쪽). 가입 후 메일 로그의 링크로 활성화 |

`[!]` **`AUTH_MOCK_ENABLED`를 반드시 꺼야 합니다.** 켜 두면 토큰 없는 요청에 고정 사용자
하나가 주입되어(`MockAuthenticationFilter`) 로그인하지 않아도 회원 API가 200을 줍니다.
두 계정을 가르는 것이 이 검증의 전부이므로 그 상태로는 아무것도 확인할 수 없습니다.

`[!]` 5174에서 띄우려면 `CORS_ALLOWED_ORIGINS`에 그 주소가 있어야 합니다. dev 프록시의
`changeOrigin`은 Host만 바꾸고 Origin은 그대로 보냅니다(391 기록과 같은 이유).

## 3. 계약 응답으로 확인한 것

두 계정의 Access Token으로 직접 호출한 결과입니다.

### 초대 보내기까지

| 요청 | 응답 |
| --- | --- |
| API-019 `GET /users/search?nickname=partyqa` | `200` · `{"userId":15,"nickname":"partyqa2","visibility":"PRIVATE"}` |
| API-019 `nickname=p` (한 글자) | `400 VALIDATION_FAILED` |
| API-049 `POST /parties` | `201` · `owner` · `members[].joinedAt` · `maxMembers: 4` |
| API-051 `POST /parties/{id}/invitations` | `201 PENDING` |
| API-051 같은 사람에게 다시 | `409 INVITATION_PENDING` |
| API-050 `GET /parties` (초대한 쪽) | `pendingInvitations[]`에 대기 초대가 들어옵니다 |
| API-052 `GET /parties/invitations` (초대받은 쪽) | `memberCount: 1` — **나를 세지 않은 수**입니다 |

- **`PRIVATE` 사용자가 그대로 나옵니다.** 가입 기본값이 `PRIVATE`라 빼면 닉네임 초대가
  사실상 막힙니다(API-019 처리 규칙). 화면은 `비공개 프로필` 표시만 덧붙입니다
- 검색어 길이를 화면이 먼저 보는 근거가 `400`입니다. 한 글자씩 칠 때마다 요청이 나가면
  매번 거절당합니다(`api/users.ts` `isSearchableNickname`)

### 수락·거절과 파티 상태

| 요청 | 응답 |
| --- | --- |
| API-053 수락 | `200` · **파티 전체**(API-049와 같은 본문). 멤버 2명 |
| API-053 같은 초대 재수락 | `409 INVITATION_NOT_PENDING` |
| API-052 수락 뒤 대기 목록 | 빈 `items` |
| API-055 나가기(멤버) | `200` · `{"status":"ACTIVE","ownerId":14,...}` |
| API-056 종료(파티장) | `200` · `status: CLOSED` · `closedReason: OWNER_CLOSED` |
| API-056 종료된 파티 재종료 | `409 PARTY_CLOSED` |
| API-056 파티장이 아닌 사람 | `403 FORBIDDEN` |
| API-069 강퇴(파티장) | `200` · 대상이 목록·팝콘에서 빠집니다 |
| API-069 일반 멤버가 호출 | `403 FORBIDDEN` |
| API-069 자기 자신을 대상으로 | `400 VALIDATION_FAILED` |
| 강퇴당한 사람의 API-057 | `404 RESOURCE_NOT_FOUND` |
| 강퇴 뒤 재초대 → 수락 | 다시 들어옵니다. 강퇴로 차단이 생기지 않습니다 |

- 나가기 · 종료 · 강퇴가 **모두 같은 모양**(`PartyState`)이라 화면이 응답만 봐서는 무엇을
  불렀는지 알 수 없습니다. 그래서 경로와 메서드를 `api/parties.test.ts`가 따로 고정합니다
- 종료된 파티는 기본 목록(`status=ACTIVE`)에서 빠집니다. 5.1이 따라 비는 근거입니다

### 계약과 다른 점

| 항목 | 계약 | 실제 |
| --- | --- | --- |
| API-050 · API-052 응답 | `{ items }` | `{ items, nextCursor, hasNext }` 커서 페이지 |
| API-057 `flavors[]` | `8개 맛을 항상 모두 포함` | **빈 배열** |
| API-058 파티 추천 | 1차 MVP | **`404`. 구현되지 않았습니다** |

- 커서 페이지는 화면에 해가 없어 `api/parties.ts`에서 `items`만 벗겨 씁니다. 활성 파티는
  사용자당 10개가 상한이라(API-049) 목록은 한 장에 다 들어옵니다
- `[!]` **`flavors: []`는 맛 기준정보가 아직 적재되지 않았기 때문입니다.** API-044도 빈
  `items`를 줍니다(S15P21E106-392 기록의 같은 문제, 후속 466 · 467). 그래서 5.8 · 5.9의
  통이 비고 `대표 맛`이 빈칸입니다. **화면을 빈 응답에 맞춰 고치지 않았습니다** — 적재
  뒤 재확인이 맞습니다
- API-058이 없어 5.4 · 5.5는 목업 그대로입니다(`api/parties.ts`)

실제 Chrome에서 5174의 dev 서버로 두 계정을 오가며 확인했습니다.

| # | 누가 | 한 일 | 결과 |
| --- | --- | --- | --- |

| 2 | A | 5.3에서 `partyqa2` 검색 | 결과 한 줄과 `비공개 프로필` 배지 |

호출로 대신하고(쿠키는 실제 흐름과 같습니다) 버튼은 DOM `click()`으로 눌렀습니다.
이벤트 처리는 사용자가 누른 것과 같은 경로이지만, 좌표를 짚어 누른 것은 아닙니다.
같은 문제를 391 기록도 남기고 있습니다.

## 5. 확인하지 못한 것

| 항목 | 이유 |
| --- | --- |
| 5.6 `거절`의 브라우저 동작 | 계약 응답(`409`까지)과 화면 테스트로만 고정돼 있습니다. 브라우저에서는 수락만 밟았습니다 |
| 5.8 · 5.9의 팝콘 그림 | 맛 기준정보와 평가가 없어 통이 빈 채로만 봤습니다. 알이 쌓인 모습은 적재 뒤에 봐야 합니다 |
| `409 PARTY_FULL` · `409 ACTIVE_PARTY_LIMIT_REACHED` | 4명 · 10개를 채우지 않았습니다. 화면은 `ApiError`의 문구를 그대로 보여줍니다 |
| 차단 관계의 `404` | 차단 화면(7.8)을 거치지 않았습니다. 계약대로면 없는 사람처럼 보입니다 |
| 초대 목록 두 번째 장 | `size=50` 한 장만 읽습니다. 받은 초대가 50개를 넘는 상태를 만들지 못했습니다 |
| 8.1 알림 → 5.6 | 알림 목록이 아직 목업이라 가리키는 초대 번호(501)가 서버에 없습니다. 누르면 찾지 못한 상태가 됩니다 |
| 폴링 | 초대 수락이 파티원 전원에게 반영되는 방식이 `폴링 가정`으로만 적혀 있어 구현하지 않았습니다. 화면을 다시 열어야 바뀝니다 |
| 배포 환경 | 로컬만 확인했습니다 |

자동으로 고정한 것은 `src/api/parties.test.ts`(경로 · 메서드 · 본문 · 오류 코드) ·
`src/api/users.test.ts`(API-019) 와 `src/pages/party/*`의 화면 테스트에 있습니다.
