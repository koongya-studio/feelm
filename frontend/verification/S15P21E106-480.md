# 회원 탈퇴 연동 검증 기록

2026-09-17, 7.8-A-1 회원 탈퇴를 로컬 백엔드로 걸어 본 결과입니다.
대상은 API-013(S15P21E106-480)입니다.

## 1. 왜 남기는가

탈퇴는 **되돌릴 수 없고 자동 테스트로 한 번밖에 못 밟는** 흐름입니다. 통합 테스트는
가짜 서버 위에서 돌기 때문에 다음 셋을 볼 수 없습니다.

1. **실제 백엔드가 주는 오류 코드 이름** — 화면이 코드로 문구를 가르는데 이름이 하나만
   달라도 조용히 기본 문구로 떨어집니다
2. **`DELETE`에 본문을 싣는 요청이 그대로 도착하는지** — 개발은 Vite 프록시, 배포는
   Nginx를 거칩니다
3. **탈퇴 뒤 계정 행이 실제로 어떻게 남는지** — 익명화 치환과 재로그인 거절

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | 이미 떠 있던 로컬 백엔드(8080). 이 업무는 백엔드를 고치지 않습니다 |
| DB | 로컬 `feelm-postgres` 컨테이너 |
| 프론트 | Vite dev 서버 **5207**(5173은 다른 worktree가 사용 중), 이 작업 브랜치 소스 |
| 계정 | `withdraw480_1` ~ `withdraw480_8`을 만들어 쓰고 **검증 뒤 모두 지웠습니다** |

**5173이 아닌 포트로 띄우면 CORS에 걸립니다.** 백엔드 `application-local.yml`의
`allowed-origins` 기본값이 `http://localhost:5173` 하나이고, 브라우저는 `GET`이 아닌
요청에 `Origin`을 붙입니다. 그래서 화면은 멀쩡히 뜨는데(같은 출처 `GET`은 `Origin`이
없어 통과) `DELETE`만 **403**으로 막혔습니다. 응답 본문이 비어 있어 화면에는
`요청을 처리하지 못했습니다`가 떠서 코드 문제처럼 보였습니다. 프록시가 나갈 때
`Origin`을 5173으로 바꾸는 임시 설정으로 우회했고, 그 파일은 커밋하지 않았습니다.

## 3. 확인한 것

### 3.1 계약이 정한 네 갈래가 실제로 그대로 온다

`curl`로 로컬 백엔드에 직접 보냈습니다.

| 보낸 것 | 받은 것 |
| --- | --- |
| 올바른 비밀번호 | `204` + `Set-Cookie: refresh_token=; Path=/api/v1/auth; Max-Age=0` |
| 틀린 비밀번호 | `401 INVALID_CREDENTIALS` |
| 빈 비밀번호 | `400 VALIDATION_FAILED` |
| 비밀번호 없는 계정 | `409 PASSWORD_NOT_SET` |

화면이 문구를 가르는 이름(`INVALID_CREDENTIALS` · `PASSWORD_NOT_SET`)이 실제와 같습니다.
`API-014`의 `hasPassword`도 `password_hash`를 지우면 바로 `false`로 바뀝니다.

### 3.2 화면이 틀린 비밀번호를 가른다

5207의 화면에서 체크 → 틀린 비밀번호 → `탈퇴하기` → 확인 창 → `탈퇴`.

- `비밀번호가 올바르지 않아요.`가 떴고 확인 창만 닫혔습니다. 화면에 남아 다시 적을 수 있습니다
- 계정은 그대로 `ACTIVE`였고 세션도 끊기지 않았습니다
- **요청이 두 번 나갑니다.** 공통 클라이언트가 코드를 가리지 않고 401에 재발급을 한 번
  시도하기 때문입니다(`api/client.ts`). 두 번 다 `401 INVALID_CREDENTIALS`이라 결과는
  같지만 Refresh Token이 한 번 회전합니다. API-012 비밀번호 변경도 같은 모양입니다
  (4장)

### 3.3 화면이 탈퇴를 끝낸다

같은 화면에서 올바른 비밀번호로 이었습니다.

- `DELETE /api/v1/users/me` **204** → `POST /api/v1/auth/logout` **204** → `/app/start`(0.1)
- DB에서 그 계정이 `WITHDRAWN`이고 `withdrawn-{id}@feelm.invalid` · `withdrawn-{id}`로
  치환됐으며 `birth_date` · `gender`가 비고 `visibility`가 `PRIVATE`이었습니다
- 같은 이메일 · 비밀번호로 다시 로그인하면 `INVALID_CREDENTIALS`입니다

## 4. 확인하지 못한 것

- **소셜 전용 계정의 안내 화면을 브라우저에서 보지 못했습니다.** 백엔드가 `409`를 주는
  것과(3.1) 화면이 안내를 세우는 것은(`SettingsFlow.test.tsx`) 각각 확인했지만 둘을
  이어 보지는 못했습니다. 쿠키는 포트를 가리지 않아 5173에 떠 있던 다른 worktree의
  세션과 Refresh Token이 겹쳤고, 새로고침할 때마다 다른 계정으로 복구돼 원하는 계정을
  화면에 세울 수 없었습니다. **5173을 비우고 다시 하면 됩니다**
- **배포 Nginx를 거치는 경로는 확인하지 않았습니다.** 본문 있는 `DELETE`가 프록시를
  통과하는 것은 개발 프록시에서만 봤습니다
- **401 재발급 재시도가 탈퇴에서 요청을 두 번 보내는 것**(3.2)은 고치지 않았습니다.
  공통 클라이언트의 거동이라 이 업무 범위를 벗어납니다. 후속 업무 후보입니다
