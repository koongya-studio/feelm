# 소셜 로그인·가입 연동 검증 기록

2026-09-16, 0.2 · 0.3 · 0.6의 소셜 버튼과 콜백 화면을 로컬에서 걸어 본 결과입니다.
대상은 소셜 계열(S15P21E106-499, API-007 · API-008 · API-009)입니다.

**제공자 자격 증명이 아직 없어 실제 구글·네이버·카카오 로그인은 확인하지 못했습니다**
(팀 결정 2026-09-16: 값이 들어오기 전까지 구현만 진행). 그래서 이 기록은 다른 연동
업무의 검증 기록과 성격이 다릅니다 — 화면과 계약 사이는 확인했고, 제공자와 백엔드
사이는 확인하지 못했습니다. 확인하지 못한 것은 5장에 있습니다.

## 1. 왜 남기는가

이 흐름에는 자동 테스트가 고정할 수 없는 자리가 셋 있습니다.

1. **`redirectUri`가 세 곳에서 같아야 합니다** — 각 사 콘솔, 백엔드 허용 목록
   (`OAUTH_ALLOWED_REDIRECT_URIS`), 프론트가 만드는 값. 테스트는 프론트가 만드는 값만
   볼 수 있습니다
2. **client-id가 없는 제공자의 버튼이 잠기는지**는 빌드 변수에 달려 있어 테스트 환경과
   실제 실행이 다릅니다
3. **오류 코드 이름이 실제 백엔드와 같은지** — 화면은 코드로 문구를 가르는데 이름이
   하나만 달라도 조용히 기본 문구로 떨어집니다

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | **이미 떠 있던 로컬 백엔드(8080)**. 이 업무는 백엔드를 고치지 않으므로 새로 띄우지 않고 읽기 요청만 보냈습니다 |
| 프론트 | Vite dev 서버 **5199**(5173이 사용 중), 이 작업 브랜치 소스 |
| 빌드 변수 | `.env.local`에 `VITE_GOOGLE_CLIENT_ID`만 넣어 **한 제공자만 열린 상태**를 만들었습니다. 커밋하지 않습니다 |
| 데이터 | 만들지 않았습니다. 가입을 끝내지 못해 남는 것이 없습니다 |

백엔드에 보낸 것은 전부 **거절당할 요청**입니다(가짜 인가 코드 · 가짜 가입 토큰 · 없는
제공자). 계정이나 기록이 생기지 않습니다.

## 3. 확인한 것

### 3.1 자격 증명이 없는 제공자는 잠긴다

0.6 로그인에서 `VITE_GOOGLE_CLIENT_ID`만 넣은 상태로 확인했습니다.

| 버튼 | 결과 |
| --- | --- |
| 구글 로그인 | 눌린다 |
| 네이버 로그인 | 잠김 |
| 카카오 로그인 | 잠김 |
| `소셜 로그인은 준비 중입니다` | 사라짐(한 곳이라도 열려 있으므로) |

셋 다 비어 있으면 전과 같이 모두 잠기고 안내 문구가 남습니다.

### 3.2 콜백이 요청을 확인하고 백엔드를 부른다

`sessionStorage`에 요청을 넣고 같은 `state`로 콜백 주소를 열었습니다.

- 요청을 소비하고(`feelm.oauth`가 지워짐) API-007을 호출했습니다
- 실패 안내와 `로그인 화면으로`가 그려졌습니다. 주소에 인가 코드가 남은 화면이라
  머무르지 않고 돌아갈 길을 주는 것이 의도입니다
- `state`가 다르면 백엔드를 아예 부르지 않습니다(단위 테스트로도 고정)

### 3.3 0.3-A가 실제 API-016으로 닉네임을 확인한다

콜백이 넘기는 값과 같은 Router state로 0.3-A를 열었습니다.

- 제안 닉네임(`구글사용자`)이 입력 칸에 들어와 있습니다
- `중복 확인`이 실제 백엔드를 불러 `사용할 수 있는 닉네임이에요`를 받았습니다
- 이메일·비밀번호 칸이 없고 종이가 세 줄로 끝납니다

### 3.4 오류 코드 이름을 실제 백엔드와 맞췄다

화면을 거치지 않고 로컬 백엔드에 직접 보내 이름을 확인했습니다.

| 보낸 것 | 응답 | 화면 문구 |
| --- | --- | --- |
| API-007, 허용 목록에 없는 `redirectUri` | `400 VALIDATION_FAILED` | 소셜 로그인 설정이 올바르지 않아요 |
| API-007, 등록되지 않은 제공자(`/apple`) | `400 UNSUPPORTED_PROVIDER` | 지금은 이 제공자로 로그인할 수 없어요 |
| API-008, 가짜 `signupToken` | `401 SIGNUP_TOKEN_INVALID` | 가입 시간이 지났어요. 소셜 로그인부터 다시 해 주세요 |

허용 목록이 비어 있으면 **모든 `redirectUri`가 거절**됩니다(`VALIDATION_FAILED`).
자격 증명을 넣을 때 허용 목록도 함께 넣어야 합니다.

## 4. 자동 테스트로 덮은 것

- `src/utils/oauth.test.ts` — 동의 화면 주소의 값, `redirectUri` 계산과 덮어쓰기,
  `state` 불일치, 요청을 읽는 것과 지우는 것의 분리
- `src/pages/auth/OAuthCallbackPage/OAuthCallbackPage.test.tsx` — 로그인·가입 갈림길,
  가입 토큰 전달, 취소·위조 처리, 오류 코드 안내
- `src/pages/auth/SocialSignupProfilePage/SocialSignupProfilePage.test.tsx` — 계약 필드,

## 5. 확인하지 못한 것

- **실제 제공자 로그인 전체 흐름.** client-id와 허용 목록이 없어 동의 화면부터 갈 수
  없습니다. 값이 들어오면 ① 신규 가입(콜백 → 0.3-A → 0.5), ② 기존 계정 재로그인
  (콜백 → 1.1 또는 2.1), ③ 같은 이메일 계정이 있을 때의 `409 EMAIL_DUPLICATED`를
  순서대로 확인해야 합니다
- **브라우저에서 POST 계열 응답 문구.** 5173이 이미 쓰이고 있어 5199로 띄웠는데, 백엔드
  `allowed-origins`가 5173이라 브라우저에서 나간 POST가 `403 Invalid CORS request`로
  막혔습니다. 그래서 4장의 오류 문구는 직접 호출로만 확인했습니다. 5173이 비면 화면에서
  다시 봐야 합니다
- **각 사 로고 사용 가능 여부.** 브랜드 가이드 확인이 필요합니다(screen-spec-auth.md 5장)
- **소셜 계정 연결(API-009).** 7.8-A에 진입 자리가 없어 전송 계층만 두었습니다
