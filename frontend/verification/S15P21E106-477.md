# OTT 클릭과 감상 확인 연동 검증 기록

2026-09-16, 로컬 백엔드를 띄우고 2.4 → 2.4-A → 2.5 → 7.7을 실제 응답으로 걸어 본
결과입니다. 대상은 감상 기록 계열(S15P21E106-477, API-033 · API-034 · API-035)입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 확인하지 못한
것은 5장에 있습니다.

인증 세션과 가입 흐름은 [S15P21E106-376.md](./S15P21E106-376.md)에 있습니다.

## 1. 왜 남기는가

감상 기록은 **상태 기계**입니다. 같은 화면이 `LINK_CLICKED` · `WATCHED_UNRATED` ·
`RATED` · `EXPIRED`에 따라 다르게 동작하고, 그 전이를 정하는 것은 이제 서버입니다
(API-033 재클릭 규칙, API-035 `409`, API-034 만료 반영). 자동 테스트는 응답을 흉내 낼
뿐 **재클릭이 정말 새 기록을 만들지 않는지**, **이미 답한 기록이 정말 `409`인지**를
고정하지 못합니다.

계약에 **단건 조회가 없다는 것**도 한 번 돌려 봐야 드러납니다. 2.4-A는 URL의 번호로 기록
하나를 여는 화면인데, 목록을 훑어 찾습니다. 찾지 못한 기록과 이미 답한 기록을 화면이
어떻게 가르는지가 이 업무에서 새로 생긴 자리입니다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 백엔드 | 이 작업 브랜치 소스, `local` 프로파일, `MAIL_MODE=log`, `AUTH_MOCK_ENABLED=true` |
| 백엔드 포트 | **8082**. 8080 · 8081을 다른 작업이 쓰고 있어 비켜 띄웠습니다 |
| DB | **별도 데이터베이스 `feelm_477`**. 같은 로컬 PostgreSQL 컨테이너 안에 새로 만들었습니다 |
| Redis | `infra/compose`의 로컬 Redis(공용) |
| 프론트 | Vite dev 서버 **5177**, `VITE_API_PROXY_TARGET=http://localhost:8082` |
| 데이터 | 아래 3장의 임시 시드. 확인 뒤 데이터베이스를 통째로 지웠습니다 |

**DB를 따로 만든 이유**는 같은 컨테이너의 `feelm`을 다른 작업의 백엔드가 쓰고 있었기
때문입니다. 공용 DB에 이 브랜치의 Flyway를 적용하면 그쪽 실행 중인 백엔드까지 영향을
받습니다. 새 데이터베이스는 Flyway가 처음부터 만들었고, 확인이 끝난 뒤
`DROP DATABASE feelm_477`로 흔적을 남기지 않았습니다.

`AUTH_MOCK_ENABLED=true`로 둔 것은 감상 기록 API가 전부 회원 전용이기 때문입니다.
계정을 가르는 확인이 아니라 고정 사용자 하나(`AUTH_MOCK_USER_ID=1`)로 충분합니다.

## 3. 시드 데이터

- 사용자 1명(`id=1`) — 모의 인증이 주입하는 사용자
- 영화 3편 — `검증영화 클릭`(901, 넷플릭스 · 티빙), `검증영화 재클릭`(902, 웨이브),
  `검증영화 OTT없음`(903, 연결 없음)
- 가입 흐름으로 만든 계정 1개(`verify477user@example.com`) — 메일 링크 인증까지 확인

`[!]` **curl로 한글이 든 JSON 본문을 보낼 때는 UTF-8 파일로 만들어 `--data-binary @file`로
보내야 합니다.** Git Bash가 인자를 코드페이지로 넘기면 닉네임이 깨져
`400 VALIDATION_FAILED`가 됩니다. 도구 문제이며 계약 위반이 아닙니다.

## 4. 확인한 것

### 계약 응답으로 확인한 것

| 요청 | 응답 |
| --- | --- |
| API-033 `POST /movies/901/ott-clicks {"ottId":1}` | `201` · `LINK_CLICKED` · `confirmDueAt`=+2일 · `expiresAt`=+7일 |
| API-033 같은 영화 다른 OTT 재클릭 | **`200`** · 같은 `watchRecordId` · 시각 갱신 · 목록의 `ott`가 티빙으로 바뀜 |
| API-033 `WATCHED_UNRATED` 상태에서 재클릭 | **`200`** · 상태·시각 모두 그대로 |
| API-033 `EXPIRED` 뒤 재클릭 | **`201`** · 새 `watchRecordId` |
| API-033 영화에 연결되지 않은 OTT | `404 RESOURCE_NOT_FOUND` |
| API-034 `status=WATCHED_UNRATED&status=RATED` | `200` — 반복 지정이 그대로 걸립니다 |
| API-034 `status[0]=RATED` | **`200`** — 인덱스 표기는 **거절이 아니라 무시**되어 거른 적 없는 전체 목록이 옵니다 |
| API-034 `confirmDue=true` | `200` |
| API-034 `confirmDue=TRUE` | `400 VALIDATION_FAILED` — 정확한 소문자만 받습니다 |
| API-035 `{"watched":true}` | `200` · `WATCHED_UNRATED` · `watchedAt` 있음 |
| API-035 같은 기록 다시 | `409 INVALID_WATCH_STATUS` |
| API-035 `{"watched":false}` | `200` · `EXPIRED` · `watchedAt: null` |
| API-035 없는 기록 | `404 RESOURCE_NOT_FOUND` |

- **`status[0]=` 표기가 400이 아니라 무시된다**는 점이 검색(API-028)과 다릅니다. 화면은
  계약대로 반복 지정을 보내므로 영향이 없지만, 잘못 보낸 클라이언트가 **거른 적 없는
  전체 목록을 받는다**는 뜻이라 후속 후보로 적어 둡니다
- 평가로 만들어진 기록이 `ott: null` · `clickedAt: null`로 오는 것은 스키마
  (`INSERT INTO watch_records(user_id, movie_id, status, rated_at)`)에서 확인했습니다.
  타입을 그 모양(`nullable`)에 맞춘 근거입니다

### 화면에서 확인한 것

| 확인 | 결과 |
| --- | --- |
| 2.4 기록 없음 | 알약이 `넷플릭스에서 바로 보기` + `이동 시 링크 클릭함으로 기록돼요` |
| 2.4 알약 클릭 | 기록이 남고 `/app/watch-records/4/confirm`으로 이동 |
| 2.4-A 상황 문구 | `넷플릭스로 이동했어요 · 방금 전` — 고정 문구가 아니라 실제 `clickedAt` |
| 2.4-A `봤어요` | `/app/movies/901/rate`로 이동 |
| 2.5 감상 정보 줄 | `9월 16일 · 넷플릭스에서 시청` — 방금 만든 기록의 `watchedAt`과 OTT |
| 7.7 목록 | `안 남긴 영화 1` · `검증영화 클릭` · `9. 16 · 넷플릭스에서 시청` |
| 2.4 `LINK_CLICKED` | 알약이 `감상 확인하기`로 바뀌고 그 기록의 2.4-A로 갑니다 |
| 2.4-A 이미 답한 기록(감상함) | `이미 답한 감상이에요` · `검증영화 클릭은 감상한 영화로 남아 있어요` · `평가하러 가기` |
| 2.4-A 이미 답한 기록(만료) | 같은 화면에서 `감상 대기가 끝났어요` · `평가하러 가기` 없음 |
| 2.4-A 없는 기록(`/watch-records/9999/confirm`) | `감상 기록을 찾을 수 없어요` · `홈으로 이동`만 |
| 2.4-A 응답 중 `409` | 화면을 다시 읽어 `이미 답한 감상이에요`로 넘어갑니다 |
| 2.4 클릭 실패(`404`) | `기록을 남기지 못했어요. 잠시 후 다시 눌러 주세요` + **이동하지 않음** |

`409`는 화면을 열어 둔 채 다른 경로로 같은 기록에 답해 만들었고, 클릭 실패는 상세를
띄운 뒤 그 영화의 OTT 연결을 지워 만들었습니다.

- **영화 제목 뒤 조사를 받침에 맞춰 고릅니다.** 처음에는 `검증영화 클릭는`으로 나왔고,
  `utils/korean.ts`에 `topicParticle`을 더해 고쳤습니다. 제목은 서버 값이라 고정 조사를
  쓸 수 없습니다

## 5. 확인하지 못한 것

- **2일 · 7일 경계.** `confirmDue=true` 질의가 `200`인 것까지만 봤고, 확인 시각이 지난
  기록만 걸러 오는지는 시각을 조작해야 해서 만들지 않았습니다. 경계 판정은 백엔드 쪽
  시험이 고정하고 있습니다(`WatchServiceTest`)
- **만료 반영.** 목록 조회가 만료된 `LINK_CLICKED`를 `EXPIRED`로 옮기는 경로는 7일을
  기다려야 해서 확인하지 못했습니다
- **200건이 넘는 감상 기록.** 기록 하나를 찾을 때 목록을 최대 네 장(50 × 4) 훑습니다.
  그보다 오래된 기록은 찾지 못하며, 그 상태에서 2.4-A가 `찾을 수 없어요`가 되는 것은
  만들어 보지 않았습니다. 단건 조회 계약이 생기면 없어질 한계입니다
- **로그인하지 않은 상태의 `401`.** `AUTH_MOCK_ENABLED=true`로 띄워 이 경로를 만들 수
  없었습니다. 자동 테스트가 오류가 그대로 올라오는 것까지 고정합니다
- **배포 환경.** 배포 DB의 영화에 OTT가 연결되어 있는지는 확인하지 않았습니다. 연결이
  없으면 2.4의 알약은 `내 별점 남기기`로 남습니다

## 6. 남은 어긋남

**평가가 아직 목업이라 감상 기록과 어긋납니다**(이 업무의 범위 밖).

- 2.5에서 평가해도 서버 기록은 `WATCHED_UNRATED`에 남아 **7.7에서 빠지지 않습니다.**
  평가 생성(API-036)은 백엔드에 들어와 있고(업무 -474) 연동하면 서버가 같은 트랜잭션에서
  기록을 `RATED`로 옮깁니다
- 목업 알림(8.1 · 8.2)이 가리키는 감상 기록 번호는 서버에 없어 2.4-A가
  `감상 기록을 찾을 수 없어요`가 됩니다. 알림이 실제 API가 되면 사라집니다
- 7.5 추천 기록(API-048 목업)은 감상 상태를 스냅샷 값으로 그립니다. OTT 링크만 누른
  영화가 그 목록에서는 이전 상태로 보입니다
