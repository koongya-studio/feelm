# 검색 · 필름 화면 자동 테스트 간헐 실패 확인 기록

2026-09-22, 전체 테스트 실행(`npm run test:run`)에서 무작위로 한두 건씩 깨지던 시험의 원인을
찾아 고친 기록입니다.

**결론부터**: 원인은 둘이고 서로 다릅니다. 하나는 **주소 갱신이 낮은 우선순위로 미뤄지는 것**,
다른 하나는 **화면이 아직 붙어 있는데 전역 스텁을 먼저 거두는 것**입니다. 둘 다 화면 코드가
아니라 시험 환경의 문제이며, 시험을 건너뛰거나 단정문을 약하게 바꾸지 않고 고쳤습니다.

## 1. 어떻게 재현했나

전체 실행을 잇따라 세 번 돌려 세 번 모두 깨뜨렸습니다. 기계가 바쁠수록 잘 깨지며, 깨진
파일만 단독으로 돌리면 늘 통과합니다.

| 실행 | 깨진 시험 |
| --- | --- |
| 1회 | `FilmPage` — 다음 장 칸이 릴 안에서 보일 즈음 다음 장을 부르고… |
| 2회 | `SearchPage` — 두 글자부터 찾는다고 알리고 주소에 검색어를 남기지 않는다 |
| 3회 | 위 둘 모두 |

CPU를 일부러 점유한 상태에서는 `FilmPage`의 다른 시험(끝의 다음 장 칸으로 나머지 프레임을
이어 받아…)도 같은 방식으로 깨졌습니다.

## 2. 검색 화면 — 주소가 결과보다 늦게 온다

```
type('괴물');
await resultsHeading(1);                      // 결과 머리줄을 기다린다
expect(location()).toBe('/search?q=%EA%B4%B4%EB%AC%BC');   // 여기서 '/search'가 잡혔다
```

4.1 검색은 조건을 주소에 적고(`setParams(..., { replace: true })`) 곧바로 첫 장을 받습니다.
주소를 먼저 적으므로 결과보다 늦을 수 없어 보이지만, **`MemoryRouter`는 주소 상태를
`React.startTransition` 안에서 바꿉니다**(react-router 8 `components.js`).

```js
let setState = React.useCallback((newState) => {
  if (useTransitions === false) setStateImpl(newState);
  else React.startTransition(() => setStateImpl(newState));
}, [useTransitions]);
```

전환은 낮은 우선순위라 뒤로 미룰 수 있습니다. 반면 검색 결과(`setSearch`)는 보통 갱신입니다.
그래서 **결과 머리줄이 먼저 커밋되고 주소는 아직 이전 값**인 순간이 생기고, 기계가 바쁠수록
그 틈이 벌어져 바로 뒤의 단정문에 잡힙니다.

**고친 방법**: 시험용 라우터에서 전환을 끕니다(`test/render.tsx`의 `useTransitions={false}`).
화면이 하는 일은 그대로이고 주소 갱신의 커밋 시점만 결과와 같아집니다. 기다리는 단정문으로
감싸 덮는 대신 어긋남 자체를 없앴습니다.

## 3. 필름 화면 — 스텁을 거둔 뒤에 화면이 다시 그려진다

```
ReferenceError: IntersectionObserver is not defined
 ❯ src/pages/film/FilmPage/index.tsx:235   const observer = new IntersectionObserver(
```

3.1의 자동 이어 받기 시험은 `IntersectionObserver`를 전역에 심고
(`vi.stubGlobal`) 모듈을 다시 불러 화면이 그것을 쓰게 합니다. 끝난 뒤에는
`vi.unstubAllGlobals()`로 거둡니다.

문제는 **거두는 시점**입니다. vitest는 `afterEach`를 나중에 등록한 것부터 돌리므로
(기본값 `sequence.hooks: 'stack'`), 이 파일의 `afterEach`가 `test/setup.ts`의 `cleanup()`보다
**먼저** 돕니다. 즉 화면이 아직 붙어 있는 채로 전역이 사라집니다. 그 틈에 앞서 보낸 요청이
돌아와 화면이 다시 그려지면, 관찰자를 만드는 자리에서 터집니다. 기계가 바쁠수록 응답이 그
틈에 도착할 확률이 높아집니다.

**고친 방법**: 스텁을 거두기 전에 `cleanup()`으로 화면을 먼저 걷습니다.

## 4. 화면 코드는 바꾸지 않았다

두 원인 모두 실제 브라우저에서는 일어나지 않습니다. 주소 전환은 사용자가 기다리는 대상이
아니고, `IntersectionObserver`는 중간에 사라지지 않습니다. 그래서 바꾼 것은 시험 쪽 두
파일뿐입니다.

| 파일 | 바꾼 것 |
| --- | --- |
| `src/test/render.tsx` | `MemoryRouter`에 `useTransitions={false}` |
| `src/pages/film/FilmPage/FilmPage.test.tsx` | 스텁을 거두기 전에 `cleanup()` |

## 6. 확인하지 못한 것과 남은 위험

- **간헐 실패는 "없음"을 증명할 수 없습니다.** 일곱 번 연속 통과는 확률을 크게 낮춘 것이지
  재발하지 않는다는 보장이 아닙니다. 다시 나오면 이 기록의 두 유형부터 확인합니다.
- **도우미를 쓰지 않는 시험은 이번 수정의 보호를 받지 않습니다.** `renderWithRouter` ·
  `withRouter`를 거치지 않고 `MemoryRouter`를 직접 만드는 시험 파일에는 `useTransitions={false}`가
  걸리지 않습니다. `SearchBackFlow.test.tsx:218`은 결과를 기다린 직후 주소를 바로 읽어 2장과 같은
  모양입니다. 깨지면 그 단정문을 `waitFor`로 감싸거나 도우미로 옮깁니다.
- **전역 스텁을 걷는 다른 시험 파일은 손대지 않았습니다.** `SignupPaper` · `SettingsFlow` ·
  `BlockedUsersPage`도 `vi.unstubAllGlobals()`를 쓰지만 거두는 것이 `fetch` · `innerHeight`라
  없어져도 생성자처럼 즉시 터지지 않습니다. 같은 증상이 나오면 같은 방법으로 고칩니다.
- **CI에서는 확인하지 않았습니다.** 로컬 실행만으로 판단했습니다.
