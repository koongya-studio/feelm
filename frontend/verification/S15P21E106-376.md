# 인증 세션과 가입 흐름 검증 기록

2026-09-11, 실제 백엔드를 띄우고 브라우저에서 확인한 결과입니다. 대상은 공통 HTTP 기반과
인증 세션(S15P21E106-364), 재발급 실패 판정 수정(S15P21E106-373), 가입과 이메일 인증
연동(S15P21E106-366)입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 배포와 이후 연동에
남은 것은 6장에 있습니다.

백엔드가 단독으로 확인한 로그인 제한·메일 제한·차단은
[backend/verification/S15P21E106-375.md](../../backend/verification/S15P21E106-375.md)에
있습니다.

## 1. 왜 남기는가

세션 거동은 자동 테스트로 고정한 부분이 있지만, 실제로 브라우저에서 그렇게 도는지는 따로
봐야 합니다. 그리고 그 확인이 어렵습니다.

| 확인할 것 | 자동화·재현이 어려운 이유 |
| --- | --- |
| 토큰 만료 후 자동 재발급 | Access Token 수명이 30분이라 낮춰 띄우지 않으면 만료를 기다려야 합니다 |
| 동시 401에 재발급 1회 | 단위 테스트로 고정했지만 실제 브라우저에서 요청이 겹치는지는 네트워크 기록을 봐야 합니다 |
| 다중 탭 | 창을 두 개 띄우고 한쪽이 회전시킨 뒤 다른 쪽을 움직여야 합니다 |
| 백엔드 장애 회복 | 백엔드를 내렸다 올려야 하고, 새로고침하면 증상이 사라져 화면 안에서 움직여야 합니다 |
| 가입 흐름 | 인증 메일 링크를 백엔드 로그에서 꺼내야 이어집니다 |

특히 장애 회복은 **새로고침하면 증상이 사라집니다.** 앱이 다시 뜨면서 세션을 처음부터
복구하기 때문입니다. 화면 안에서 이동해야 드러나며, 그래서 처음 만들 때 놓쳤습니다
(S15P21E106-373).

결함과 후속 업무는 Jira에 있으므로 여기에 다시 적지 않고 가리키기만 합니다.

## 2. 지금 실제 API를 쓰는 곳

목업과 실연동이 섞여 있습니다. 어디가 실제인지 모르면 무엇을 확인한 것인지도 알 수 없습니다.

| 화면·기능 | 상태 |
| --- | --- |
| 로그인·로그아웃, 세션 복구 | 실제 (API-004·005·006) |
| 가입, 이메일 인증, 인증 메일 재발송 | 실제 (API-001·002·003) |
| 홈 인사말의 프로필 | 실제 (API-014) |
| 영화·검색·감상·온보딩·OTT·추천·파티 | 목업 (`src/api/mockTransport.ts`) |
| 소셜 로그인 | 미연동. 버튼을 잠가 두었습니다 |

목업 도메인은 URL 질의로 지연과 실패를 넣을 수 있습니다(`?mockDelay=`·`?mockError=`).
실연동 도메인에는 적용되지 않습니다.

## 3. 사전 준비

백엔드와 데이터 저장소는
[backend/verification/S15P21E106-375.md](../../backend/verification/S15P21E106-375.md)
2장을 따릅니다. `MAIL_MODE=log`여야 인증 링크가 로그에 남습니다.

프론트엔드는 `frontend`에서 띄웁니다. 개발 서버가 `/api`를 백엔드로 넘기므로 같은 출처가
됩니다.

```bash
npm run dev            # http://localhost:5173/app/
```

토큰 만료를 확인할 때만 백엔드를 짧은 수명으로 띄웁니다. 40초면 화면을 움직이기에 충분하고
기다리기에도 짧습니다.

```bash
./gradlew bootRun --args='--spring.profiles.active=local --feelm.jwt.access-token-ttl=40s'
```

확인은 브라우저 개발자도구 네트워크 탭에서 `/api/v1`을 걸러 봅니다. **개발 환경은
StrictMode라 효과가 두 번 실행되므로 같은 요청이 두 번 보이는 것이 정상입니다.** 중요한 것은
재발급이 몇 번 나가는지입니다.

## 4. 확인한 것

### 4.1 Access Token 보관

`localStorage`·`sessionStorage`·`document.cookie`·`indexedDB`를 `src/` 전체에서 찾으면
주석에만 나오고 실제 호출은 없습니다. Access Token은 모듈 메모리에만 있고 새로고침하면
사라지며, 복구는 httpOnly `refresh_token` 쿠키가 맡습니다(ADR-0009).

```bash
grep -rn "localStorage\|sessionStorage\|document.cookie\|indexedDB" src --include=*.ts --include=*.tsx
```

### 4.2 세션 복구와 자동 재발급

| 시나리오 | 절차 | 결과 |
| --- | --- | --- |
| 새로고침 복구 | 로그인 후 홈에서 새로고침 | `users/me` 401 → `token/refresh` 200 → `users/me` 200. 인사말에 실제 닉네임이 뜹니다 |
| 만료 후 자동 재발급 | 수명 40초로 띄우고 로그인한 뒤, 40초를 넘겨 화면 안에서 이동 | `users/me` 401 두 건 → **재발급 1회** → 재시도 200 두 건. 화면은 깜빡임 없이 유지됩니다 |
| 동시 401에 재발급 공유 | 위와 같음 | 401이 두 건인데 `token/refresh`는 한 번만 나갑니다 |
| 비로그인 | 로그인하지 않고 홈 진입 | `token/refresh` 401 한 번. 이후 반복하지 않습니다 |

두 번째 줄은 새로고침이 아니라 **화면 안에서** 이동해야 합니다. 새로고침하면 앱이 다시 뜨며
세션을 처음부터 복구해 만료 경로를 타지 않습니다.

### 4.3 다중 탭

같은 주소로 탭을 두 개 열고 양쪽에서 로그인 상태를 만든 뒤, 한쪽에서 재발급이 일어나게
두었습니다. 다른 탭도 정상 동작했습니다.

Refresh Token이 쿠키라 **탭이 공유합니다.** 한쪽의 회전이 다른 쪽을 무효화하지 않고, 뒤늦게
움직인 탭은 갱신된 쿠키로 재발급받습니다.

### 4.4 백엔드 장애와 회복

S15P21E106-373이 고친 부분입니다. 수정 전후를 같은 절차로 확인했습니다.

| 단계 | 절차 | 수정 전 | 수정 후 |
| --- | --- | --- | --- |
| 장애 중 | 백엔드를 내리고 화면 안에서 이동 | `users/me` 502, `token/refresh` 503 | `users/me` 502만. 세션을 건드리지 않습니다 |
| 회복 후 | 백엔드를 올리고 **새로고침 없이** 화면 안에서 이동 | `users/me` 401 두 건뿐. **재발급 시도가 없습니다** | 401 두 건 → `token/refresh` 200 → 200 두 건 |

수정 전에는 재발급이 5xx를 받으면 세션을 끝냈고, 그러면 백엔드가 살아나도 재발급을 다시
시도하지 않았습니다. 배포 중 재시작 한 번이면 그때 앱을 열어 둔 모두가 로그아웃된 것처럼
보입니다.

**새로고침하면 증상이 사라집니다.** 반드시 화면 안에서 이동해 확인합니다.

### 4.5 가입부터 로그인까지

S15P21E106-366 기준입니다. 인증 메일은 실제로 오지 않으므로 백엔드 로그에서 링크를 꺼냅니다.

```
가입            POST /auth/signup        201  → 0.5로 이동, 인증 메일 안내 표시
미인증 로그인   POST /auth/login         403  → "이메일 인증을 마쳐야 로그인할 수 있습니다"
                                               + 인증 메일 다시 보내기
메일 링크 인증  POST /auth/email/verify  200  → "이메일 인증이 완료됐어요" (호출 1회)
로그인          POST /auth/login         200  → 취향 초기 설정으로 이동
```

링크는 백엔드 로그의 `로컬 확인용 링크`에서 꺼내 주소창에 붙여 넣습니다.

인증 호출이 한 번인 것이 중요합니다. 토큰이 1회용이라 StrictMode의 두 번째 실행이 첫 토큰을
태우면 정상 링크가 항상 실패합니다.

로그인 실패 분기도 함께 봤습니다. 틀린 비밀번호는 `401`로 "이메일 또는 비밀번호가 올바르지
않습니다"가 뜨고 재발급을 시도하지 않습니다. 공개 API의 401은 재발급 대상이 아닙니다.

## 5. 발견한 것

- **S15P21E106-373** 재발급이 5xx를 받으면 세션이 끝나 백엔드 회복 후에도 돌아오지 못했습니다.
  4.4에 수정 전후가 있습니다
- **S15P21E106-374** 백엔드 장애 중 홈 인사말이 오류 표시 없이 사라집니다. 세션 복구와 별개로
  화면의 실패 표시가 없습니다
- 이미 인증한 링크를 다시 누르면 `409 ALREADY_VERIFIED`가 아니라
  `400 VERIFICATION_TOKEN_INVALID`가 옵니다. 토큰이 사용 즉시 무효화되기 때문이며, 사용자는
  "이미 인증했는데 링크가 올바르지 않다"는 안내를 봅니다. 화면은 계약대로 구현했고 계약 쪽에서
  다룰 일입니다

## 6. 남은 검증

- **배포 환경의 세션과 쿠키.** 로컬은 개발 서버 프록시로 같은 출처를 만들지만 배포는 Nginx가
  같은 일을 합니다. 쿠키의 `Secure`가 로컬에서는 localhost 예외로 통과하므로 실제 HTTPS에서
  다시 봐야 합니다
- **실제 메일 수신함에서 링크 클릭.** 로컬은 로그에서 꺼내 주소창에 붙여 넣으므로 메일
  클라이언트가 링크를 어떻게 다루는지는 확인하지 못했습니다
- **만료 토큰 경로.** 인증 토큰 수명이 24시간이라 브라우저에서 확인하지 못했고 단위 테스트로만
  덮었습니다
- **소셜 로그인.** 미연동이며 버튼을 잠가 두었습니다
- **목업으로 남은 도메인.** 연동할 때마다 이 문서에 시나리오를 더합니다
