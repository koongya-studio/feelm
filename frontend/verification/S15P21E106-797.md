# 전체 실행 간헐 실패 재발 확인 기록

2026-09-22, `npm run test:run`(전체 실행)이 기계가 바쁠 때 무작위로 한둘씩 깨지던 것을 다시
찾아 고친 기록입니다. -789가 고친 두 유형과는 다릅니다.

**결론부터**: 원인은 시험마다 다릅니다. Jira가 적은 둘에 하나가 더 나와 셋입니다.

| 깨진 시험 | 원인 | 절 |
| --- | --- | --- |
| 3.1 필름 — 다음 장 계열 | **기다리는 예산이 모자랐다.** 갱신은 끝내 도착하지만 기본 예산(기다림 1초 · 시험 5초)을 넘겼다 | 2 |
| 7.2 프로필 편집 — 미리보기 · 7.1로 돌아가기 | **이동이 전환에 실려 제때 그려지지 않았다.** 데이터 라우터가 주소를 `startTransition`으로 바꾸는데, 시간을 쪼개 그리는 전환은 기계가 바쁘면 5초를 넘도록 커밋되지 않는다 | 3 |
| 4.2 검색 — 보조 패널 (앞의 둘을 고친 뒤 드러남) | **서로 다른 응답 사이를 잡았다.** 제목은 검색 결과가 주고 줄거리 · 유사한 작품은 다른 요청이 채우는데, 제목만 기다리고 나머지를 바로 읽었다 | 6 |

셋 다 시험 환경의 문제이고 화면 코드는 한 줄도 바꾸지 않았습니다. 시험을 건너뛰거나 단정문을
약하게 바꾸지도 않았습니다.

## 1. 어떻게 재현했나

기준은 `origin/develop`(`07ca0dea`, -787 병합 직후)이고 별도 worktree에서 돌렸습니다. CPU를
일부러 점유한 채 전체 실행을 반복했습니다. 기계는 22코어입니다.

| 대상 | 부하 | 실행 | 결과 |
| --- | --- | --- | --- |
| 전체 실행 | 없음 | 3 | 모두 통과 |
| 전체 실행 | CPU 12개 점유 | 7 | **5회 실패** |
| 전체 실행 | CPU 24개 점유 | 3 | **2회 실패** |
| 전체 실행 (일꾼 32 · 파일 순서 섞기) | CPU 16개 점유 | 8 | **6회 실패** |
| `FilmPage.test.tsx`만 | CPU 12개 점유 | 1 | 통과 |
| `ProfileEditPage.test.tsx`만 | CPU 24개 점유 | 8 | 모두 통과 |

**파일 하나만 돌리면 깨지지 않습니다.** 전체 실행은 100개가 넘는 파일을 일꾼에 나눠 동시에
돌리므로, 바깥 부하가 더해지면 일꾼 하나가 받는 몫이 크게 줄어듭니다.

부하를 준 18회에서 깨진 것은 다섯 종류였고, 3.1 필름이 대부분이었습니다.

| 깨진 시험 | 횟수 | 잡힌 모양 |
| --- | --- | --- |

Jira가 적은 7.2 시험(`비공개로 돌린 키워드는 미리보기에서 빠지고…`) 자체는 **2장의 예산을 고친
뒤 최신 `develop`에 rebase하고 나서** 잡혔습니다(3장). 그 전에는 같은 `describe`의 이웃만
깨졌습니다.

## 2. 3.1 필름 — 예산을 넘긴 것

깨진 모양이 둘뿐입니다. 하나는 시험 하나의 예산 5초를 넘긴 것이고, 다른 하나는 `waitFor`의
예산 1초 안에 조건이 참이 되지 못해 **마지막 폴의 값**이 그대로 단정문에 잡힌 것입니다.

```
AssertionError: expected 20 to be 40        // 다시 불러오기를 누른 뒤 1초 안에 40칸이 되지 못했다
 ❯ FilmPage.test.tsx:334  await waitFor(() => expect(frameCount()).toBe(40));
```

**갱신은 끝내 도착합니다.** 같은 부하에서 예산만 늘려(`asyncUtilTimeout` 20초 ·
`testTimeout` 60초) 전체 실행을 5회 돌리면 모두 통과합니다.

### 얼마나 모자랐나

기다림마다 걸린 시간을 재기 위해 `@testing-library`의 `asyncWrapper`를 잠시 감싸 전체 실행의
기다림 823개를 모두 기록했습니다(확인용이며 저장소에는 남기지 않았습니다).

| 기다림 | 부하 없음 | CPU 16개 점유 |
| --- | --- | --- |
| 1초를 넘긴 기다림 | 12개 (모두 예산을 따로 적어 둔 장면 시험) | **28개** |
| 기본 예산만 쓰는 기다림 중 가장 긴 것 | 0.29초 (`FilmPage`) | **2.07초** (`FilmPage`) |
| `FilmPage.test.tsx` 파일 | 4.4초 | 15~17초 |
| `끝의 다음 장…` 시험 하나 | 0.88초 | 3.8~7.5초 |

즉 **부하 없이 0.1~0.3초면 끝나던 기다림 열 몇 개가 부하 아래에서 1초를 넘습니다.** 어느
시험이 먼저 넘길지는 그때그때 다릅니다. 1초는 한가한 기계에서만 넉넉한 값입니다.

### 3.1 필름이 유독 오래 기다리는 까닭

이 시험들이 전체에서 가장 무겁습니다. 한 장을 20칸으로 두고 세 장까지 이어 받으므로 45칸을
그리고, 칸 수를 세는 도우미가 이렇습니다.

```js
function frameCount() {
  return screen.queryAllByRole('button', { name: /^영화 \d+ 상세 보기$/ }).length;
}
```

`queryAllByRole`에 이름을 주면 **버튼마다 접근성 이름을 다시 계산**합니다. 이 저장소는 시험에서
CSS를 실제로 물리므로(`vite.config.ts`의 `css: true`) 그 계산이 `getComputedStyle`까지 갑니다.
`waitFor`는 조건이 참이 될 때까지 이 도우미를 되풀이해 부르므로 칸이 늘수록 기다림이 무거워집니다.

## 3. 7.2 프로필 편집 — 이동이 전환에 실린 것

예산을 5초로 늘린 뒤에도 최신 `develop`에 rebase하고 돌리니 **Jira가 적은 그 시험이 5.6초를
넘겨 깨졌습니다.** 예산이 모자란 것과는 다른 이야기입니다.

```
TestingLibraryElementError: Unable to find an element with the text: 다른 사용자에게 보이는 내 프로필입니다.
 ❯ ProfileEditPage.test.tsx:370
     fireEvent.click(screen.getByRole('button', { name: '내 공개 프로필 미리보기' }));
     expect(await screen.findByText('다른 사용자에게 보이는 내 프로필입니다.')).toBeInTheDocument();
```

미리보기 안내 바는 데이터를 기다리지 않고 화면이 붙는 순간 그려집니다. 그것이 5초 동안 없었다는
것은 **이동이 아직 커밋되지 않았다**는 뜻이고, 깨진 순간의 화면 덤프에도 편집 화면(`프로필 편집`
제목 · 연필 · `내 공개 프로필 미리보기` 단추)이 그대로 있습니다. 떠나기를 묻는 `alertdialog`는
없습니다 — 무언가가 막은 것이 아니라 아직 그리지 못한 것입니다.

까닭은 데이터 라우터가 주소를 바꾸는 방식입니다(react-router 8 `lib/components.js`).

```js
if (reactDomFlushSyncImpl && flushSync) reactDomFlushSyncImpl(() => setStateImpl(newState));
else if (useTransitions === false) setStateImpl(newState);
else React$1.startTransition(() => { ...; setStateImpl(newState); });
```

전환은 **시간을 쪼개 그립니다.** React는 5ms마다 양보하고 다음 조각을 macrotask로 미루는데,
그 5ms는 실제로 흐른 시간이라 일꾼이 OS에 밀리면 컴포넌트 몇 개마다 양보하게 됩니다. 양보 한
번이 다시 잡히기까지 또 밀리므로, 한가할 때 수십 밀리초면 끝나는 이동이 부하 아래에서 초 단위로
늘어납니다. 7.2 → 7.2-A는 배경층·프로필 레이아웃까지 새로 그리는 큰 이동이라 조각이 많습니다.

**고친 방법**: 시험용 라우터에서 전환을 끕니다(`useTransitions={false}`). -789가
`test/render.tsx`의 `MemoryRouter`에 건 것과 같은 조치이고, 이 파일은 `useBlocker` 때문에
데이터 라우터를 직접 만들어 그 도우미를 쓰지 않으므로 여기에 따로 걸었습니다. 화면이 하는 일은
그대로이고 주소 갱신의 커밋 시점만 보통 갱신과 같아집니다.

> -787의 확인 기록은 `useTransitions={false}`를 걸어도 그대로 깨졌다고 적었습니다. 그때는
> 예산이 1초였고 같은 실행에서 3.1 필름이 함께 깨지고 있었으므로, 전환을 꺼도 남는 예산 문제가
> 실패를 덮고 있었던 것으로 보입니다. 이번에는 예산을 먼저 고친 뒤 전환만 따로 바꿔
> 8회(전 3회 중 2회 실패 → 후 6회 모두 통과)로 갈랐습니다.

## 4. 무엇을 바꿨나

| 파일 | 바꾼 것 |
| --- | --- |
| `src/test/setup.ts` | 기다리는 단정문의 예산을 5초로 둔다(`asyncUtilTimeout`) |
| `vite.config.ts` | 시험 하나의 예산을 20초로 둔다(`testTimeout`) |
| `src/pages/film/FilmPage/FilmPage.test.tsx` | 다음 장 시험 넷의 한 장 칸 수를 줄인다 |
| `src/pages/my/ProfileEditPage/ProfileEditPage.test.tsx` | 시험용 데이터 라우터에서 전환을 끈다 |
| `src/pages/search/SearchPage/SearchDesktop.test.tsx` | 늦게 오는 응답을 기다린다(3장 뒤 발견, 6장) |

**예산**은 부하 아래에서 잰 값을 기준으로 잡았습니다. 기본 예산만 쓰는 기다림의 최대가
2.07초이므로 5초는 그 2.4배이고, 시험 하나의 최대가 7.5초이므로 20초는 2.7배입니다. 장면이
도는 화면(5.9 팝콘 섞기 · EXT 분석)은 예산을 각자 적어 두고 있어 그대로 두었고, 그 시험들이
5초를 넘겨 깨지던 것은 시험 하나의 예산이 감쌉니다.

**칸 수**는 이어 받기와 무관합니다. 이 시험이 보는 것은 커서를 들고 다음 장을 붙이는 것,
겹쳐 온 프레임을 한 번만 그리는 것, 실패해도 그린 것을 두고 자동으로 다시 부르지 않는 것입니다.

| 시험 | 전 | 후 |
| --- | --- | --- |
| 끝의 다음 장 칸으로 나머지 프레임을… | 20 + 20 + 5 = 45칸 | 3 + 3 + 1 = 7칸 |
| 다음 장에 이미 그린 프레임이 섞여 오면… | 20 + 6 = 25칸(20번이 겹침) | 4 + 4 = 7칸(4번이 겹침) |
| 다음 장을 받지 못해도 그린 프레임은… | 20 + 실패 + 10 = 30칸 | 3 + 실패 + 3 = 6칸 |
| 다음 장 칸이 릴 안에서 보일 즈음… | 20 + 실패 + 20 = 50칸 | 5 + 실패 + 5 = 10칸 |

가장 무겁던 `끝의 다음 장…`이 0.88초에서 0.21초가 됐습니다.

## 5. 단정문을 약하게 한 것이 아니다

- **예산은 "조건이 참이 되는가"가 아니라 "얼마나 빨리 참이 되는가"를 잽니다.** 늘려도 조건이
  끝내 참이 되지 않으면 그대로 깨집니다. 늘어난 시간은 깨지는 시험만 치릅니다.
- **건너뛴 시험도, 지운 단정문도 없습니다.** 895개가 그대로입니다.
- **칸 수는 시험의 주제가 아닙니다.** 커서 값, 호출 인자, 겹침 처리, 다음 장 칸이 사라지는 것,
  실패 뒤 관찰자를 다시 걸지 않는 것을 모두 그대로 봅니다.
- **전환을 끈 것은 커밋 시점만 바꿉니다.** 어디로 이동하는지, 무엇이 그려지는지는 그대로이고,
  실제 앱(`src/App.tsx`)의 라우터는 손대지 않았습니다.

## 6. 덤으로 나온 셋째 — 4.2 검색 보조 패널

두 원인을 고친 뒤 부하를 준 실행에서 한 번 더 깨진 곳이 있어 함께 고쳤습니다. 원인은 또
다릅니다.

```
❯ SearchDesktop.test.tsx:202
    await waitFor(() => expect(within(aside).getByRole('heading', { name: '기생충' })).toBeInTheDocument());
    expect(within(aside).getByText(detail.synopsis!)).toBeInTheDocument();   // 여기서 깨졌다
```

보조 패널의 제목은 **검색 결과**(`searchMovies`)가 그대로 주고(`AsidePanel title={item.title}`),
줄거리 · 감독 · 출연 · 장르는 **상세**(API-030)가, 유사한 작품은 **API-031**이 채웁니다. 제목만
기다리고 나머지를 바로 읽으면 서로 다른 응답 사이가 잡힙니다. 부하 아래 9회 중 1회 깨졌고,
깨질 때 시험이 0.3초 만에 끝난 것이 예산 문제가 아님을 말해 줍니다.

**고친 방법**: 늦게 오는 쪽(`detail.synopsis` · `유사한 작품`)을 `findBy*`로 기다립니다. 단정문은
그대로 둡니다.

이 시험은 -784가 만들고 -798이 손댄 것이라 이 업무의 범위 밖입니다. 한 줄짜리 시험 수정이고,
두면 이 업무의 완료 조건(부하 아래 5회 연속 통과)을 아무도 채울 수 없어 **사용자 결정으로
(2026-09-22) 이 MR에 함께 넣었습니다.** 리뷰에서 빼자고 하면 커밋 하나만 빼면 됩니다.

## 8. 확인하지 못한 것과 남은 위험

- **간헐 실패는 "없음"을 증명할 수 없습니다.** 여덟 번 연속 통과는 확률을 낮춘 것이지 재발하지
  않는다는 보장이 아닙니다. 다시 나오면 2장 · 3장 · 6장의 세 유형부터 확인합니다.
- **예산을 늘린 값은 이 기계에서 잰 것입니다.** CI(`node:20.19-alpine`)에서는 MR !572의
  파이프라인 #215967이 한 번 통과했습니다(`frontend-mr-test` 128초). 다만 **한 번**이고 그때
  러너가 한가했는지는 알 수 없으므로, CI가 바쁠 때도 넉넉한지는 지켜볼 일입니다.
- **전환을 끈 것은 시험용 라우터뿐입니다.** 실제 앱은 전환을 그대로 쓰므로, 느린 기기에서 이동이
