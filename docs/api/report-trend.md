### 서명 URL 다운로드

`GET` `/api/v1/report-images/{imageId}/download?expires={epochSeconds}&signature={signature}`

- JWT 인증은 요구하지 않는다. URL 자체가 10분 동안만 유효한 다운로드 capability다
- `expires`는 UTC Unix epoch seconds다
- `signature`는 UTF-8 문자열 `{imageId}\n{expires}`를 리포트 이미지 전용 Secret으로 HMAC-SHA256 서명한 Base64URL(no padding) 값이다
- 서명이 올바르지 않거나 만료됐으면 `403 FORBIDDEN`, 이미지 메타데이터 또는 파일이 없으면 `404 RESOURCE_NOT_FOUND`를 반환한다
- 성공 응답은 PNG 바이트이며 `Content-Type: image/png`, `Content-Disposition: attachment`와 `Cache-Control: private, no-store`를 사용한다

### 오류 응답

- 공통 오류만 해당

### 처리 규칙

- 반기당 사용자 리포트는 하나다. 기간과 발급 시각은 `Asia/Seoul` 기준이다.
- 상반기(`H1`) 리포트의 **새 프레임 포함 마감**은 6월 30일 23:50, 뽑기 가능 시각은 7월 1일 00:00이다. 하반기(`H2`)는 12월 31일 23:50 마감, 다음 해 1월 1일 00:00부터 뽑을 수 있다. 23:50 이후 새로 필름에 추가된 프레임은 이번 리포트에서 제외하고 다음 반기 집계 구간에 포함한다. 따라서 H1의 프레임 생성 구간은 전년도 12월 31일 23:50부터 해당 연도 6월 30일 23:50 직전까지, H2는 해당 연도 6월 30일 23:50부터 12월 31일 23:50 직전까지다(모두 한국시간).
- 기존 프레임·연결 평가·영화 메타데이터의 상태는 마감 시각부터 **최대 5분 뒤(23:55)까지** 획득한 PostgreSQL 일관 스냅샷을 사용한다. 따라서 23:50 이후 스냅샷 획득 전까지 기존 평가를 수정하거나 프레임을 삭제한 내용은 이번 리포트에 반영될 수 있다. 스냅샷 획득 이후 변경은 반영하지 않는다. 23:55까지 스냅샷을 얻지 못하면 늦은 현재 데이터를 과거 상태로 추정해 공개하지 않고 `준비 중` 및 운영 알림 대상으로 둔다. 화면의 `23:50 기준`은 정확한 데이터 상태 시각으로 표기하지 않고, 프레임 포함 마감과 실제 스냅샷 시각의 차이를 구분한다.
- 마감 후 리포트를 미리 집계·검증한다. 정상 경로에서는 준비된 결과를 자정에 뽑기 가능하게 공개한다. 자정에 계산을 시작하거나 사용자 버튼으로 집계를 시작하지 않는다. 준비가 실패하거나 지연되면 불완전한 결과를 발급하지 않고 `준비 중`으로 표시해 재시도·운영 알림 대상으로 삼는다.
- `READY`는 계산 완료 상태이지 목록 공개 여부가 아니다. 사용자가 `새 리포트 뽑기`를 누르면 준비된 결과를 발급하고 프론트가 인화 애니메이션을 보여준 뒤 4컷 목록에 노출한다. 발급하지 않은 리포트는 목록에서 숨긴다. 다음 반기의 예정 공개 시각(7월 1일 또는 다음 해 1월 1일 00:00 KST)이 되면 미발급 이전 `READY` 리포트를 자동으로 목록에 공개한다. 새 반기 리포트가 평가 부족·집계 실패·지연으로 없거나 아직 `READY`가 아니어도 이전 리포트 공개는 늦추지 않는다.
- `items`는 본인의 `READY` 중 `issuedAt != null`이거나 해당 반기의 **다음** 반기 공개 시각이 지난 것만 포함한다. `year` 내림차순, `half`는 `H2`가 `H1`보다 먼저다. `GENERATING`은 목록 카드가 아니라 `current`에서만 알린다.
- `current`는 호출 시점에 공개 시각이 지난 가장 최근 반기의 본인 리포트 행이다. 해당 반기 행이 없으면 `null`; 아직 계산 중인 행은 `status: GENERATING`과 `issuedAt: null`로 나타난다. 미래 반기의 preview는 내보내지 않는다. 홈의 첫 발급 버튼은 `current.status=READY`이고 `issuedAt=null`인 경우에만 표시한다.
- `preparing`은 최신 공개 반기에 `GENERATING` 행이 있거나, 행이 전혀 없고 정상 최종 준비 배치 완료 기록도 없으면 `true`다. 계산 결과가 `READY`이면 `false`다. 정상 완료 기록의 대상이 0명이어서 행이 없으면 `current=null, preparing=false`다. 공개 시각 전 미래 반기의 계산 상태를 나타내지 않는다.
- `createdAt`은 저장된 리포트의 생성 시각(UTC)이며 필름 반영 마감 시각이나 버튼 발급 시각이 아니다. 첫 발급 시각은 `current.issuedAt`과 API-080에서 따로 노출한다.
- 첫 발급 완료 시각은 서버의 `taste_reports.issued_at`에 기록한다(API-080). 자동 목록 공개는 발급 기록을 만들지 않고 조회 시각으로 판정한다. 목록에 공개된 미발급 과거 리포트는 `issuedAt=null`로 남는다.
- 마감 스냅샷의 필름에 남아 있으면서 해당 반기 집계 구간에 생성된 프레임이 3개 미만이면 리포트를 생성하지 않는다. 프레임 없이 `봤어요` 기록만 있는 영화는 포함하지 않는다. 현재 프레임은 평가와 1:1로 연결되어 있지만 집계 기준은 평가 변경 이력이 아니라 필름 프레임이다.
- 반기 최종 준비가 성공했으나 대상 사용자가 0명이면 리포트 행은 없고 기간별 배치 완료 기록만 남긴다. 목록은 `current=null, preparing=false`를 반환하므로 준비 실패·지연과 구분한다.
- 반기 집계는 Spring+PostgreSQL이 담당한다. 마감 후 5분 이내 스냅샷 획득과 자정까지의 준비 성능은 생성 구현에서 검증한다.

### 상태값

- ReportStatus: `GENERATING`, `READY` (계산 상태이며 발급/목록 공개 상태와 별개)
- `half`: `H1`, `H2`

### 미정 사항

- [x] 생성 시점: 마감일 23:50 이후 사전 집계·검증, 다음 날 00:00부터 준비된 결과를 뽑기 가능하게 공개. 버튼은 발급 동작
- [x] 최소 집계 수: 마감 시점 필름에 남은 해당 구간의 프레임 3개 이상
- [x] 생성 주체: Spring+PostgreSQL. 새 프레임은 23:50에 끊고 기존 데이터의 상태는 23:50~23:55 사이의 일관 스냅샷으로 고정
- [x] 다음 반기 예정 공개 시각에 이전 미발급 `READY` 리포트 자동 공개. 새 반기 리포트의 존재·완료 여부와 무관
- [x] 발급 API-080·서버 `issued_at`과 API-059의 `items`/`current`/`preparing` 계약

## API-060 리포트 상세 조회

`GET` `/api/v1/reports/{reportId}`

| 항목 | 값 |
|---|---|
| 단계 | 2차 MVP |
| 인증 | 회원 |
| 관련 요구사항 | FR-23 |
| 화면 | ⑦-1 리포트 상세, ⑪-1-a 리포트 상세 |
| 미정 사항 | 있음 |
| 비고 | - |

### 설명

완성된 반기별 취향 4컷과 상세 리포트를 조회한다. 취향 4컷은 이번 반기 대표 장르 → 감독 → 배우 → 사용자의 필름 분석에 따른 캐릭터 순서이며, 상세 화면에는 장르·국가·시대 비율, 감독·배우 감상 편수, 캐릭터 설명, 지난 반기 비교를 표시한다.

### 인증 및 권한

- 회원. 본인 리포트만

### Path Parameters

- `reportId`

### Query Parameters

없음

### Request Body

없음

### Response

`200 OK`

```json
{
  "reportId": 301,
  "period": { "year": 2026, "half": "H1" },
  "summary": { "ratingCount": 38, "newFlavorCount": 2, "averageScore": 4.1 },
```

리포트의 집계 대상은 마감 스냅샷 시점에 **내 필름에 남아 있는 프레임**이다. `frames.created_at`이 해당 6개월 집계 구간에 속하는 프레임을 그 반기의 영화로 센다. 기존 응답의 `summary.ratingCount`도 이 프레임 수와 일치한다. 현재 스키마에서는 프레임이 평가와 1:1로 연결되지만, 집계의 기준은 평가 변경 이력이 아니라 필름이다. 한줄평 내용이나 별점 높낮이는 포함 여부를 바꾸지 않는다. 평가를 완전히 삭제해 프레임이 사라지면 이후 리포트의 집계·과거 판정에서 제외하고, `봤어요` 감상 기록만 남은 영화는 프레임이 없으므로 포함하지 않는다.

### 포함 섹션과 필드

| 화면 섹션 | 응답 필드 | 계약 |
|---|---|---|
| 취향 4컷 | `fourCut.genre`, `director`, `actor`, `character` | 네 칸은 같은 `period`의 리포트 결과다. 이름은 각각 `topGenres[0]`, `topDirectors[0]`, `topActors[0]`, `characterCard`와 일치한다. 대표 장르는 해당 반기 필름 프레임의 장르별 영화 편수가 많은 순으로 선정하고, 편수가 같을 때만 그 장르 영화의 평균 별점으로 순서를 정한다 |
| 4컷 이미지·표기 | 각 칸의 `name`, `displayName`, `image`; 감독의 `work` | `name`은 표시 이름이다. `displayName`은 큰 글자용 표기로 없으면 `null`이며 화면은 `name`을 사용한다. 이미지가 없으면 `image.url: null`, 감독 대표작 이미지가 없으면 `work: null`로 반환한다. **`fourCut.character`에는 `image`를 두지 않는다.** 04 칸 그림은 고정 16종의 저장소 에셋이므로 화면이 `characterCard.code`로 짝지어 찾는다 |
| 상세 비율 | `genreShares`, `countryShares`, `eraShares` | 각 항목은 `{ "label": string, "share": number }`이며 `share`는 화면에 표시할 0~100의 **정수 퍼센트**로 최종 단계에서 반올림한다(`5/12 = 41.67%` → `42%`). 해당 반기에 추가되어 마감 스냅샷의 필름에 남은 **프레임 한 개(영화 한 편)를 한 표**로 세며 별점 크기로 가중하지 않는다. 상위 항목만 반환할 수 있어 배열 합계를 100으로 가정하지 않는다. `eraShares`만은 상위 두 연대의 이름 줄 뒤에 나머지 연대를 모두 합친 `그 이전` 한 줄을 덧붙인다(업무 -774). `그 이전`은 이름과 달리 남은 연대 전부이며 상위 두 줄보다 최근인 연대도 들어갈 수 있고, 합칠 나머지가 없으면 그 줄을 넣지 않는다. 개봉 연도가 없는 영화는 어느 줄에도 세지 않되 분모에는 남는다 |
| 감독·배우 | `topDirectors`, `topActors` | `count`는 해당 반기 리포트에 포함된 감상 영화 편수로 표시한다 |
| 캐릭터 설명 | `characterCard` | `code`는 16종을 식별하는 불변 값이다. `name`은 카드 이름, `tagline`은 한 줄 요약, `description`은 네 축을 풀어 쓴 설명문이다. `axes`는 네 축의 판정 결과이며 화면이 축 막대를 그려 왜 이 카드인지 보인다. 각 항목은 `{ "axis": "EXPLORATION" | "TONE" | "STANCE" | "VOLUME", "value": string, "label": string }`이고 순서는 코드의 글자 순서와 같다. `basis`는 `{ "frameCount": number, "lowSample": boolean }`이며 `frameCount`가 10 미만이면 `lowSample`이 `true`다. `name`·`tagline`·`description`은 기준정보라 바뀔 수 있고 `code`만 계약이다 |
| 지난 반기와 비교 | `comparisons` | 각 항목은 `{ "label": string, "delta": number, "isNew": boolean }`이며 **비교 축은 팝콘 맛**이다(업무 -774). `label`은 `popcorn_flavors.display_name`이고 장르명이 아니다. 영화 한 편에 대표 맛이 하나라 반기 안의 비율 합이 100%가 되며, 한 편이 여러 장르에 중복으로 세어지는 장르는 이 자리에 쓰지 않는다. 3.3 인화 화면의 `새로 넓어진 팝콘 맛` 요약도 같은 축이다. 대표 맛이 없는 프레임은 어느 항목에도 세지 않되 분모에는 남는다. 같은 마감 스냅샷에 남아 있는 프레임을 이번/직전 6개월 구간으로 나눠 각 비율을 계산한다. `delta`는 같은 항목의 **반올림 전** 이번 반기 비율에서 직전 반기 비율을 뺀 퍼센트포인트 차이를 마지막에 정수 반올림한 값이다(`41.67% − 30% = 11.67%p` → `+12%p`). 표시된 정수 비율이나 과거 리포트에 저장된 비율을 빼지 않는다. `isNew: true`는 이번 반기 전의 **필름에 남아 있는 모든 프레임**에서 해당 항목을 찾을 수 없을 때만 붙인다. 직전 6개월에만 없고 더 이전의 남아 있는 프레임에 있었다면 `false`다. 첫 리포트처럼 비교할 지난 반기 리포트가 없으면 빈 배열이다 |
| 발급 화면 요약 | `highlights` | 인화 화면의 주황색 표시 영역에 노출할 짧은 문장 최대 3개다. 생성된 반기 스냅샷의 실제 비교·신규 감독·새 팝콘 맛 등 확인 가능한 결과로 만들며, 목업 문구나 근거 없는 수치를 반환하지 않는다. 이전 반기 등 근거가 없으면 해당 비교 문구를 생략하거나 사실에 맞는 요약으로 대체한다 |
| 취향 키워드 | `keywords` | 각 항목은 `{ "code": string, "label": string, "rationale": string }`이며 그 반기 집계에서 **수치로 뒷받침되는 것만** 만든다(업무 -774). `rationale`에 그 수치를 그대로 적는다. **규칙마다 임계값을 두고 넘긴 것만** 아래 순서대로 최대 네 개를 반환하므로 반기마다 뜨는 종류가 달라지고, 하나도 넘기지 못하면 빈 배열이다. 화면은 비면 이 섹션을 숨긴다. 와이어프레임의 `계획형 안티히어로` · `빠른 전개` · `반전 선호`는 캐릭터 성격·전개 태그 기준정보가 없어 범위 밖이며, 없는 근거를 지어내지 않는다 |

취향 키워드 규칙과 임계값은 다음과 같다. 위에서부터 조건을 넘긴 것만 골라 네 개를 채우면 멈춘다.

| 순서 | `code` | 조건 | `label` · `rationale` 예 |
|---|---|---|---|
| 1 | `DIRECTOR_BINGE` | 한 감독 3편 이상 | `봉준호 몰아보기` · `봉준호 영화 4편` |

`GENRE_FAVORITE`(1위 장르가 2편 이상이고 평균 ★4.0 이상)는 `GENRE_DEVOTEE` · `GENRE_OMNIVORE` 다음에 같은 장르 묶음에서 판정한다. 앞쪽 규칙일수록 그 반기를 다른 사용자의 반기와 가르는 힘이 세다고 보아 순서를 정했다.

`fourCut.*.image`는 `{ "url": string | null, "cutoutUrl"?: string | null, "position"?: { "x": number, "y": number }, "zoom"?: number }` 형태를 사용하며 `genre`·`director`·`actor` 세 칸에만 있다. `cutoutUrl`은 배경이 제거된 이미지, `position.x/y`는 0~100 범위의 크롭 위치다. `cutoutUrl`, `position`, `zoom`은 없으면 생략할 수 있다. 이미지가 없어도 네 칸의 이름과 상세 데이터는 반환하며 화면은 텍스트 대체 표시를 사용한다.

감독·배우 칸의 `image.url`은 리포트에 선정된 `personId`의 기존 `people.profile_url`을 반기 결과에 보존해 반환한다. 기존 TMDb 적재가 `profile_path`를 이 필드에 저장하므로 리포트 조회나 인화 버튼에서 TMDb를 다시 호출하지 않는다. 해당 인물의 URL이 없거나 사진 표시가 허용되지 않으면 `null`이며, 프론트는 이름만 있는 카드로 대체한다. `cutoutUrl`이나 영문 `displayName`을 사진 URL에서 추측해 만들지 않는다. 외부 PNG에 사진을 합성해 공유하는 권한은 앱 안에서 URL을 표시하는 경우와 별도로 확인한다.

`createdAt`은 저장된 리포트 행의 생성 시각이며 사용자가 버튼을 눌러 뽑은 시각이 아니다. 4컷의 인화 월(`H1`의 다음 7월, `H2`의 다음 해 1월)은 `period`에서 정한다.

상세 화면의 저장·공유 버튼은 이 조회 응답의 별도 상태가 아니다. 두 버튼과 공유 시트의 `이미지로 저장`은 API-061의 같은 취향 4컷 PNG를 사용한다. `저장`을 단순 화면 이탈로 처리하지 않는다.

### 오류 응답

- `404 RESOURCE_NOT_FOUND`: 리포트가 없거나 타인 소유, 또는 예정 공개 시각 전
- `409 REPORT_GENERATING`

### 처리 규칙

- 리포트는 생성 시점 스냅샷이며 이후 평가 변경을 반영하지 않는다
- API-060은 `READY` 상태의 저장된 결과를 반환하며 조회할 때 현재 평가 데이터를 다시 분석하지 않는다
- 본인 `READY`의 상세는 **해당 반기 예정 공개 시각 이후** 첫 인화 화면도 저장 결과로 렌더링해야 하므로 `issuedAt=null`이어도 조회할 수 있다. 공개 전에는 본인 리포트도 404로 숨긴다. 목록 공개 여부는 이후 상세 접근 권한이 아니며, 타인·없는 ID도 모두 404다. 내부 `content.generation` 메타데이터는 응답에서 제외한다
- 반기 비율과 대표 장르는 그 6개월 동안 필름에 추가되어 마감 시점에도 남은 프레임의 **영화 편수**를 기준으로 하며 별점은 대표 장르의 편수 동률일 때만 사용한다. 비율과 퍼센트포인트 차이는 각각 원본 분자·분모로 계산한 뒤 마지막에 정수 반올림한다. 과거 리포트의 표시용 정수 비율만으로 차이를 다시 계산하지 않는다. 화면 목업 수치를 실제 계산 결과로 사용하지 않는다
- `isNew`는 단순히 직전 반기 0%라는 뜻이 아니라 리포트 기준 스냅샷에 **남아 있는 이전 기간의 필름 프레임 전체**에 해당 항목이 없다는 뜻이다. 삭제되어 필름에서 사라진 프레임은 과거 이력으로 세지 않으며, 평가 삭제 후 남은 `봤어요` 감상 기록도 세지 않는다. 따라서 과거 리포트에 나타난 항목이어도 관련 과거 프레임이 모두 사라졌다면 다시 `신규`가 될 수 있다. 이전 리포트 스냅샷 자체는 바꾸지 않는다
- `characterCard`는 고정된 **16종 중 하나**이며 네 축을 각각 두 값으로 판정한 조합이다. 축 순서는 `EXPLORATION`(`E` 탐험 / `R` 정착) → `TONE`(`L` 빛 / `D` 그림자) → `STANCE`(`H` 가슴 / `M` 머리) → `VOLUME`(`V` 다작 / `S` 정독)이고, 네 글자를 이어 붙인 값이 `code`다. 16종을 다 쓰므로 후보 없음이 발생하지 않으며 `characterCard`를 `null`로 반환하지 않는다
- 판정은 **그 반기에 리포트가 생성된 사용자 전체**를 모집단으로 한 상대 판정이다. 축별 중앙값은 집계 배치가 한 번 구해 리포트와 함께 스냅샷으로 저장하며, 리포트가 생성 시점 스냅샷이므로 조회 시 다시 계산하지 않는다. 같은 반기의 모든 리포트는 같은 중앙값 스냅샷을 쓴다
- 기본 규칙은 **값이 중앙값 이상이면 앞글자**(`E`·`L`·`H`·`V`)다. 축별 예외가 셋 있다. `EXPLORATION`은 중앙값이 0이면 전원이 `E`가 되므로 그때만 `1개 이상 = E`로 판정한다. `TONE`은 분모가 0이면(중립 맛만 감상) `L`을 기본값으로 둔다. `STANCE`는 값이 중앙값과 같으면 그 사용자 평점의 표준편차가 작은 쪽을 `H`로 둔다
- 축의 지표는 `EXPLORATION`이 `summary.newFlavorCount`, `STANCE`가 `summary.averageScore`, `VOLUME`이 `summary.ratingCount`이고, `TONE`만 팝콘 집계에서 새로 계산한 **밝은 맛 비중**이다
- 밝은·어두운 맛 배정은 표시명이 아니라 **`popcorn_flavors.code`** 로 건다. 표시명은 변경 가능한 기준정보이고 실제로 마이그레이션에서 값이 옮겨간 적이 있다. 밝음은 `FLAVOR_C`·`FLAVOR_F`·`FLAVOR_G`(관계·로맨스·코미디·가족·애니메이션·판타지), 어두움은 `FLAVOR_B`·`FLAVOR_D`·`FLAVOR_E`(공포·미스터리·스릴러·범죄·전쟁), 중립은 `FLAVOR_A`·`FLAVOR_H`(다큐·역사 / 액션·SF)다. 중립 2종은 분자와 **분모 모두에서 제외**한다. 이 배정의 근거는 두 마이그레이션이 바꾸지 않은 `popcorn_flavors.representative_keywords`다
- 모집단이 **30명 미만**이면 중앙값이 한두 명에 흔들리므로 축별로 사전 정의한 고정 임계값을 쓴다. `STANCE`는 평점 3.8, `VOLUME`은 편수 10편, `TONE`은 밝은 맛 비중 0.5이며 `EXPLORATION`은 `1개 이상 = E`를 쓴다. 이 폴백을 적용했는지는 중앙값 스냅샷에 함께 기록한다
- 카드는 리포트 생성 조건(프레임 3편 이상)을 만족하면 **항상 발급한다.** 카드에 별도 하한을 두지 않는다. `basis.frameCount`는 그 반기 프레임 편수이고 10편 미만이면 `basis.lowSample`이 `true`이며 화면이 기준 편수를 함께 안내한다
- 네 축은 서로 독립이 아니다. 어두운 쪽을 선호하는 사용자가 평점도 낮은 경향이 있어 `D`와 `M`, `L`과 `H`가 함께 나오기 쉽다. 상대 판정이 각 축을 반반으로 가르므로 한쪽 쏠림은 막지만 축 간 상관은 남아 일부 조합이 드물게 나올 수 있다. 반기 1회차 실데이터를 확인한 뒤 `TONE`·`STANCE`의 정의를 조정할 수 있다
- `name`·`tagline`·`description`과 04 칸 그림은 기준정보이며 `code`에서 파생한다. 계약은 `code`뿐이므로 표시 문구가 바뀌어도 응답 계약은 그대로다. 16종은 다음과 같다

| `code` | 카드 이름 | 축 |
|---|---|---|
| `ELHV` | 길 위의 낙천가 | 탐험·빛·가슴·다작 |
| `ELHS` | 토끼굴에 빠진 아이 | 탐험·빛·가슴·정독 |
| `ELMV` | 세계 일주하는 수집가 | 탐험·빛·머리·다작 |
| `ELMS` | 풀숲의 관찰자 | 탐험·빛·머리·정독 |
| `EDHV` | 복수자 | 탐험·그림자·가슴·다작 |
| `EDHS` | 돌아오지 못한 자 | 탐험·그림자·가슴·정독 |
| `EDMV` | 금기를 여는 자 | 탐험·그림자·머리·다작 |
| `EDMS` | 심연을 들여다본 학자 | 탐험·그림자·머리·정독 |
| `RLHV` | 이야기 많은 아이 | 정착·빛·가슴·다작 |

## API-080 리포트 첫 발급 기록

`POST` `/api/v1/reports/{reportId}/issue`

| 항목 | 값 |
|---|---|
| 단계 | 2차 MVP |
| 인증 | 회원·본인 리포트만 |
| 관련 요구사항 | FR-23 |
| 화면 | 홈/필름의 `새 리포트 뽑기` 인화 완료 |

### 설명

이미 준비된 리포트의 **홈 첫 인화 완료**를 서버에 한 번 기록한다. 이 요청은 반기 분석을 시작하거나 재집계하지 않는다. 프론트는 인화 애니메이션을 보여준 뒤 이 요청에 성공하면 목록으로 이동한다. 나중에 목록·상세에서 `다시 뽑기` 애니메이션을 제공하더라도 이 API를 호출하지 않는다.

### Request

Path parameter `reportId`: 양의 정수. 요청 본문 없음.

### Response

첫 요청과 재시도 모두 `200 OK`:

```json
{ "reportId": 301, "issuedAt": "2026-07-01T00:00:14Z" }
```

`issuedAt`은 UTC의 **최초** 기록 시각이며, 중복 요청은 값을 바꾸지 않는다.

### 오류 응답

- `404 RESOURCE_NOT_FOUND`: 없는 ID 또는 타인 리포트
- `409 REPORT_GENERATING`: 본인 리포트가 아직 `GENERATING`
- `409 CONFLICT`: 공개 시각 전 또는 다음 반기 공개 시각이 지난 미발급 리포트의 첫 발급

### 처리 규칙

- H1은 같은 해 7월 1일 00:00 KST부터 다음 해 1월 1일 00:00 KST 직전까지, H2는 다음 해 1월 1일 00:00 KST부터 7월 1일 00:00 KST 직전까지 최초 발급할 수 있다. 경계 시각은 앞 포함·뒤 제외다.
- `READY`와 발급은 별도 상태다. `issued_at`은 조건부 갱신으로 최초 한 번만 저장하고 동시·반복 요청은 기존 시각을 반환한다. 이미 발급된 리포트의 재시도는 발급 창이 지난 후에도 기존 시각을 반환한다.
- 발급 요청이 실패하면 화면은 성공한 것으로 처리하지 않고 사용자가 재시도할 수 있게 한다. 애니메이션 재생 횟수 자체는 백엔드에서 세지 않는다.

### 인증 및 권한

### Path Parameters

- `reportId`

### Query Parameters

없음

### Request Body

없음

### Response

`201 Created`

```json
{
  "imageId": 811,

  "downloadUrl": "https://j15e106.p.ssafy.io/api/v1/report-images/811/download?expires=1788067860&signature=...",
```

### 오류 응답

- `404 RESOURCE_NOT_FOUND`
- `409 REPORT_GENERATING`

### 처리 규칙

- 파일 형식은 PNG만. PDF는 제공하지 않는다
- 서버는 Java2D headless 렌더링으로 PNG를 생성한다
- PNG는 서비스 노드의 `/srv/feelm/data/report-images`에 저장하고 Backend 컨테이너에는 `/data/report-images`로 읽기·쓰기 bind mount한다(ADR-0023)
- DB에는 서버가 생성한 상대 `storage_key`만 저장한다. 클라이언트가 보낸 파일명이나 경로를 저장 키로 사용하지 않는다
- 리포트 이미지 디렉터리는 Nginx 정적 공개 경로로 노출하지 않는다. API-061이 본인 리포트인지 확인한 뒤 발급하는 서명 URL로만 접근한다(NFR-07)
- 다운로드 URL은 발급 시점부터 10분 동안 유효하다. 다운로드 엔드포인트는 JWT 없이 접근할 수 있지만 만료 시각과 애플리케이션 서명을 검증하고, 실패하거나 만료되면 파일을 반환하지 않는다
- 다운로드 서명에는 리포트 이미지 식별자와 만료 시각을 포함하고 전용 Secret으로 HMAC-SHA256 서명한다. JWT Secret을 재사용하지 않으며 비교는 constant-time으로 수행한다
- 다운로드 응답은 `Content-Type: image/png`와 `Cache-Control: private, no-store`를 사용한다
- 이미 생성된 이미지와 파일이 모두 있으면 재렌더링하지 않고 새 서명 URL만 발급한다. DB 행만 있고 파일이 없으면 원본 리포트로 다시 렌더링해 복구한다
- 생성 대상은 상세 화면 전체나 인화기 배경이 아닌 취향 리포트 4컷 PNG다. 공유 이미지에는 닉네임·계정 식별자 등 개인정보를 넣지 않는다. 앱 안의 4컷에 닉네임이 보이더라도 공유·저장용 PNG는 별도로 안전하게 렌더링한다
- 클라이언트의 `저장`/`이미지로 저장`은 URL 발급 성공 메시지만 보여주는 것이 아니라 PNG 파일을 실제로 내려받는다. 스토리지 또는 다운로드 중계 경로는 프론트가 이미지 바이트를 읽어 공유할 수 있도록 접근·CORS 정책을 맞춘다
- 공유는 클라이언트가 PNG 파일을 기기 공유 시트로 전달하는 방식이며 서버 측 SNS 연동은 없다. 카카오톡·인스타그램 노출은 설치 앱·기기·브라우저 지원에 좌우되므로 특정 앱의 표시/게시 완료를 API가 보장하지 않는다. 이미지 파일 공유가 불가능하면 다운로드 후 해당 앱에서 직접 공유할 수 있게 안내한다

## API-064 급상승 영화

| 항목 | 값 |

| 미정 사항 | 구현 세부값은 실측 후 조정 |
| 비고 | 실시간 조회 이벤트 집계(ADR-0017) |

### 설명

최근 로그인 사용자의 영화 상세 조회 추이를 기반으로 급상승 영화를 제공한다. 비회원 상세 조회는 `VIEW` 발행 대상이 아니다([스트리밍 계약](./streaming-contract.md#43-이벤트별-payload)). 순위는 Spark Structured Streaming이 사전 집계하며 API 요청 시 다시 계산하지 않는다(ADR-0017).

첫 유효한 급상승 목록이 생기기 전에는 아래 고정 초기 순서 A를 보여준다. 첫 비어 있지 않은
집계 결과 B가 생기면 B로 전환하고, 이후 새 유효 B가 없으면 마지막 B를 기간 제한 없이
유지한다. 빈 5분 집계는 A로 되돌리거나 B를 지우지 않는다. KOBIS는 초기 목록에 사용하지 않는다.

| --- | --- | ---: |
| 1 | 오디세이 | 134626 |
| 2 | 왕과 사는 남자 | 124813 |
| 3 | 스파이더맨: 브랜드 뉴 데이 | 86995 |
| 4 | 프로젝트 헤일메리 | 80719 |
| 5 | 인턴 | 55230 |
| 6 | 옵세션 | 36815 |
| 7 | 타짜 | 17057 |
| 8 | 스파이더맨: 노 웨이 홈 | 79065 |
| 9 | 트로이 | 522 |
| 10 | 스파이더맨: 파 프롬 홈 | 68176 |

### 인증 및 권한

- 공개

### Path Parameters

없음

### Query Parameters

- `size` (integer, 기본 10, 허용 1~30). 범위를 벗어나거나 정수가 아니면 `400 VALIDATION_FAILED`

### Request Body

없음

### Response

`200 OK`

```json
{
  "source": "VIEW",
  "period": { "from": "2026-09-18T11:00:00Z", "to": "2026-09-18T12:00:00Z" },
  "updatedAt": "2026-09-18T12:00:00Z",
  "stale": false,
  "items": [
    {
      "rank": 1,
      "rankDelta": null,
      "movie": { "movieId": 550, "title": "파이트 클럽", "posterUrl": "https://..." },
      "ratingCount": 120,
      "averageScore": 4.3,
      "trendScore": 1.0
    }
  ]
}
```

초기 A는 `source="DEFAULT"`, `period=null`, `updatedAt=null`, `stale=false`로 반환한다.
각 항목의 `rankDelta`와 `trendScore`는 `null`이며 `rank`는 위 고정 순서다.
영화 메타데이터와 평점 필드는 기존 영화 데이터에서 채운다. B는 `source="VIEW"`이고
위 예시처럼 집계 시각과 점수를 포함한다. `size`는 선택된 목록의 앞부분에 적용한다.

### 오류 응답

- `400 VALIDATION_FAILED`: `size`가 정수가 아니거나 1~30 범위를 벗어남
- `503 TREND_UNAVAILABLE`: Redis 조회 장애 등으로 최신 또는 마지막 정상 급상승 결과(B)를 조회할 수 없고 초기 고정 목록(A)으로 안전하게 대체할 수도 없음
- 그 외 공통 오류 적용

### 처리 규칙

- 여러 사용자의 `VIEW` 이벤트는 Spark Structured Streaming이 사전 집계하고 Spring Boot는 Redis 결과를 조회한다
- `to`는 UTC 5분 경계다. 현재 구간 `[to-60분, to)`의 영화별 고유 조회 회원 수 `C`와 직전 구간 `[to-120분, to-60분)`의 고유 조회 회원 수 `P`를 비교한다. 구간 시작은 포함하고 끝은 제외한다.
- 같은 `eventId`의 재전달은 스트리밍 계약의 watermark 기반 중복 판정 창에서 제거한다. 서로 다른 `eventId`여도 같은 회원이 같은 영화를 한 구간에서 여러 번 조회했다면 고유 조회자 1명으로 센다. `dwellMs`는 순위에 사용하지 않는다.
- `C >= 3`이고 증가분 `D = C - P > 0`인 영화만 후보로 삼는다. `D` 내림차순, `C` 내림차순, `movieId` 오름차순으로 정렬해 최대 30편을 게시한다. 후보가 없으면 기존 유효 B를 덮어쓰지 않는다.
- API는 게시된 목록의 정렬 순서에서 앞 `size`편만 반환한다. `rank`와 `rankDelta`는 최대 30편 전체 스냅샷을 기준으로 계산하며 `size`에 따라 다시 계산하지 않는다.
- 후보 중 최대 증가분을 `Dmax`라 할 때 각 영화의 `trendScore = D / Dmax`다. 후보가 있을 때 값의 범위는 `(0, 1]`이며 평점이 아니다.
- `rankDelta`는 직전 게시 스냅샷의 순위에서 현재 순위를 뺀 값이다. 직전 목록에 없으면 신규 진입으로 `null`, 순위가 같으면 `0`이다. 현재 목록에서 이탈한 영화는 응답하지 않는다.
- 입력 이벤트가 없는 때에도 UTC 5분 경계마다 집계를 확인하며, 유효한 후보가 있을 때만 새 B를 게시한다. Spark의 이벤트 소비·마이크로배치 실행 주기는 별도로 정한다. 정상 도착한 `VIEW`의 발생부터 결과 게시까지 10분 이내를 초기 운영 목표로 삼고 실측한다.
- API 요청 시 인기 순위를 다시 계산하지 않는다
- 최신 유효 B(`feelm:trending:current`, TTL 15분)를 읽으면 `stale=false`로 `200 OK`를 반환한다. 최신 결과가 없고 마지막 유효 B(`feelm:trending:last-good`, 만료 없음)를 읽을 수 있으면 원래 `period`·`updatedAt`을 유지하고 `stale=true`로 반환한다. 오래되었다는 이유만으로 B를 폐기하지 않는다.
- 유효 B가 아직 없으면 초기 A를 `200 OK`로 반환한다. Redis 조회 장애로 최신 또는 마지막 정상 급상승 결과(B)를 조회할 수 없으면 `503 TREND_UNAVAILABLE`을 반환한다. Redis 전체 유실 시 마지막 B의 보존은 보장할 수 없으며, 저장된 B가 없음을 정상적으로 조회한 뒤 A를 사용한다.
