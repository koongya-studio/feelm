# ADR-0025: 평가 삭제가 감상 기록을 안 본 상태로 되돌린다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-25 |
| 결정자 | S15P21E106-884 작업 승인 |
| 관련 | FR-18, API-034, API-035, API-037, API-038, ERD D-6, D-9, S15P21E106-721, S15P21E106-884 |

## 맥락

감상 기록 `watch_records`는 한 사용자와 한 영화에 대해 `LINK_CLICKED` · `WATCHED_UNRATED` · `RATED` · `EXPIRED` 중 하나의 상태를 가진다. 기록은 두 경로로 생긴다. OTT 보러가기 클릭이 `LINK_CLICKED` 기록을 만들고 감상 확인(API-035)의 `watched: true`가 `WATCHED_UNRATED`로 옮긴다. 평가 저장(API-036)은 활성 기록이 없으면 `RATED` 기록을 새로 만든다(D-6).

지금까지 평가 삭제(API-038)는 `ratings` 행을 지우고 `frames`는 CASCADE로 함께 지우면서, 감상 기록은 `WATCHED_UNRATED`로 되돌렸다. 본 것은 사실이고 평가만 없는 상태라는 뜻이다.

그 결과 앱에서 평가만 남겼다가 지운 영화가 `최근 본 영화`와 `안 남긴 영화`에 영원히 남는다. S15P21E106-721이 API-035에 `WATCHED_UNRATED` → `EXPIRED` 전이를 더해 서버에는 되돌릴 수단이 생겼지만, 그 전이를 부르는 화면이 없어 사용자는 닿을 수 없다.

남은 선택은 평가 삭제와 감상 취소를 사용자가 따로 고르게 할 것인가, 아니면 평가 삭제 하나로 합칠 것인가다.

## 결정

평가 삭제(API-038)가 연결된 감상 기록을 `EXPIRED`로 되돌린다. 같은 트랜잭션에서 처리하며 별도의 감상 취소 동작을 화면에 두지 않는다.

`watched_at`과 `rated_at`을 비우고 `expired_at`을 적는다. 감상 취소(API-035 `watched:false`)가 남기는 모양과 같아 어느 경로로 왔든 `EXPIRED` 행의 뜻이 하나다. 행은 지우지 않고 이력으로 남긴다(D-9).

사용자가 마주하는 동작은 셋으로 정리된다. 잘못 평가했으면 평가 화면에서 삭제해 안 본 상태로 되돌린다. 봤는데 점수를 바꾸고 싶으면 수정(API-037)을 쓴다. 영화가 마음에 들지 않았을 뿐이면 낮은 점수를 남긴다. 삭제와 취소를 나누어 고르게 하면 세 경우가 네 갈래로 늘어 사용자가 무엇을 눌러야 할지 헷갈린다(사용자 결정 2026-09-25).

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 평가 삭제가 감상까지 되돌린다 · 백엔드 한 트랜잭션 (선택) | 사용자가 고를 것이 없고 화면이 늘지 않는다. 중간 실패가 없으며 어느 화면에서 지워도 결과가 같다 | API-038의 계약이 바뀐다. 클릭으로 쌓인 감상 이력도 함께 만료된다 |
| 감상 취소를 별도 사용자 동작으로 분리 | 평가와 감상의 의미를 나누어 유지하고 평가 없이 생긴 기록도 되돌릴 수 있다 | 같은 목적에 선택지가 둘이라 무엇을 눌러야 할지 헷갈린다. 진입점을 두 화면에 더해야 한다 |
| 프론트가 API-038 뒤에 API-035를 이어 부른다 | 서버 계약을 바꾸지 않는다 | 두 요청이 별개 트랜잭션이라 사이에서 끊기면 기록만 남는다. 다른 화면에서 지우면 되돌아가지 않는다 |
| 감상 기록 삭제 API 신설 | 뜻이 직관적이다 | 기존 상태 기계와 중복되고 이력 보존 정책(D-9)과 어긋난다 |

선택지를 나누지 않기로 한 근거는 사용자의 실제 행동이다. 점수를 고치려는 사람은 삭제가 아니라 수정을 쓰고, 영화가 별로였던 사람은 낮은 점수를 남긴다. 평가를 지우는 사람은 대체로 잘못 남겼거나 보지 않은 경우다. 그렇다면 삭제 하나가 그 뜻을 그대로 담는 편이 화면도 단순하고 설명할 것도 적다.

백엔드에 두는 이유는 원자성이다. 화면이 두 요청을 이어 부르면 사이에서 끊길 때 평가만 사라지고 기록이 남는데, 그 상태를 수습할 경로를 화면마다 다시 만들어야 한다. 서버가 한 트랜잭션으로 처리하면 평가를 어디에서 지우든 결과가 같다.

## 결과

- **얻는 것**: 사용자가 고를 것이 없는 단순한 동작, 평가를 지우면 추천 후보로 되돌아오는 일관된 결과, 중간 실패가 없는 원자적 처리, 화면 추가 없음
- **감수하는 것**: 보러가기로 쌓인 `ott_id` · `clicked_at` · `watched_at`이 평가 삭제로 함께 만료된다. 파티 추천에서 한 사람의 평가 삭제가 파티원 전체의 후보를 바꾼다. 보고 나서 평가를 지우려던 사용자는 본 기록까지 잃으므로 확인 창이 그 사실을 분명히 말해야 한다
- **남는 공백**: 보러가기 뒤 `봤어요`만 누르고 평가하지 않은 기록은 화면에서 되돌릴 수 없다. API-035의 `WATCHED_UNRATED` → `EXPIRED` 전이(S15P21E106-721)는 서버에 남겨 두되 진입점을 만들지 않는다. 그 경우가 실제로 문제가 되면 별도 업무로 다시 본다
- **후속 작업**: S15P21E106-884에서 API-038 구현과 계약 문서, 2.5 확인 창 문구를 고친다. `docs/api/watch.md`의 API-038 처리 규칙과 `docs/erd.md`의 상태 흐름을 함께 갱신한다
