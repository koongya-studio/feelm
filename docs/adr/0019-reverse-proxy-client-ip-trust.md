# ADR-0019: 클라이언트 IP는 신뢰 목록 안의 프록시가 보낸 X-Real-IP만 채택하고 IP 제한은 프리픽스 단위로 집계한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-09 |
| 결정자 | BE-A 박시현 결정, S15P21E106-288에서 기록. Nginx 설정 정리는 인프라 담당 합의 대상(S15P21E106-326) |
| 관련 | API-078(개정 전 API-003), API-004, API-010, S15P21E106-223(현재 Nginx 구성), S15P21E106-281(결정 D-9), S15P21E106-288, S15P21E106-312, S15P21E106-326 |

## 맥락

인증·재설정 메일 발송(API-003·API-010)에는 IP 단위 제한이 있다. 애플리케이션은 클라이언트 IP를
`HttpServletRequest#getRemoteAddr()`로만 얻고 전달 헤더를 읽지 않았다(S15P21E106-281 결정 D-9).
신뢰할 프록시 목록 없이 헤더를 믿으면 헤더 한 줄로 IP 단위 제한의 예산 주체를 바꿀 수 있기 때문이다.

**그 전제는 이미 깨져 있다.** `infra/nginx/nginx.conf`는 S15P21E106-223(`53d15a4`)부터 `/api`를
backend 컨테이너로 프록시하고, `infra/compose/service.yml`의 backend 서비스에는 공개 포트가 없어
Compose 네트워크에서만 닿는다. 그래서 Tomcat이 보는 발신지는 **항상 Nginx 컨테이너 IP 하나**이고,
전체 사용자가 IP 단위 제한의 한 예산을 함께 소모한다. 메일 IP 한도 10건/1시간이 사실상 서비스 전체
한도로 동작한다. 이 결정은 미래 대비가 아니라 **살아 있는 결함의 수정**이다.

Nginx가 지금 보내는 헤더는 두 가지다. `X-Forwarded-For`는 `$proxy_add_x_forwarded_for`로 클라이언트가
보낸 값 뒤에 실제 발신 주소를 **이어 붙이고**, `X-Real-IP`는 `$remote_addr`로 **덮어쓴다**. Tomcat
`RemoteIpValve`는 목록을 오른쪽부터 평가하므로 이어 붙인 값에서도 외부 클라이언트는 예산 주체를 바꿀
수 없다. 그러나 목록의 항목이 **모두 신뢰 대역이면 밸브는 맨 왼쪽 값을 채택한다**(`invoke`가 내부
프록시 판정보다 먼저 값을 대입한다). Tomcat에 닿는 모든 발신지가 신뢰 대역인 이 구성에서는, 내부
대역에서 Nginx로 요청을 보낼 수 있는 주체가 `X-Forwarded-For: 172.16.x.y`를 회전시켜 예산을 무한히
얻는다(S15P21E106-288 리뷰 B-3).

집계 단위도 함께 문제가 된다. 예산을 주소 하나 단위로 나누면 IPv6 클라이언트는 보통 `/64` 이상을
배정받으므로 주소만 바꿔 예산을 무한히 새로 얻는다. 반대로 IPv4는 NAT 뒤 공용 주소를 여러 사용자가
공유해 이미 한 예산을 나눠 쓴다. 두 방향이 서로 반대라 한 값으로 둘 수 없다.

## 결정

클라이언트 IP는 **신뢰 목록 안의 발신지가 보낸 `X-Real-IP`일 때만** 헤더에서 얻고, 그 밖에서 직접 온
요청의 헤더와 `X-Forwarded-For`는 무시한다. IP 단위 제한의 예산은 주소 하나가 아니라 **프리픽스 단위
버킷**으로 나눈다. IPv4는 `/32`, IPv6는 `/64`가 기본값이며, 값이 없거나 주소 리터럴이 아닌 요청은 한
버킷을 공유한다.

```yaml
server:
  forward-headers-strategy: native
  tomcat:
    remoteip:
      remote-ip-header: x-real-ip
      protocol-header: x-forwarded-proto
      host-header: ""
      port-header: ""
      internal-proxies: 127.0.0.0/8,::1/128,172.16.0.0/12
feelm:
  auth:
    client-ip:
      ipv4-prefix-length: 32
      ipv6-prefix-length: 64
```

- `native`는 Tomcat `RemoteIpValve`를 쓴다. 밸브는 신뢰 목록에 있는 발신지의 요청에서만 헤더를 읽는다.
- `X-Real-IP`를 읽는 이유는 Nginx가 그 헤더를 `$remote_addr`로 덮어써 **항목이 하나만 남기** 때문이다.
  클라이언트가 보낸 `X-Real-IP`는 Nginx에서 통째로 대체되므로 전달되지 않고, 맥락에 적은 "모든 항목이
  신뢰 대역일 때 맨 왼쪽 값" 경로가 생기지 않는다. `infra/` 파일을 바꾸지 않고 지금 성립한다.
- 신뢰 목록은 backend 컨테이너에 닿을 수 있는 경로로 좁힌다. 실제 판정은 Compose 브리지
  (`172.16.0.0/12`)가 전담하고, 루프백은 컨테이너 자기 헬스체크와 로컬·테스트 실행 경로다.
- `host-header`·`port-header`는 끈다. `native`는 XFF만 켜지 않고 밸브가 `X-Forwarded-Host`로
  `getServerName()`을 바꾸는데 Nginx는 그 헤더를 정리하지 않는다. 지금 요청에서 절대 URL을 만드는 코드는
  없지만, 생기면 조용히 결함이 된다.
- 프리픽스 길이의 허용 범위는 대역 전체가 아니라 결정 근거의 폭(IPv4 `/24`~`/32`, IPv6 `/48`~`/64`)이다.
  대역 전체를 허용하면 아래에서 기각한 값이 그대로 기동한다.
- `protocol-header`를 켠 결과로 `X-Forwarded-Proto: https`인 요청은 `isSecure()`가 참이 되고
  `getServerPort()`가 443이 된다. 현재 이 값을 읽는 코드는 없고 Refresh 쿠키의 `Secure`는 설정값이다.

Nginx 쪽 후속 정리는 S15P21E106-326에서 구성한다. 모든 backend 프록시 경로가
`X-Forwarded-For`도 `$remote_addr`로 덮어쓰고 `X-Forwarded-Host`·`X-Forwarded-Port`를 제거한다.
배포 환경에서는 Nginx와 backend가 공유하는 Compose 네트워크의 Nginx 주소가 신뢰 목록에 포함되는지
[`infra/README.md`](../../infra/README.md)의 절차로 확인한다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A (선택) `native` + 신뢰 목록 + `X-Real-IP` | Nginx가 이미 덮어써 보내는 헤더라 인프라 변경 없이 지금 적용된다. 항목이 하나뿐이라 좌우 평가 순서에 방어가 의존하지 않는다 | 표준 헤더가 아니고 Nginx 설정과 짝으로 유지해야 한다. 새 프록시 위치가 이 헤더를 세팅하지 않으면 조용히 프록시 IP로 집계된다 |
| B `X-Forwarded-For`를 현재 구성(이어 붙이기) 그대로 읽음 | 표준 헤더이고 프록시 체인이 남는다 | 항목이 모두 신뢰 대역이면 맨 왼쪽 값이 채택된다. Tomcat에 닿는 발신지가 전부 신뢰 대역인 이 구성에서 내부 주체가 예산 주체를 바꿀 수 있다 |
| C `X-Forwarded-For` + Nginx가 `$remote_addr`로 덮어쓰기 | 표준 헤더를 쓰면서 항목도 하나가 된다 | `infra/` 변경과 배포가 선행되어야 하고, 그때까지 B의 구멍이 열려 있다. S15P21E106-326의 후속 정리로 남긴다 |
| D `framework`(`ForwardedHeaderFilter`) | 서블릿 컨테이너에 독립적이다 | 신뢰할 프록시 목록 개념이 없어 발신지를 가리지 않고 헤더를 믿는다 |
| E 헤더를 계속 무시 | 추가 설정이 없다 | 지금 상태 그대로다. 전체 사용자가 IP 예산 하나를 공유한다 |
| F IPv6도 주소 단위(`/128`) | 정상 사용자를 가장 좁게 묶는다 | IPv6 클라이언트가 주소만 바꿔 예산을 새로 얻으므로 IP 축이 사실상 사라진다 |
| G IPv4도 넓은 프리픽스(예: `/16`) | 여러 주소를 쓰는 공격자를 함께 묶는다 | 무관한 사용자가 함께 걸리는 범위가 커진다. 공유 예산 문제는 한도 값에서 다루는 편이 낫다(S15P21E106-287) |
| H 파싱 실패 값을 원문 그대로 버킷으로 | 입력을 잃지 않는다 | 밸브는 항목이 IP인지 검증하지 않으므로 값을 조금씩 바꾸면 매번 새 예산이 생기고 Redis 키 개수도 무한이 된다. 프리픽스 표기를 그대로 보내면 실제 주소의 버킷과 해시 입력이 겹친다 |

## 결과

- **얻는 것**: Nginx 뒤에서 IP 단위 제한이 실제 클라이언트별로 동작한다(현재 결함의 수정). 애플리케이션
  포트에 직접 붙은 요청이 헤더로 예산 주체를 바꿀 수 없고, 내부 대역 주체의 좌측 항목 회전 경로도 닫힌다.
  IPv6 클라이언트가 주소를 바꿔 예산을 새로 얻는 우회가 막힌다. 클라이언트 IP를 쓰는 다른 기능도 같은
  판정을 공유한다.
- **감수하는 것**:
  - `X-Real-IP`는 표준 헤더가 아니다. Nginx의 프록시 블록이 이 헤더를 세팅해야 하고, 세팅하지 않는 새
    경로가 생기면 그 경로는 프록시 IP 하나로 집계된다. 조용히 나빠지는 방향이라 배포 시 확인이 필요하다.
  - 신뢰 목록이 배포 환경과 어긋나면 헤더가 무시되어 같은 상태가 된다. Nginx 컨테이너 대역 확인은
    S15P21E106-326에 있다.
  - 신뢰 목록의 사설 대역 안에서는 헤더를 믿는다. 그 대역에 접근할 수 있는 주체는 이미 backend 컨테이너에
    직접 요청할 수 있는 위치이므로 그 경계 안쪽은 네트워크 구성으로 지킨다.
  - 밸브의 신뢰 판정 자체(`NetMaskSet.contains`)는 내부적으로 `InetAddress.getByName`을 호출한다. 즉
    신뢰 발신지가 보낸 헤더에 호스트 이름이 있으면 그 단계에서 이름 조회가 일어난다. 애플리케이션 코드는
    이름 조회를 하지 않지만(`ClientIpBucket`이 직접 파싱한다) 밸브 단계까지 닫는 것은 Nginx가 헤더를
    덮어쓰는 구성이다.
  - NAT 뒤 공용 IPv4를 공유하는 사용자들은 계속 한 예산을 나눠 쓴다.
  - 값이 없거나 주소 리터럴이 아닌 요청은 모두 한 버킷의 예산을 나눠 쓴다.
  - Redis 키의 해시 입력이 IP 원문에서 버킷 표기로 바뀌어, 적용 시점에 진행 중이던 창의 카운터는 이어지지
    않고 만료로 사라진다. 롤링 배포 중에는 두 키 모양이 공존한다.
- **후속 작업**:
  - S15P21E106-326: 변경된 Nginx 설정을 적용한 뒤 배포 환경의 공유 네트워크 대역과 위조 헤더 요청을
    검증한다.
  - S15P21E106-312: 로그인 시도(API-004)에 IP 단위 제한을 추가할 때 같은 버킷과 같은 클라이언트 IP 판정을
    쓴다. 현재 정본 문서와 코드의 API-004에는 IP 축이 없다.
