# ADR-0018: Kafka 이벤트는 폴링 기반 트랜잭셔널 아웃박스로 발행한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-09-07 |
| 결정자 | 팀 확정, S15P21E106-147에서 기록 |
| 관련 | NFR-05, NFR-06, S15P21E106-147, S15P21E106-148, ADR-0017 |

## 맥락

Spring Boot는 평가·온보딩·사용자 행동을 PostgreSQL에 저장한 뒤 Kafka로 알려야 한다.
PostgreSQL과 Kafka는 하나의 원자적 트랜잭션에 참여하지 않으므로 DB 커밋 뒤 프로세스가
종료되거나 Kafka가 실패하면 추천 시스템이 변경을 영구히 알지 못할 수 있다. 반대로 Kafka
상태를 사용자 요청 성공 조건으로 삼으면 추천 파이프라인 장애가 평가·검색 등 서비스 기능으로
전파된다.

현재 Spring Boot 실행 인스턴스는 하나이고 구버전과 신버전이 동시에 동작하는 롤링·블루그린
배포를 사용하지 않는다. Jira 148에서도 아웃박스 발행 작업자는 하나만 실행할 예정이다.
Kafka Connect·Debezium과 별도 모니터링·알림 시스템은 도입되어 있지 않다. Kafka는 단일
Broker, 복제 계수 1로 운영한다. 이벤트 계약은 `eventId`를 멱등 처리 기준으로 정하고,
강한 신호는 Consumer가 PostgreSQL 최신 상태를 다시 읽도록 한다.

## 결정

모든 Kafka 이벤트는 Spring의 단일 폴러가 처리하는 트랜잭셔널 아웃박스를 통해
at-least-once로 발행한다. 순서 변경과 장기 지연이 Consumer에 미치는 영향을 감수하고,
Consumer는 아래 기준에 따라 중복과 지연 이벤트를 처리한다.

- 도메인 데이터와 완성된 이벤트 JSON을 같은 PostgreSQL 트랜잭션으로 저장한다.
- 아웃박스는 DB 내부 `bigint` PK와 외부 멱등 기준인 UUID `eventId`를 분리한다.
- 발행기는 저장된 Topic, Long 파티션 키와 JSON을 다시 구성하지 않고 그대로 전송한다. 사용자 이벤트의 키는 userId, `PARTY_REFRESH`는 partyId다.
- 상태는 `PENDING`과 `PUBLISHED`만 사용한다. 실패는 `PENDING`을 유지한 채 시도 횟수,
  최근 오류와 다음 시도 시각으로 나타낸다.
- Kafka 성공 응답을 확인한 뒤에만 `PUBLISHED`로 변경한다. Kafka 응답을 기다리는 동안에는
  DB 트랜잭션을 유지하지 않는다.
- 한 이벤트의 실패가 다른 이벤트를 막지 않는다. 다만 `PARTY_REFRESH`는 같은 파티의 앞선
  이벤트가 Kafka 성공 응답을 받고 `PUBLISHED`로 기록될 때까지 후속 이벤트의 발행을 보류한다.
  다른 파티와 사용자 이벤트는 계속 발행한다. 앞선 파티 이벤트가 장기 실패하면 그 파티의
  후속 계산도 지연된다.
- 현재는 단일 `fixedDelay` 폴러가 이전 실행의 발행 결과와 DB 갱신을 모두 끝낸 뒤 다음
  실행을 시작한다. 여러 작업자의 선점을 위한 `PROCESSING`과 lease는 두지 않는다.
- 최종 `FAILED` 상태와 최대 재시도 횟수는 두지 않는다. 별도 알림이 없는 상태에서 재시도를
  중단하면 사실상 영구 미발행이 될 수 있기 때문이다.
- 완료된 이벤트만 `published_at`을 기준으로 정리하며 `PENDING`은 나이로 삭제하지 않는다.

초기 설정값은 폴링 500ms, 배치 100건, 재시도 간격 1·2·4·8·16초 뒤 최대 30초와 약 ±20% 편차,
완료 이벤트 보관 7일이다. 폴링 간격은 설정으로 조정할 수 있게 하고, 별점 저장부터 갱신된 추천
후보 조회까지의 지연을 측정해 최종값을 결정한다. 나머지 초기값도 이벤트량과 운영 지표를 측정한
뒤 조정한다.

Producer는 `acks=all`과 멱등 발행을 사용한다. 한 발행 작업의 전체 제한 시간은 5초를
초기값으로 두고, 이를 넘는 장애는 아웃박스 재시도가 담당한다. 단일 Broker이므로
`acks=all`도 Broker 또는 디스크 자체 손실을 막지는 못한다.

## 발행 성공과 실패의 경계

```text
사용자 요청
  DB 트랜잭션: 도메인 데이터 저장 + PENDING 이벤트 저장

별도 폴러
  짧은 DB 조회
  → DB 트랜잭션 종료
  → Kafka 발행과 Broker 응답 대기
  → 성공·실패별 짧은 DB 갱신
```

Kafka에는 기록됐지만 `PUBLISHED` 갱신 전에 애플리케이션이 종료되면 같은 `eventId`가 다시
발행될 수 있다. DB와 Kafka 사이의 이 불확실성은 `PROCESSING` 상태로 제거할 수 없으므로
Consumer가 중복을 견뎌야 한다.

## 아웃박스 데이터 기준

아웃박스에는 다음 정보를 저장한다.

| 분류 | 필드 |
|---|---|
| 식별·전송 | `id`, `event_id`, `event_type`, `topic`, `partition_key`, `message` |
| 상태·재시도 | `status`, `attempt_count`, `next_attempt_at`, `last_attempt_at`, `last_error` |
| 수명 | `created_at`, `published_at` |

`message`는 전체 도메인 데이터의 복사본이 아니라 실제 Kafka 이벤트 한 건이다. RATING과
ONBOARDING은 기존 계약의 변경 요약만 담고 Python Consumer가 사용자 최신 상태를 다시
조회한다. VIEW와 클릭처럼 행동 자체가 집계 입력인 신호는 처리에 필요한 값을 담는다.

DB는 사용자 이벤트에 공통 봉투의 필수 필드와 JSON 객체 여부,
`message.eventId = event_id`, `message.eventType = event_type`,
`message.userId = partition_key`를 검사한다. `PARTY_REFRESH`는 계약 §4.3의 전용 JSON을
사용하므로 topic과 `message.partyId = partition_key`, `inputId`·`members`의 존재 및
필드 집합을 별도 CHECK 분기로 검증한다. 이벤트별 세부 payload 규칙은 애플리케이션에서 검증한다.

### 테이블 구조

| 컬럼 | PostgreSQL 타입 | Null | 역할 |
|---|---|---|---|
| `id` | `bigint GENERATED BY DEFAULT AS IDENTITY` | 불가 | DB 내부 PK와 동일 조회 조건의 순서 기준 |
| `event_id` | `uuid` | 불가 | 사건의 외부 식별자이자 Consumer 멱등 기준 |
| `event_type` | `varchar(30)` | 불가 | 이벤트 종류 |
| `topic` | `varchar(249)` | 불가 | 저장 당시 결정한 Kafka Topic |
| `partition_key` | `bigint` | 불가 | Kafka key인 `userId` 또는 `PARTY_REFRESH`의 `partyId` |
| `message` | `jsonb` | 불가 | Kafka로 보낼 완성된 사용자 이벤트 봉투 또는 파티 refresh 전용 JSON |
| `status` | `varchar(20)` | 불가 | `PENDING` 또는 `PUBLISHED` |
| `attempt_count` | `integer` | 불가 | 지금까지의 발행 시도 횟수 |
| `next_attempt_at` | `timestamptz` | 불가 | 다음 발행 가능 시각 |
| `last_attempt_at` | `timestamptz` | 가능 | 최근 발행 시도 시각 |
| `last_error` | `text` | 가능 | 최근 발행 실패 원인 |
| `created_at` | `timestamptz` | 불가 | 아웃박스 생성 시각 |
| `published_at` | `timestamptz` | 가능 | Kafka 성공 응답 확인 시각 |

`event_id`는 유일해야 하고 `attempt_count`는 0 이상이어야 한다. `status`는 두 허용값만
저장한다. 사용자 이벤트 `message`는 JSON 객체이고 `eventId`, `eventType`, `occurredAt`,
`userId`, `payload`를 가져야 하며 `payload`도 객체여야 한다. 중복 저장한 `eventId`,
`eventType`, `userId`는 바깥 컬럼과 일치해야 한다. `PARTY_REFRESH`만 전용 JSON 예외를
적용하고 아웃박스 `event_id`는 전송 본문 밖에서 보존한다.

폴러는 `status = 'PENDING' AND next_attempt_at <= now()`를 `next_attempt_at, id` 순서로 최대
100건 조회한다. `PARTY_REFRESH`는 같은 `partition_key`에 더 작은 `id`의 `PENDING` 이벤트가
있으면 조회 대상에서 제외한다. 이를 위해 `(next_attempt_at, id) WHERE status = 'PENDING'`
부분 인덱스를 둔다. 같은 파티의 선행 요청 확인에는
`(partition_key, id) WHERE event_type = 'PARTY_REFRESH' AND status = 'PENDING'`
부분 인덱스를 사용한다.
완료 정리는 `PUBLISHED`와 `published_at`만 기준으로 하며 오래된 `PENDING`은 삭제하지 않는다.

### JSON을 그대로 발행하는 이유

Publisher는 `message`를 현재 이벤트 DTO로 역직렬화하거나 PostgreSQL 최신 값으로 다시 만들지
않는다. 재시도 사이에 코드나 도메인 데이터가 바뀌어도 처음 저장한 사건의 `eventId`와 내용이
달라지지 않게 하기 위해서다. 이벤트 계약 자체를 변경할 때의 호환성과 배포 순서는 Producer와
Consumer 담당자가 별도로 합의하며 Jira 147에서 미리 새로운 버전 정책을 확정하지 않는다.

## Producer 초기 설정

Producer 내부 재시도는 한 번의 발행 작업 안에서 짧은 네트워크 오류를 흡수하고, 정해진 시간
안에도 실패하면 아웃박스 재시도가 장기 장애와 애플리케이션 재시작을 담당한다.

| 설정 | 초기값 | 판단 근거 |
|---|---:|---|
| `acks` | `all` | Broker 저장 성공을 확인한 뒤 완료로 판단 |
| `enable.idempotence` | `true` | 같은 Producer 세션의 내부 재시도 중복 감소 |
| `delivery.timeout.ms` | `5000` | 내부 재시도를 포함한 한 발행 작업의 상한 |
| `request.timeout.ms` | `3000` | 개별 Broker 요청 대기 제한 |
| `max.block.ms` | `3000` | 메타데이터·버퍼 대기로 호출이 장시간 막히는 상황 제한 |
| `max.in.flight.requests.per.connection` | `5` | 멱등 Producer 조건을 지키면서 제한된 병렬 전송 허용 |
| `retries` | 별도 지정하지 않음 | 시도 횟수보다 `delivery.timeout.ms`로 전체 시간을 제한 |
| key serializer | `LongSerializer` | 사용자 이벤트는 `userId`, 파티 refresh는 `partyId`를 key로 전달 |
| value serializer | `StringSerializer` | 저장된 JSON을 이중 직렬화하지 않고 전송 |

여러 Kafka 레코드를 하나의 Kafka 트랜잭션으로 묶는 요구가 없고 Kafka 트랜잭션으로
PostgreSQL과의 원자성을 만들 수도 없으므로 `transactional.id`는 사용하지 않는다. 멱등
Producer는 같은 실행 안의 Producer 재시도 중복을 줄일 뿐, Kafka 성공 뒤 DB 완료 갱신 전에
프로세스가 종료되어 새 Producer가 재발행하는 경우까지 제거하지 않는다.

## 순서와 Consumer 영향

Kafka는 같은 Topic·Partition에 Producer가 실제로 기록한 순서를 유지한다. 그러나 앞서 발생한
아웃박스 이벤트가 실패하고 뒤 이벤트가 성공하면 사건 발생 순서와 Kafka 기록 순서는 달라질
수 있다. 사용자 이벤트는 앞 이벤트가 성공할 때까지 같은 사용자의 이후 이벤트를 막지 않는다.
`PARTY_REFRESH`는 같은 파티의 앞선 이벤트를 Kafka에 기록하고 아웃박스 `PUBLISHED`로
확정하기 전에는 후속 이벤트를 발행하지 않는다. 이 규칙은 Kafka 기록 순서까지 보장한다.
현재 Spark 파티 작업은 배치 내부 offset 정렬을 하지 않으므로 배포 시
`--max-records-per-trigger 1`로 배치당 입력을 한 건으로 제한한다. 이 설정은 전체 파티
처리량을 낮추므로 운영 지연을 측정한다. Kafka 순서대로 Redis 결과가 게시되는지는 연동 검증한다.

- RATING·ONBOARDING은 PostgreSQL 최신 상태를 다시 읽으므로 최종 상태보다 중복 계산 비용이
  주된 영향이다.
- VIEW·클릭 등 시간 기반 집계는 `occurredAt`을 사용한다.
- 장기 지연된 약한 신호가 Spark watermark 밖으로 밀릴 수 있으며, Consumer는 이벤트 시간과
  중복 판정 창을 기준으로 이를 처리한다. 구체적인 허용 지연과 판정 창은 실측 후 조정한다.

중복 처리도 신호에 따라 책임이 다르다.

- `RATING`·`ONBOARDING`은 매번 PostgreSQL의 최신 전체 상태로 다시 계산하므로 자연 멱등이다.
- `DISMISS`·`VIEW`·`RECOMMENDATION_CLICK`·`OTT_CLICK`은 누적값이 부풀 수 있어 Consumer가
  `eventId`로 중복 제거한다.
- 현재 계약의 중복 판정 창을 벗어난 재발행은 약한 신호를 소폭 부풀릴 수 있다. 이 위험은
  아웃박스의 영구 유실 방지를 우선하기 위해 감수하며 운영 지표를 바탕으로 판정 창을 조정한다.

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 폴링 기반 트랜잭셔널 아웃박스 (선택) | 현재 Spring·PostgreSQL 범위에서 영속 복구 가능 | 폴링 지연, 테이블 운영, 중복 처리 필요 |
| DB 커밋 뒤 직접 비동기 발행 | 구현이 단순하고 지연이 작음 | 종료·장기 장애 뒤 복구할 영속 기록 없음 |
| DB 커밋 뒤 동기 발행 | 요청 시점에 결과 확인 가능 | Kafka 장애가 API 지연·실패로 전파되고 이중 쓰기 간격은 남음 |
| DB·Kafka 트랜잭션 동기화 | 프레임워크가 커밋 순서를 관리 | 두 시스템의 원자적 커밋은 아니므로 실패 방향만 바뀜 |
| Debezium CDC 아웃박스 | 애플리케이션 폴러 없이 변경 로그 기반 전달 | 현재 없는 Connect·Debezium 운영 범위가 추가됨 |
| `PROCESSING`과 lease | 다중 폴러의 원자적 선점 가능 | 현재 불필요한 DB 쓰기와 고립 행 복구가 생기며 근본 중복은 남음 |
| 최종 `FAILED` 격리 | 반복 실패 부하 제한 | 알림·재처리 절차가 없어 조용히 방치될 수 있음 |

## 구현 검증 기준

| 상황 | 기대 결과 |
|---|---|
| 도메인 저장 또는 아웃박스 저장 실패 | 두 저장이 함께 롤백된다 |
| Kafka 연결 불가 | 사용자 기능은 성공하고 이벤트는 `PENDING`에 남는다 |
| 일부 이벤트만 발행 실패 | 성공 건만 `PUBLISHED`, 실패 건은 독립적으로 백오프한다 |
| Kafka 성공 뒤 완료 갱신 실패 | 같은 `eventId`와 메시지로 재발행할 수 있다 |
| 애플리케이션 재시작 | 기존 `PENDING`을 자동으로 다시 조회한다 |
| Broker 복구 | 별도 수동 변경 없이 밀린 이벤트를 발행한다 |
| 완료 이벤트 정리 | 보관 기간이 지난 `PUBLISHED`만 삭제하고 `PENDING`은 보존한다 |

구현 MR은 로컬 Kafka에서 Topic, `userId` key와 JSON value를 확인한다. PostgreSQL 통합
테스트에서는 도메인 데이터와 아웃박스의 원자성, 공통 봉투 제약, 폴링 대상과 재시도 시각을
검증한다. Kafka 성공 뒤 DB 갱신 전 종료처럼 재현 시점이 짧은 장애는 발행 성공 뒤 완료 갱신을
실패시키는 테스트 대역으로 검증한다.

모니터링 도입 전에는 `PENDING` 건수, 가장 오래된 생성 시각, 최대 시도 횟수와 최근 오류를
DB에서 수동 확인한다. 기본 오류 로그에는 `eventId`, `eventType`, Topic, 시도 횟수와 다음 시각을
남기고 사용자 행동이 포함될 수 있는 `message` 전체는 기록하지 않는다. 아웃박스 적체만으로
애플리케이션 전체 Health를 `DOWN`으로 만들지는 않는다.

## 결과

- **얻는 것**: 도메인 커밋과 발행 대상 기록의 원자성, Kafka 장애·재시작 후 자동 복구,
  사용자 기능과 추천 파이프라인 장애의 분리, 도메인별 발행 정책 통일
- **감수하는 것**: at-least-once 중복, 일시적인 추천 지연과 일부 순서 변경, 폴링·정리 비용,
  알림이 없어 수동으로 적체를 확인해야 하는 운영 위험
- **후속 작업**: S15P21E106-148과 후속 구현 업무에서 DB migration, 공통 이벤트 저장과 Kafka relay를 MR 크기 기준에 맞게
  분리한다. 다중 인스턴스가 도입되면 lease 기반 선점을 재검토하고, 모니터링 도입 뒤에는
  최종 실패 격리와 운영자 재처리 절차를 검토한다.
