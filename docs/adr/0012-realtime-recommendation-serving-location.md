# ADR-0012: 실시간 추천 서빙 계산(Fold-in·재정렬·파티 집계·XAI)은 FastAPI 서비스에서 수행한다

| 항목 | 값 |
|---|---|
| 상태 | 채택 |
| 결정일 | 2026-08-31 |
| 결정자 | 팀 확정, 기록 박시현(BE). AI·인프라 담당과 세부 경계 협의 예정 |
| 관련 | A-12, ERD D-4, NFR-04, NFR-05, API-040, API-045, API-058, README 7장 미확정 사항 |

## 맥락

ALS 학습은 PySpark 배치(ADR-0001)로 하고 산출물(Item Factor, 후보)은 언어 중립 형식으로 저장된다. 그러나 평가 직후 추천 갱신(Fold-in), 파티 조합별 집계, 추천 이유 생성은 **요청 시점**에 계산해야 하며 Spark를 요청마다 띄울 수 없다. 이 계산을 Java(Spring)에서 할지 Python(FastAPI)에서 할지가 쟁점이다. 계산 자체(벡터 내적, 작은 선형방정식)는 두 언어 모두 가능하므로 기준은 (a) 시놉시스 임베딩·LLM 설명 등 Python 전용 라이브러리 사용 계획, (b) 추천 로직을 AI 담당이 Python으로 계속 수정·운영하는지다.

## 결정

실시간 서빙 계산(Fold-in·재정렬·파티 집계·XAI)을 **FastAPI 서비스로 분리**하고 Spring Boot는 내부 API로 호출한다. FastAPI는 기동 시 Item Factor를 메모리에 올려 두고 요청 시 numpy 수준의 계산으로 응답하며, 장애 시 Spring은 추천 API만 `503`을 반환하고 영화·검색·평가 기능은 유지한다(NFR-05).

## 고려한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| FastAPI 분리 (선택) | AI 담당이 자기 언어로 서빙 코드 소유, Python 라이브러리 사용 가능, NFR-04·05 프로세스 분리 | 배포 단위·내부 API 계약 추가, 요청 홉 1개, EC2 자원 재배분 |
| Spring Boot 통합 | 배포 1개, 내부 API 없음, 트랜잭션과 캐시 무효화 일원화 | 추천 로직 이중 구현(Python 배치 ↔ Java 서빙), Python 전용 라이브러리 사용 불가 |
| 배치 결과만 서빙(실시간 계산 없음) | 가장 단순 | 평가 즉시 반영·파티 추천·신규 사용자 개인화 불가 — FR-10/12/22 약화 |

## 결과

- **얻는 것**: 추천 로직 단일 소유, 라이브러리 자유
- **감수하는 것**: 배포·운영 복잡도, 내부 API 계약 문서, 장애 격리 구현(FastAPI 장애 시 추천 API만 503)
- **후속 작업**: 내부 API 명세 초안(S15P21E106-111)·README 7장 갱신(S15P21E106-117) 진행 중, ERD `taste_analyses` 갱신 주체는 내부 API 협의에서 확정
