# Pipeline AGENTS.md

루트 `AGENTS.md`의 공통 절차를 전제로, `pipeline/`에서 작업하는 AI 코딩 도구가
따라야 할 작업 절차를 정의한다.

## 1. 기준 문서

- HDFS 경로·Parquet 스키마·ID 매핑·모델 산출물: `pipeline/contracts/`
- 서비스 경계: `docs/api/`, `docs/erd.md`
- 아키텍처: `docs/adr/`의 채택된 ADR
- 요구사항: `docs/requirements.md`
- 실행·재현 방법: `pipeline/README.md`와 변경 영역의 `README.md`

`pipeline/docs/`의 연구 자료는 명시적으로 승격되지 않은 계약을 확정하지 않는다.
`pipeline/contracts/`는 내부 교환 계약의 기준이며 API·DB·ADR을 덮어쓰지 않는다.
영역이 겹치거나 계약과 구현이 다르면 임의로 진행하지 않고 합의한다.

Spark와 Consumer는 독립 실행 단위다. 서로의 코드·의존성을 공유하지 않고
`pipeline/contracts/`로 연결한다. 정확한 런타임은 `pipeline/README.md`를 따른다.

## 2. 검증

변경한 실행 단위와 검증 계층에 맞는 명령을 사용한다.

- Spark: `pipeline/spark/`에서 `uv run pytest`, `uv run ruff check .`
- Consumer: `pipeline/consumer/README.md`와 Consumer 자체 프로젝트의 명령
- 문서·주석 전용 변경: 링크·명령·diff를 검증한다.

로컬·합성 fixture 검증은 HDFS 권한·네트워크·분산 실행·재시도를 입증하지
않는다. 실환경 검증은 환경·산출물 버전, 명령, 결과, 실패 정리·재시도와
미검증 범위를 따로 남긴다. Secret·실제 URI·내부 주소는 기록하지 않는다.

## 3. 적용 범위

변경이 닿는 범위에 따라 세 단계 중 하나를 적용한다. 섞이면 가장 높은 단계를 따른다.
기본·게이트 단계의 판정과 근거는 플랜 상단 판정란에 적고, 플랜을 만들지 않는 검증만
단계의 판정과 근거는 시작 보고와 MR에 적는다.

| 단계 | 조건 | 적용 |
| --- | --- | --- |
| 검증만 | 문서·주석 전용 변경 또는 생산 동작·계약을 바꾸지 않는 테스트 코드만 변경 | 2장 검증. 예외 근거를 시작 보고와 MR에 남긴다 |
| 기본 | 아래 트리거에 해당하지 않음 | 4장의 산출물과 완료 기준을 한 세션에서 충족한다. 게이트 없음 |
| 게이트 | 아래 트리거 중 하나 이상 | 4장의 산출물과 완료 기준에 더해 두 게이트를 거친다 |

트리거. diff 또는 플랜에 하나라도 있으면 해당한다.

- `pipeline/contracts/`, `docs/api/`, `docs/erd.md`, 채택된 ADR의 변경 또는 그 계약과 다른 구현
- HDFS 경로, Parquet 스키마, ID 매핑 또는 모델 산출물 형식·수명 주기의 신설·변경
- 학습·검증·테스트 분할, 데이터 제외·중복, 지표 분모 또는 후보 생성 의미의 변경
- 실제 HDFS·분산 클러스터 검증 또는 Kafka·Redis를 포함한 외부 시스템 읽기·쓰기
- 재시도·멱등성·부분 실패 처리 또는 임시·부분 산출물의 게시·정리 방식 변경
- `pipeline/spark/common/`, 다른 담당자 소유 영역, `pipeline/spark/pyproject.toml`,
  `pipeline/spark/uv.lock`, `pipeline/configs/`, `.env.example` 또는 환경 변수 계약

## 4. 작업 절차와 게이트

기본·게이트 단계에서 AI는 플랜, 구현, 리뷰 세 단계의 산출물을 남기고 각 완료 기준을
충족한다. 산출물은 다음 단계가 Jira 요구사항, 기준 문서, 저장소 상태와 함께 작업을
재현할 수 있을 정도로 작성한다. 검증만 단계는 2장 검증만 수행하며 이 산출물을 만들지
않는다. 동일 worktree를 여러 작업자가 동시에 수정하지 않는다.

1. **플랜** — 루트 `plans/<Jira-Key>.md`. 설계, 미확정 항목, 기준선(시작 커밋과 기존
   미커밋 변경·새 파일), 3장 판정과 트리거, 열리는 리뷰 게이트, 계약 영향·합의, 인수 테스트
   목록을 적는다. 인수 테스트마다 테스트 이름, 전제·입력, 기대 결과인 산출물·오류·상태
   변화를 명시하고 로컬·클러스터·HDFS 검증 계층을 구분한다. 테스트로 확인할 수 없는 변경은
   대체 검증과 통과 조건을 둔다. 완료 기준: 모든 동작에 테스트 또는 대체 검증이 대응하고,
   계약·공용 파일 영향이 팀과 합의되어 있다.
2. **구현** — 인수 테스트를 만족하는 최소 변경을 작성한다. 완료 기준: 플랜의 인수 테스트가
   모두 존재하고 통과하며 2장의 해당 검증이 성공한다. 플랜 목록 대비 테스트의 추가·삭제·
   기대값 변경과 플랜 이탈은 사람 확인 후 플랜에 기록한다. 테스트를 약화하지 않는다.
3. **리뷰** — 루트 `plans/<Jira-Key>-review.md`. 변경 단위마다 diff와 그 단위가 참조하는
   계약 절만 읽고 다음 관점을 한 번에 적용한다. Secret·개인정보·내부 주소 점검은 diff 전체에
   한 번, 단위 간 계약과 산출물 정합성은 마지막에 한 번 본다.
   - HDFS·Parquet·ID·모델 산출물·API·DB 계약 정합성
   - 데이터 누수, 분할, 제외·중복·분모·후보 생성을 포함한 지표 정확성
   - 분산 실행, 부분 실패, 재시도, 멱등성과 임시·부분 산출물 정리
   - 테스트 실효성과 로컬·실환경 검증 범위, Secret·개인정보·내부 주소 노출
   측정 칸에는 읽은 기준 문서 절 수, 열린 게이트와 MR 리뷰에서 뒤늦게 발견된 누락(병합 후)을
   적는다.

리뷰 편성은 3장 단계에 따른다.

- **기본 단계(W1)**: 리뷰어 한 명이 위 관점을 한 세션에서 모두 적용한다.
- **게이트 단계(W2)**: 두 세션이 같은 대상을 독립으로 리뷰한다. A는 위 관점 그대로 보고,
  B는 변경이 목적을 달성하지 못하는 경우를 찾는다. B는 결함 발견 여부와 관계없이 인수
  테스트마다 데이터 경계·교차 실행·부분 실패·재시도 시나리오와 결과를 리뷰 템플릿의
  공격 시도 기록에 남긴다. 열린 트리거는 구체적인 입력 또는 실행 순서로 결함을 내거나
  결함이 없음을 보인다. A와 B는 각각 루트 `plans/<Jira-Key>-review-A.md`와
  `-review-B.md`에 쓰고 서로의 리뷰 파일을 읽지 않는다. 반영 전에 두 결과를 합집합으로
  `plans/<Jira-Key>-review.md`에 모아 A-n/B-n 번호를 유지한 채 채택·기각·후속을 표시한다.
  이 대조표는 AI가 만들고 사람은 갈래가 있는 항목만 판단하며, 반영은 채택 목록만 고친다.

게이트 단계에서는 두 지점에서 사람이 개입한다. 게이트는 자동 검증이 부족한 동안의 대체
장치다. 게이트 단계 MR 5건 연속으로 사후 누락이 0이면 분리 리뷰의 완화를, 기본 단계 MR에서
사후 누락이 나오면 트리거 확대를 검토한다.

- **플랜 승인**: 플랜 완료 후 사람이 확인하고 승인·수정 지시를 플랜에 추기한 뒤 구현을
  시작한다.
- **분리 리뷰**: 리뷰는 구현과 다른 세션에서 플랜·diff·기준 문서만 보고 수행한다.

## 5. 플랜과 기록

- 기본·게이트 단계의 플랜과 리뷰 결과는 커밋하지 않는다. MR 본문에 플랜 요약, 플랜 대비
  변경점과 리뷰 결과, 로컬·실환경 검증을 요약한다. 검증만 단계는 시작 보고와 MR에 판정·
  근거와 2장 검증 결과를 남긴다.
- 기본·게이트 단계의 플랜과 리뷰 파일은 `pipeline/templates/plan.md`와
  `pipeline/templates/review.md` 양식으로 작성하고 측정 칸을 비워 두지 않는다.
- 리뷰 파일의 측정 칸과 플랜의 인수 테스트 목록은 MR 본문 "검증" 절에 옮겨 적는다.
- 세션은 해당 Jira의 worktree 디렉터리에서 시작한다.
- 프로젝트 수준 결정은 `docs/adr/`로 승격한다.
- 미래 작업에 필요한 사실을 플랜이나 MR 본문에만 남기지 않는다. 계약, 아키텍처, 요구사항과
  재현 방법 변경은 반드시 해당 기준 문서에 반영한다.
