# 644 GBT 이미지와 운영 실행 연결

표준 Consumer 이미지에 v26의 고정 CPU 런타임을 포함하고 기존 개인·파티 실행 명령을
환경 설정으로 GBT에 연결한다. 모델 원점수·개인 Top500·파티 집계·이벤트/Redis 계약은 바꾸지 않는다.
운영 서버 변경, HDFS 게시, 모델 포인터 변경과 전체 재게시는 이 구현에 포함하지 않는다.
실행 결과·실번들 대조·미검증 범위는 [644 검증 기록](GBT-644-VERIFICATION.md)에 있다.

## 실행 선택

`infra/compose/distributed.yml`은 아래 공용 설정을 개인·파티 컨테이너에 함께 전달한다.
기존 `feelm-foldin-consumer`와 `python -m feelm_consumer.party_main` 명령을 그대로 사용한다.

| 변수 | 의미 |
| --- | --- |
| `CONSUMER_RUNTIME` | `legacy`(미설정 기본값) 또는 `gbt`. 다른 값은 시작 실패 |
| `CONSUMER_GBT_BUNDLE_URI` | GBT에서 필수. 626의 검증된 불변 로컬/HDFS bundle URI |
| `CONSUMER_GBT_SERVING_REVISION` | GBT에서 필수. 독립 검증한 `sha256:<manifest 64 hex>` |
| `CONSUMER_GBT_MAX_SNAPSHOT_BYTES` | GBT에서 필수. 개인 writer·파티 reader에 같은 1~67,108,864 byte 예산 |
| `CONSUMER_GBT_SNAPSHOT_RETENTION_SECONDS` | 개인 GBT에서 필수. 이전 세대 입력 보존 기간, 1~2,147,483,647초 |

GBT 환경 선택은 개인의 기존 `--publish-live` 경로를 사용한다. 기본 shadow로 잘못 실행되어
서비스 후보를 갱신하지 않는 상황을 막는다. 독립 `--gbt-bundle ...` CLI는 종전 의미를 유지하므로
개인의 shadow 검증은 별도 `gbt-shadow-*` group으로 실행할 수 있다. CLI와 운영 환경 설정을 섞지 않는다.

기존 DB/Redis/Kafka 연결·topic/group 설정을 재사용한다. 파티에 DB 연결을 추가하지 않는다.
GBT는 ALS model/mapping/metadata 없이 실행된다. 최초 전환 환경에서는 개인·파티의 기존
ALS URI를 제거한다. `CONSUMER_GROUP_URI`와 `CONSUMER_DISCOVERY_POPULARITY_URI`는
발견 추천에서 계속 필요하며 둘을 함께 유지한다. 두 번들의 매핑과 새 GBT catalog를 검증한다.

필수 GBT 값 누락·잘못된 revision/예산·한쪽만 설정된 발견 번들은 실패하며 ALS로 우회하지 않는다.
로그의 `consumer runtime selected role=personal mode=GBT`와 `role=party mode=GBT`는 선택 증거다.
이 로그만으로 bundle 로딩이나 Redis 게시 성공을 판단하지 않는다.

## 이미지·로컬 검증

Python3.12, NumPy2.4.6, PyArrow19.0.1, SciPy1.15.2, XGBoost CPU2.1.4를 잠근다.
XGBoost CPU wheel의 native 라이브러리를 사용하고 Spark/pandas/GPU 패키지를 추가하지 않는다.
builder와 최종 runtime 단계에서 실제 XGBoost import를 실행해 native dependency 누락을 탐지한다.
최종 이미지는 비root이며 기존 Java/libhdfs 검사를 유지한다. 모델·catalog는 이미지에 복사하지 않는다.

```bash
docker build --target test -t feelm-consumer-gbt-test pipeline/consumer
docker build -t feelm-consumer-gbt-runtime pipeline/consumer
python -m unittest infra.scripts.test_verify_consumer_e2e infra.scripts.test_consumer_distributed_deployment
```

Consumer 계산 결과→로컬 fixture 검사는 Consumer 테스트에 있고, Consumer→Backend fixture 동일성은
main의 기존 `consumer-test`가 실행하는 `test_verify_consumer_e2e`에서 반드시 검사한다.
infra MR은 `infra/`와 `.gitlab/`만 받으므로 이 모듈의 `VerifyConsumerE2ETest`만 실행한다.
교차 fixture용 `ConsumerBackendFixtureContractTest`는 전체 checkout의 main 검사에서 실행되며,
fixture가 없거나 서로 다르면 실패한다. 파일 부재를 이유로 skip하지 않는다.
Backend의 두 fixture만 변경된 main push에도 `consumer-test`가 실행된다.
테스트 이미지는 검증 도구를 포함하지만 runtime에는 테스트·도구·연구 데이터가 들어가지 않는다.
실제 DB/Kafka/Redis에 연결하지 않는 테스트는 실서버 종단 검증을 대신하지 않는다.

## 입력 캐시 용량

`tools/measure_gbt_snapshot_size.py`는 합성 입력만 만들어 K별 canonical JSON byte를 출력한다.
실제 평가나 사용자 ID를 읽지 않는다. 실행 방법:

```bash
PYTHONPATH=pipeline/consumer/src python pipeline/consumer/tools/measure_gbt_snapshot_size.py
```

이번 합성 측정(9자리 영화 ID, 실제 평가만, 고정 길이 metadata)의 결과:

| K | 입력 JSON bytes |
| --- | ---: |
| 0 | 383 |
| 1 | 449 |
| 10 | 1,061 |
| 100 | 7,181 |
| 8,518 | 579,605 |
| 100,000 | 6,800,381 |

현재 입력은 TTL이 없고 새 세대가 게시되면 이전 입력에만 보존 시간이 붙는다(627 계약).
파티는 요청된 세대의 입력이 필요하므로 보존 시간은 Kafka 지연·재시도·파티 처리 시간을 포함해 정한다.
최대 입력 byte는 저장 허용 한도이지 메모리 예약량이 아니다.

예산 계산은 `현재 사용자별 입력 bytes 합 + 보존 시간 동안 교체된 입력 bytes 합`을 기반으로 한다.
여기에 Redis key/object overhead, input-current/state/candidates, 파티 결과와 기존 서비스 키를
더해야 한다. 관심없음·감상 목록, ID 자릿수와 메타데이터 길이에 따라 실제 크기가 달라진다.
운영 사용자 수·갱신률과 `MEMORY USAGE` 측정 없이 특정 TTL/byte 값이나 증설을 확정하지 않는다.

## 인프라 담당자 인계와 첫 전환

1. 검증한 이미지 digest와 626 bundle URI/revision, 발견 번들 두 URI를 준비한다.
   이 변경의 `ci-consumer-mr-boundary.py`에는 검토 대상 pyproject/lock/Dockerfile의 새 고정 해시가
   포함된다. 인프라 담당자가 diff를 검토한 뒤 기존 Consumer CI 절차로 서버의 root-owned boundary를
   적용해야 새 MR archive를 허용한다. 저장소 파일 변경만으로 설치된 정책이 바뀌지 않는다.
   기존 PyPI/파일 hash 검증·격리 네트워크 정책을 유지하고 새 잠금 의존성 설치를 확인한다.
2. 동일 릴리즈의 개인627·파티747·Backend742가 포함됐는지 확인하고 위 필수 환경 값을 검토한다.
   먼저 격리 환경에서 ALS 파일 없이 두 GBT 실행 경로와 실제 후보 소비를 확인한다.
3. 628/735의 승인된 전환 절차에서 기존 writer를 정리하고 model pointer, 개인 상태/입력/Candidate,
   파티 요청과 전체 사용자 재게시를 함께 조율한다. 이 문서는 그 절차를 자동 실행하지 않는다.
4. 활성 환경의 `CONSUMER_RUNTIME=gbt`와 공용 bundle/revision/budget을 적용한다.
   개인·파티 모두 새 이미지로 실행되는지 확인한다. 프로세스 실행/Kafka partition 할당만으로
   성공 판정하지 말고 실제 modelVersion·servingRevision·새 generation과 Backend 소비를 확인한다.
5. 평가 한 건 뒤 GBT 입력·후보·완료 알림·Backend 새 버퍼를 대조한다. 파티도 새 입력 참조로
   요청/게시/소비되는지 확인하고 전환하지 않은 사용자·실패 건은 735로 재처리한다.

현재 `deploy-consumer.sh`/`rollback-consumer.sh`의 last-known-good는 이미지 digest만 보존한다.
따라서 **ALS↔GBT 최초 전환·복구를 이 이미지 단독 자동 롤백에 맡기지 않는다.**
628에서 이미지·환경·모델 pointer·개인/파티 후보를 포함한 이전 정상 릴리즈 복구를 준비한다.
GBT 전환 이후에도 bundle/runtime pin이 다른 이미지로 자동 복구하지 않도록 같은 정상 조합을 보존한다.
보호된 main 자동 배포 정책·권한·Secret 전달 방식은 이번 작업에서 변경하지 않는다.
