# 627 개인 GBT Consumer

742가 병합된 develop 위에서 정식 상태·Candidate v6·파티 v2 참조를 연결한다.
626의 독립 Scorer를 사용하며 모델/특징 구현은 바꾸지 않는다. 기본 실행은 shadow이고,
명시적인 `--publish-live`에서만 정식 Redis 키와 기존 완료 알림을 사용한다.

## 계산과 입력

전체 유효 평가와 관심없음 단독 항목의 가상 1.0을 입력한다. 같은 영화의 실제 평가가
우선하며 가상 평가를 DB에 저장하지 않는다. 최근 K 절단, 최소 이력/양의 평가 요구,
ALS 혼합은 없다. 관심없음 하나만 있어도 입력 1건으로 계산한다.

지원 개봉 전체 카탈로그를 GBT 원점수로 계산하고 평가·관심없음·확정 감상을 제외해
TASTE 최대 500편을 만든다. 검증된 설명 근거가 없는 TASTE의 reasons는 빈 배열이다.
발견은 기존 그룹/TMDB/KOBIS 정책을 재사용하며 TASTE 500에 한정하지 않은 전체 점수를
전달한다. 그룹/발견 번들은 함께 활성화하고, ALS/content artifact는 로딩하지 않는다.

입력 0개(평가와 관심없음 모두 없음)는 지원 개봉 카탈로그의 인기순으로 TASTE 최대 500편을
게시한다. 순서는 기존 v26 특징의 `reach_log1p` 내림차순, 동점은 movieId 오름차순이다.
인기도는 유효 TMDB 투표 수와 검증된 KOBIS 누적 관객 수 × 0.0007732457348003972 중
큰 값의 log1p이며, 결측·비정상 원천 값은 기존 특징 검증에 따라 기여하지 않는다.
GBT 예측점수나 가짜 평가를 만들지 않는다. 실제 count/hash는 빈 입력 그대로이고 후보가
있으면 READY로 게시한다. DISCOVERY는 이 경로에서 비어 있다. 기존 Backend의 최신 평가·
관심없음 제외를 재사용하며, 이 K0 경로는 watched-only를 추가 제외하지 않는다.

입력 1개 이상은 기존 GBT 원점수와 공통 제외를 유지한다. 입력은 있으나 후보가 소진되거나
서비스 가능 카탈로그 자체가 비면 EXHAUSTED 상태만 게시하고 이전 Candidate를 제거한다.
이 소진 경계와 파티 전원 K0는 이번 개인 K0 공급으로 해결하지 않는다.
미지원 이력은 cold-start로 숨기지 않고 소스 위치와 오류 코드로 격리한다.

## 입력 참조와 원자 게시

`gbt_snapshot.py`는 `gbt-input-v1` codec이다. 실제 평점·관심없음·감상 목록과 정렬된
계산 입력/source를 보존한다. inputHash는 이 입력 본문(inputSchemaVersion 포함)의
UTF-8 JSON canonical bytes(sort_keys, compact separators, ensure_ascii=False)에 대한
소문자 SHA-256이다. userId/generationId/modelVersion/servingRevision은 참조 메타데이터로
별도 검증한다. 중복 JSON 키·다른 사용자/세대·변조·byte 예산 초과를 거부한다.

정식 namespace는 `feelm`, shadow는 `feelm:shadow:gbt-v1`이다.

- `:model:current`: 742의 GBT modelKind/modelVersion/servingRevision. live 실행은 수정하지 않는다.
- `:user:<id>:input:<generation>`: 불변 전체 입력. 747는 요청된 세대만 읽는다.
- `:user:<id>:recommendation-state`, `:candidates`, `:candidate-version`: 742 정식 상태와 게시 CAS.
- `:user:<id>:input-current`: 현재 입력 identity와 publicationVersion/epoch 복구용 내부 head. 이력 원본은 없다.
- `:consumer-fence:<group>:<topic>:<partition>`: 기존 partition 소유권 토큰 형식.
- `:gbt-failure:<topic>:<partition>:<offset>`: 오류 코드·위치·revision만 담는 격리 기록.

DB를 읽기 전에 CAS를 확보하고 경합 시 DB 전체 snapshot을 다시 읽는다. 같은 Lua에서
model/fence/CAS를 검증한 후 입력·head·상태·후보를 게시한다. 유실된 입력을 같은 세대로
복구할 때도 남은 identity와 hash가 다르면 거부한다. formal 키의 JSON/타입 손상은 다음
정상 게시로 복구한다. counter 유실은 head의 CAS를 사용한다. head가 유실되면 새 사용자 CAS epoch를 발급한다. 두 순번이 모두 유실돼도
결과가 남으면 새 epoch로 복구하며, 다른 topic/group에서 이미 계산 중인 결과까지 모두
구 epoch로 거절해 DB를 재조회하게 한다. 모든 Redis 증거가 과거 값으로 함께 복원되는 장애는 보장 범위 밖이다.

현재 입력·head·상태·후보에는 TTL이 없다. 새 세대 게시 시 이전 입력만 명시 보존 기간으로
만료시키며 이미 시작된 만료를 연장하지 않는다. state 일부가 없어도 head/candidate를
통해 이전 입력을 정리한다. 입력 보존 기간과 byte 예산은 필수 인수이며 644/628에서 Kafka
재처리 기간과 메모리를 측정해 운영값을 결정한다. 격리 기록도 같은 보존 기간을 사용한다.

실제 루프는 정상 게시 후 기존 feelm.candidate-updated.v1의 broker ACK를 받고 원본 offset을
동기 커밋한다. 잘못된 이벤트/지원 불가 입력은 fenced journal 성공 후에만 격리 ACK하고
다음 요청을 처리한다. DB/Redis/알림/커밋 실패나 model/fence 변경은 루프를 닫아 이후 offset으로
건너뛰지 않는다. 격리된 입력의 수정 후 재처리와 전체 사용자 재게시는 735/628 운영 절차다.

## 실행과 검증

626 고정 GBT 의존성이 설치된 별도 환경을 사용한다. 프로젝트 lock/이미지 통합은 644 소유다.

```bash
PYTHONPATH=src python -m pytest -q
python -m ruff check .
python -m feelm_consumer.gbt_personal_runner --help
feelm-foldin-consumer --gbt-bundle /path/to/bundle --expected-revision sha256:... \
  --group-id gbt-shadow-check --snapshot-retention-seconds <approved-seconds> \
  --max-snapshot-bytes <approved-bytes>
```

기존 CONSUMER_POSTGRES_DSN/CONSUMER_REDIS_URL/CONSUMER_KAFKA_BOOTSTRAP_SERVERS를 사용한다.
shadow group은 gbt-shadow-로 시작해야 한다. 그룹과 발견 검증은 --group-uri/--popularity-uri를
함께 전달한다. shadow는 운영 완료 알림을 발행하지 않는다. live는 승인된 운영 전환 절차에서
--publish-live를 추가하며 현재 GBT 모델 포인터가 일치해야 한다. 이 작업에서는 배포하지 않았다.

검증 계층: 실제 626 XGBoost fixture의 전체/부분 점수·음수/관심없음 입력·발견 정책;
고유 Docker Redis의 Lua/부분 유실/경합/retention; 주입형 실제 Kafka 루프의 ACK/poison 진행;
공유 gbt-personal-state.json을 실제 Java RedisPartyInputReader가 읽는 계약 테스트.
Docker/JDK/외부 DB가 없는 경우 해당 통합 검증은 skip이며 실환경 검증으로 간주하지 않는다.
운영 DB·Kafka rebalance·HDFS·서버 부하 검증은 별도로 남는다.
