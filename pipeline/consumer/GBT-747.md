# 파티 GBT Consumer (S15P21E106-747)

829의 `feelm.party-refresh.v1` 최상위 3필드 요청과 627의 불변 입력 snapshot을 사용한다.
전환 중 큐에 남은 742 schema v2의 최상위 6필드 요청도 검증해 처리한다.
626의 동일 GBT로 전체 입력을 재점수화하고 기존 `feelm:party:{partyId}:candidates`와 완료 이벤트로 연결한다.
483은 제외했다. K0·소진·입력 오류로 기존 추천을 빈 목록이나 임의0점으로 교체하지 않는다.

## 실행과 전환

626 `gbt-runtime-requirements.txt`의 고정 런타임에서 실행한다.644의 이미지 통합은 별도다.

```powershell
$env:PYTHONPATH='src'
python -m feelm_consumer.party_main `
  --gbt-bundle /path/to/immutable-gbt-v26 `
  --expected-revision sha256:<approved-manifest-digest> `
  --max-snapshot-bytes <measured-byte-budget>
```

`--expected-revision`은 신뢰된 배포 입력으로 받은626 manifest SHA pin이다. 같은 폴더에서 해시를 계산해
자동 승인하지 않는다. `--max-snapshot-bytes`는1~64MiB 범위의 명시 인수이며 초과 입력을 잘라 계산하지 않는다.
기존 `PARTY_CONSUMER_KAFKA_BOOTSTRAP_SERVERS`, `PARTY_CONSUMER_KAFKA_GROUP_ID`,
`PARTY_CONSUMER_REDIS_URL`만 필수다. 토픽·재시도·poll 설정은 기존 party 환경변수를 그대로 사용한다.
새 DSN·DB 쓰기·Kafka 토픽·환경변수는 추가하지 않았다.

`--gbt-bundle`이 없으면 기존 ALS 실행 경로다. GBT 경로에서는 ALS URI 환경변수가 남아 있어도 모델을
시작할 때 읽지 않는다. **활성 모델이 legacy이고 실제 v1을 처리할 때만** 기존 세 URI로 ALS를 지연 로드할
수 있다. 세 URI가 없으면 해당 legacy 요청은 commit하지 않고 실행 설정 수정을 기다린다.
`model:current.modelKind=GBT`이면 v1의 vector를 계산하지 않는다.

배포 순서는829 계약의 전환 절차를 따른다: legacy/구 6필드/새 3필드를 구분하는 Consumer 배포 →627
전체 사용자 상태와 snapshot 검증 →829 Backend 배포 →승인된 modelKind/revision 전환 →전체 활성 파티 refresh.
새 3필드를 이해하지 못하는 Consumer로 단독 rollback하지 않는다. 이 구현이나 테스트는 운영 모델
포인터를 변경하지 않는다. 실제 서버 전환·rollback·전체 재요청 증거는628/735 범위다.

## 입력 검증과 계산

`gbt_party_events`는 `PartyRefresh`·`PartyInputReference`를 사용한다. 새 요청의 정확한 최상위 필드는
partyId, inputId, members이고, GBT member는 userId, generationId, inputSchemaVersion, inputHash,
candidateMovieIds다. 기존 6필드 요청은 schemaVersion=2, modelVersion, servingRevision도 가져야 한다.
legacy는 userId, vector, candidateMovieIds 멤버로만 식별한다. 섞인 멤버·부분 메타데이터·임의 키·중복
JSON 키를 거부한다. LongSerializer8바이트 key,1~4명·userId오름차순·중복·600개 상한을 검증한다.

inputId는 실제 Java `PartyInputId`와 같은 big-endian long/int 및 UTF-8 byte-length 구분 SHA256이다.
partyId, 검증한 modelVersion, 내부 schemaVersion=2, servingRevision, 각 userId·generation·inputSchemaVersion·inputHash를
묶는다. 후보 목록은742 hash 정의에 추가하지 않는다. `gbt-input-v1`만 지원하고 잘못된 hash/schema는 격리한다.

`RedisSnapshotReader`는 `feelm:user:{userId}:input:{generationId}`만 읽는다. 이벤트가 지정하는 URI나 Redis
key를 따라가지 않는다.627 codec으로 userId·generation·modelVersion·servingRevision·inputSchemaVersion·
canonical inputHash와 크기를 검증하며 현재 세대로 대체하지 않는다. 새 요청의 모델 정보는 이 검증된 snapshot에서
확인한다. 모든 멤버의 모델/revision이 같고 활성·로딩 모델과 일치하며 기존 inputId가 재현될 때만 계산한다.
검증한 snapshot 객체를 계산에 재사용하여 metadata 확인 뒤 입력을 다시 읽지 않는다.
입력 전체를 사용하고 최근 N개 제한은 없다.

각 구성원의 개인 TASTE500·DISCOVERY100을 합친 최대600개를 모아 최대2400편 합집합을 만든다.
**전체 구성원**의 실제 평가·관심없음·감상 영화 합집합을 제외한 동일 모집단을626 scorer로 각각 다시 점수화한다.
개인 전체 점수와 파티 부분 점수는 동일 특징·동일 모델을 사용한다. 별도 품질·언어·투표 수 컷은 없다.

- 실제 평가 우선, 실제 평가 없는 관심없음만 계산상1.0 입력이다.1개·부정·관심없음 단독도 계산한다.
- watched-only는 제외 조건이다. K0 구성원은 평균 분모에서 제외하며 가짜0점이나 개인후보순위로 채우지 않는다.
- 동일 surviving 모집단에서 사용자별 midrank fit=`(앞선 수 + 동점 수/2)/N`을 구한다. singleton·전체동점은0.5다.
- K>0 구성원 fit을 같은 가중치로 평균하고 mean 내림차순→min 내림차순→stddev 오름차순→movieId 오름차순으로
  정렬한 **뒤** 최대500편을 선택한다. ALS·rank fallback은 없다.
- `partyScore`, `meanFit`, `minFit`, `maxFit`, `stddevFit`, `memberFit[].score`를 유지한다.
  algorithmVersion=`party-gbt-mean-fit-v1`, generatedAt은 원본 Kafka timestamp의 고정 UTC 밀리초다.

## 게시·실패·재시도

정상 결과만 기존 `feelm:party:{id}:candidates`에 게시한다. Lua에서 기존 Consumer partition fence와
`feelm:model:current`의 modelKind=GBT, modelVersion, servingRevision을 동시에 검사한다.
기존 ALS publisher도 modelKind=GBT면 원자적으로 거부하므로 포인터 전환과 겹친 늦은 v1이 덮어쓰지 못한다.

내부 `feelm:party:{id}:gbt-outcome`은 해당 파티의 마지막 성공 결과와 source 위치 하나를 보존한다.
동일 source·request replay는 입력 snapshot을 다시 읽기 전에 저장한 결과를 검증·재사용한다. 새 3필드 요청은
우선 동일 source/party/inputId의 성공 메타데이터를 읽기 전용으로 확인하고, 그 모델/revision과 요청 멤버 참조로
inputId를 재검증한다. 이후 기존 atomic model/fence/source guard를 통과해야만 결과 수리·재알림을 수행한다.
Redis 성공 뒤
Kafka ACK가 유실되고 snapshot이 나중에 없어져도 원래 성공을 실패로 재계산하지 않는다. source offset은
문자열로 비교해 signed64 범위의 double 반올림을 피한다. 오래된 offset·달라진 partition·손상된 outcome·같은
offset의 다른 입력은 거부한다. 파티 키의 토픽/partition 재배치에는628의 별도 전환 검증이 필요하다.
live 결과와 outcome 중 한 키만 유실되어도 남은 최신 source를 함께 비교한다. 같은 source의 재전달은 검증된
성공본으로 누락·손상된 live 또는 누락된 outcome을 원자 복구한 뒤 알린다. 더 최신 live가 있으면 오래된 요청으로
복구하지 않는다. 모델·소유권이 달라지면 복구도 거부한다.

성공 게시→기존 `feelm.party-candidate-updated.v1` broker ACK→동기 원본 offset commit 순서다.
알림 중복은 가능하며 Spring이 현재 inputId와 modelVersion으로 최종 검증한다. 저장·알림 장애나 소유권 상실은
commit하지 않고 재처리한다. pause된 partition에서 이미 큐에 들어온 후속 record도 commit하지 않는다.

snapshot 부재·hash/schema 불일치·미지원 입력은 **성공 추천으로 게시하지 않는다**. 기존 party 후보를 유지하고
`feelm:party-consumer:quarantine:{topic}:{partition}:{offset}`에 오류 코드와 source/입력 식별자만 기록한다.
평가·원본 이벤트·접속정보·예외 상세는 저장하거나 로그에 쓰지 않는다. 로그도 성공과 QUARANTINED를 구분한다.

유효하게 해석된 구성원이 있으면 기존 `feelm.candidate-updated.v1`을 구성원별로 ACK 발행한다.
Spring의 기존 listener가 현재 관련 활성 파티들을 DB refresh 요청으로 저장하고 다시 읽는다. Consumer가
PostgreSQL에 쓰거나 새로운 recovery 토픽을 만들지 않는다. 늦은 v1도 같은 경로로 소진·재요청한다.
재요청 ACK 완료를 `feelm:party-consumer:recovery:{sha256(partyId,inputId,errorCode)}`에 기록해 같은 실패의
후속 record가 무한 재요청을 만들지 않게 한다. ACK와 marker 사이의 crash에서는 at-least-once 재요청이 가능하다.
재요청 ACK 또는 marker 쓰기 실패는 offset을 진행하지 않는다.
재시도 사이에 모델이 배포되어 오류 분류가 달라져도 같은 source/request의 최초 격리 기록을 그대로 반환하고
원래 복구 ACK를 재개한다. 동일 offset이 다른 request identity로 바뀌면 계속 거부한다.
새 3필드 요청의 실패 identity는 원본 wire의 모델 메타데이터 부재를 유지하므로, snapshot이 나중에 나타나거나
활성 모델이 바뀌어도 최초 격리·복구 기록을 이어서 사용할 수 있다.

durable 격리와 필요한 재요청 ACK가 끝나면 해당 실패 위치의 offset만 소진하고 같은 partition의 다음 정상
요청을 처리한다. 이는 계산 성공이 아니라 격리 완료다. 파싱할 수 없어 구성원을 신뢰할 수 없는 요청은
source/code만 남기고 소진한다. 운영자는 원인을 수정한 뒤 기존 정상 요청 발행 경로로 새 요청을 보낸다.
재요청 후에도 같은 입력 오류가 남으면 marker로 추가 재요청을 멈추므로 journal을 확인해 수정·재발행해야 한다.

전원K0(`NEEDS_COLD_START`)·후보소진(`EXHAUSTED`)도 기존 결과 유지와 명시 격리다.483이 제외됐으므로
후보를 공급하지 않고 자동 재요청 루프도 만들지 않는다. 입력 변경은 기존 개인 완료 이벤트로 새 파티 요청을 만든다.
로드한 모델 자체가 활성 revision과 다르면 STALE_MODEL로 중단하고 유효 요청을 terminal 실패로 소비하지 않는다.

live 결과는 기존 계약대로 TTL이 없다. 입력 snapshot의 보존·크기 정책은627을 따른다. 실패/recovery 기록은
운영 복구 근거이므로 임의 TTL로 유실시키지 않으며628 runbook에서 정리·보관 기준을 정해야 한다.
Redis snapshot 복원으로 fencing key 자체가 과거로 돌아가는 장애는 이 구현의 보장 범위 밖이다.
