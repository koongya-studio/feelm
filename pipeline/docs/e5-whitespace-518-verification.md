# S15P21E106-518: E5 입력 공백 검증

검증일: 2026-09-19. 기존 DB, TMDb 원본, 임베딩 산출물을 변경하지 않고 로컬 사본을 읽었다.

## 1. 정제 문자열과 SHA-256

현재 `batch/embedding/source.py`의 `_clean`을 Spark로 직접 실행했다. `title: ` 접두어를 포함한 입력의 SHA-256을 비교했다.

| 원문 | 현재 정제 결과 | 기준(`Movie Title`)과 SHA-256 |
| --- | --- | --- |
| `Movie Title` | `Movie Title` | 같음 |
| `Movie  Title` / `Movie   Title` | 연속 일반 공백 유지 | 다름 |
| 탭 / LF / CRLF | `Movie Title` | 같음 |
| NBSP | NBSP 유지 | 다름 |

한글 `우주 탐험`과 `우주  탐험`도 정제 결과와 SHA-256이 달랐다. 즉 현재 코드의 `r"\\s+"` 치환은 일반 공백을 접지 않는다.

## 2. 고정 E5 모델의 토큰과 벡터

기존 산출물의 모델 `intfloat/multilingual-e5-base`, revision `d128750597153bb5987e10b1c3493a34e5a4502a`, `query: ` 접두어, 최대 512토큰, 평균 풀링 및 L2 정규화를 그대로 사용했다. 위 영어·한글 합성 입력 9종을 CPU에서 인코딩했다.

- 영어 기준과 연속 일반 공백, 탭, LF, CRLF, NBSP 변형은 토큰 ID 배열이 동일했다. 한글 기준과 이중 공백 변형도 동일했다.
- 각 변형의 768차원 벡터는 해당 기준과 원소별 최대 절댓값 차이 `0.0`, 코사인 유사도 `1.0`이었다.
- 이는 검사한 입력의 결과다. 실제 237,817건 전체의 토큰·벡터 동일성을 증명한 것은 아니다.

## 3. 기존 전체 입력 영향

로컬 `raw-tmdb`, `raw-keywords`, `service-movie-id-map`을 읽어 현재 소스 텍스트를 재구성하고, `e5-base-gpu-20260916T073404Z` 산출물의 `input_text_sha256`과 대조했다. **237,817건 전부 기존 산출물 SHA와 일치**했고 매핑 ID 불일치는 없었다. 이에 따라 집계에 사용한 재구성 방식이 기존 입력과 일치함을 확인했다.

각 필드의 연속 공백을 한 칸으로 접는 방식을 가정하면 **9,508건(4.0%)**의 소스 텍스트와 입력 SHA가 바뀐다. 변경 필드별 등장 건수는 `overview` 8,518, `title` 359, `keywords` 321, `cast` 217, `director` 122, `original title` 54다. 한 영화에서 여러 필드가 바뀔 수 있어 필드별 건수의 합은 영화 건수와 다르다.

추가로 전체 9,508건을 고정 tokenizer에 `query: ` 접두어와 최대 512토큰 조건으로 넣어 토큰 ID 배열을 비교했다. **9,323건은 동일했고 185건은 달랐다.** 토큰 ID가 같은 건은 같은 모델과 연산을 적용하면 같은 벡터가 된다. 185건의 새 벡터는 이번에 생성하지 않았다.

재현 순서는 다음과 같다.

1. 위 로컬 TMDb·keyword JSON과 서비스 영화 ID 매핑을 `source.py`의 필드 선택·정렬 규칙으로 결합한다. 현재 `_clean`을 적용한 소스 텍스트의 SHA-256을 산출물 `embeddings.input_text_sha256`과 영화 ID별로 대조한다.
2. 같은 원본 필드에서 연속 공백을 한 칸으로 합친 가상 텍스트를 만들어 현재 텍스트와 비교한다. 서로 다른 영화의 수를 집계한다.
3. 서로 다른 두 텍스트에 각각 `query: `를 붙여 위 revision의 tokenizer로 최대 512토큰까지 인코딩하고 토큰 ID 배열을 비교한다. 이 과정은 DB나 기존 Parquet에 쓰지 않는다.

**결론:** 현재 정제 규칙과 기존 산출물을 그대로 사용한다면 재임베딩은 필요 없다. 연속 공백을 접는 규칙으로 변경한다면 9,508건의 입력 SHA와 그에 따른 전체 스냅샷 해시가 바뀌며, 그중 최소 185건의 벡터를 새로 계산해야 한다. 기존 산출물은 불변이므로 새 산출물 버전과 입력 템플릿 버전을 결정한 뒤 교체해야 한다. 현 배치는 전체 산출물 생성 방식이므로 선택적 재사용 절차를 별도로 만들지 않는다면 전체 재생성이 가장 단순하다. 이 작업에서는 정제 코드와 계약을 변경하지 않았다.

## 확정 방침

2026-09-19 담당자와 **현재 `tmdb-e5-v1` 유지**로 결정했다. 연속 일반 공백 보존을
회귀 테스트와 배치 README에 명시한다. 기존 임베딩 산출물과 DB `model_version`을
유지하며 재임베딩과 공유 DB/HDFS 쓰기는 수행하지 않는다. 새 공백 정규화가 필요한
경우 새 입력 레시피와 불변 산출물·DB 전환을 별도 Jira에서 다룬다.
