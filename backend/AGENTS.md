# Backend AGENTS.md

루트 `AGENTS.md`의 프로세스 규칙을 전제로, `backend` 디렉터리에서 작업하는
AI 코딩 도구가 따라야 할 작업 절차를 정의한다.

## 1. 기준 문서

- 코드 스타일과 코드 규칙: `docs/backend-convention.md`
  - 컨벤션을 적용할 수 없거나 예외가 필요하면 구현 전에 사용자에게 이유와 대안을
    제시한다.
- API 계약: `docs/api/`, 논리 스키마: `docs/erd.md`, 물리 스키마와 마이그레이션:
  `docs/db-schema-convention.md`
  - 구현은 계약을 따른다. 계약과 다르게 구현해야 하면 임의로 진행하지 않고
    합의 후 문서를 먼저 수정한다.
  - 명세에 없는 API, Entity, 필드를 임의로 추가하지 않는다.
- 담당 도메인과 공통 코드 소유권: `docs/backend-role-assignment.md`
  - 다른 담당자 소유 도메인과 공통 설정을 임의로 수정하지 않는다.
- 아키텍처 결정: `docs/adr/`
- 실행, 빌드와 Docker: `backend/README.md`

## 2. 검증

Java 21이 필요하다. Windows에서는 `./gradlew` 대신 `.\gradlew.bat`을 사용한다.
플랫폼별 명령은 `backend/README.md`를 따른다.

- 구현 중 포맷 정리: `./gradlew spotlessApply`
- 완료 검증: `./gradlew build` — `spotlessCheck`와 `test`를 포함하며 파일을
  수정하지 않는다. 포맷 위반이 있으면 `spotlessApply`로 수정 후 다시 검증한다.

완료 검증에서 작업 범위 밖의 파일을 수정하지 않는다.

## 3. 적용 범위

변경이 닿는 범위에 따라 세 단계 중 하나를 적용한다. 섞이면 가장 높은 단계를 따른다.
판정과 근거는 플랜 파일 첫 줄에 적는다.

| 단계 | 조건 | 적용 |
| --- | --- | --- |
| 검증만 | 문서, 주석, 테스트 코드만 변경 | 2장 검증 |
| 기본 | 아래 트리거에 해당하지 않음 | 4장의 산출물과 완료 기준을 한 세션에서 충족한다. 게이트 없음 |
| 게이트 | 아래 트리거 중 하나 이상 | 4장의 산출물과 완료 기준에 더해 두 게이트를 거친다 |

트리거. diff 또는 플랜에 하나라도 있으면 해당한다.

- `docs/api/`, `docs/erd.md`, `docs/db-schema-convention.md`의 변경 또는 그 계약과 다른 구현
- Flyway 마이그레이션 파일
- `global/`, `infrastructure/`, `SecurityConfig`, 다른 담당자 소유 도메인
- `@Transactional` 경계의 신설·변경, 한 유스케이스에서 둘 이상의 Repository 쓰기
- 인증·인가 코드, 토큰·쿠키 처리
- Kafka 발행·소비, Redis 키·TTL
- `build.gradle`, `application*.yml`, `.env.example`

## 4. 작업 절차와 게이트

AI는 플랜, 구현, 리뷰 세 단계의 산출물을 남기고 각 완료 기준을 충족한다. 산출물은 다음
단계가 Jira 요구사항, 정본 문서, 저장소 상태와 함께 작업을 재현할 수 있을 정도로 작성한다.
동일 worktree를 여러 작업자가 동시에 수정하지 않는다.

1. **플랜** — 루트 `plans/<Jira-Key>.md`(5장). 설계, 미확정 항목, 기준선(시작 시점의 미커밋 변경 목록),
   3장 판정과 트리거, 열리는 리뷰 게이트, 인수 테스트 목록(동작마다 테스트 이름, 전제·입력,
   기대 결과인 응답·오류 코드·상태 변화. 테스트로 확인할 수 없는 변경은 대체 검증과 통과 조건).
   이후 단계는 기준선의 기존 변경을 보호한다. 완료 기준: 모든 동작에 테스트 또는 대체 검증이
   대응하고, 계약·스키마·공용 파일 영향이 팀과 합의되어 있다.
2. **구현** — 완료 기준: 플랜의 인수 테스트가 모두 존재하고 통과하며 `./gradlew build`가
   성공한다. 플랜 목록 대비 테스트의 추가·삭제·기대값 변경과 플랜 이탈은 사람 확인 후
   플랜에 기록되어 있다. 테스트 취급은 루트 `AGENTS.md` 6장을 따른다.
3. **리뷰** — 루트 `plans/<Jira-Key>-review.md`. 변경 단위마다 diff와 그 단위가 참조하는
   계약 절만 읽고 관점을 한 번에 적용한다. 관점별로 기준 문서를 다시 읽지 않는다.
   Secret 점검은 diff 전체에 한 번, 단위 간 정합성은 마지막에 한 번(계약·트랜잭션
   경계·오류 코드)만 본다.
   - 계약 정합성 · 정확성(경계 조건, 실패 경로) · 보안(입력 검증, Secret)
   - 테스트 실효성: 플랜 목록과 실제 테스트의 대조, 기대값 변경 기록의 타당성
   - 조건부: 트랜잭션·인증 트리거에 해당하는 단위에만 동시성·트랜잭션 경계와 인가.
     게이트 개폐와 근거를 적는다.
   측정 칸: 읽은 기준 문서 절 수, 열린 게이트, MR 리뷰에서 뒤늦게 발견된 누락(병합 후).

리뷰 편성은 3장 단계에 따른다.

- **기본 단계(W1)**: 리뷰어 한 명이 위 관점을 한 세션에서 모두 적용한다.
- **게이트 단계(W2)**: 두 세션이 같은 대상을 독립으로 리뷰한다. A는 위 관점 그대로 보고,
  B는 이 변경이 자기 목적을 달성하지 못하는 경우를 찾는다. B는 인수 테스트마다 전제를 깨는
  입력·교차 실행·실패 경로를 만들어 보고, 열린 게이트 항목은 구체적 인터리빙 또는 요청
  시나리오로 결함을 내거나 결함이 없음을 보이며, 결함이 없다는 결론은 시도한 공격 목록과
  함께 적는다. A와 B는 각각 루트 `plans/<Jira-Key>-review-A.md`와 `-review-B.md`에 쓰고 서로의
  리뷰 파일을 읽지 않는다. 반영 전에 두 결과를 합집합으로 `plans/<Jira-Key>-review.md`에
  모아 A-n/B-n 번호를 유지한 채 채택·기각·후속을 표시한다. 이 대조표는 AI가 만들고 사람은
  갈래가 있는 항목만 판단하며, 반영은 채택 목록만 고친다.

게이트 단계에서는 두 지점에서 사람이 개입한다. 게이트는 자동 검증이 부족한 동안의 대체
장치다. 게이트 단계 MR 5건 연속으로 사후 누락이 0이면 분리 리뷰의 완화를, 기본 단계
MR에서 사후 누락이 나오면 트리거 확대를 검토한다.

- **플랜 승인**: 플랜 완료 후 사람이 확인하고 승인·수정 지시를 플랜에 추기한 뒤 구현을
  시작한다.
- **분리 리뷰**: 리뷰는 구현과 다른 세션에서 플랜·diff·정본 문서만 보고 수행한다.

## 5. 플랜과 기록

- 플랜과 리뷰 파일은 **저장소 루트의 `plans/`** 에 둔다. 이 문서가 `plans/`로만 적은 곳도
  모두 루트를 가리킨다. `.gitignore`의 무시 규칙이 루트에 고정된 `/plans/`와 하위 디렉터리의
  `/*/plans/`뿐이므로, 그 밖의 위치에 두면 커밋하지 않기로 한 기록이 커밋 대상이 된다.
- worktree에서 작업했으면 완료 후 산출물을 기본 체크아웃의 루트 `plans/`로 옮긴다.
  worktree를 정리하면 그 안에만 있던 플랜과 리뷰 기록이 함께 사라진다.
- 플랜과 리뷰 결과는 커밋하지 않는다. MR 본문에 플랜 요약, 플랜 대비 변경점과
  리뷰 결과 요약을 남긴다.
- 플랜과 리뷰 파일은 `docs/templates/plan.md`와 `docs/templates/review.md` 양식으로
  작성하고 측정 칸을 비워 두지 않는다.
- 리뷰 파일의 측정 칸과 플랜의 인수 테스트 목록은 MR 본문 "검증" 절에 옮겨 적는다.
- 세션은 해당 Jira의 worktree 디렉터리에서 시작한다.
- 플랜에서 프로젝트 수준 결정이 나오면 `docs/adr/`로 승격한다.
- 미래 작업에 필요한 사실을 플랜이나 MR 본문에만 남기지 않는다. 계약, 스키마와
  코드 규칙 변경은 반드시 정본 문서(`docs/api/`, `docs/erd.md`,
  `docs/backend-convention.md`, `docs/adr/`)에 반영한다.
