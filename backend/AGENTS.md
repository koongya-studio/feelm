# Backend AGENTS.md

루트 `AGENTS.md`의 프로세스 규칙을 전제로, `backend` 디렉터리에서 작업하는
AI 코딩 도구가 따라야 할 작업 절차를 정의한다.

## 1. 기준 문서

- 코드 스타일과 코드 규칙: `docs/backend-convention.md`
  - 컨벤션을 적용할 수 없거나 예외가 필요하면 구현 전에 사용자에게 이유와 대안을
    제시한다.
- API 계약: `docs/api/`, 논리 스키마: `docs/erd.md`, 물리 스키마와 마이그레이션:
  `docs/db-schema-convention.md`
  - 구현은 계약을 따른다. 계약과 다르게 구현해야 하면 임의로 진행하지 않고
    합의 후 문서를 먼저 수정한다.
  - 명세에 없는 API, Entity, 필드를 임의로 추가하지 않는다.
- 담당 도메인과 공통 코드 소유권: `docs/backend-role-assignment.md`
  - 다른 담당자 소유 도메인과 공통 설정을 임의로 수정하지 않는다.
- 아키텍처 결정: `docs/adr/`
- 실행, 빌드와 Docker: `backend/README.md`

## 2. 검증

Java 21이 필요하다. Windows에서는 `./gradlew` 대신 `.\gradlew.bat`을 사용한다.
플랫폼별 명령은 `backend/README.md`를 따른다.

- 구현 중 포맷 정리: `./gradlew spotlessApply`
- 완료 검증: `./gradlew build` — `spotlessCheck`와 `test`를 포함하며 파일을
  수정하지 않는다. 포맷 위반이 있으면 `spotlessApply`로 수정 후 다시 검증한다.

완료 검증에서 작업 범위 밖의 파일을 수정하지 않는다.

## 3. 적용 범위

- 문서, 주석, 테스트 코드만 변경하는 작업은 검증만 수행한다.
- 그 외 모든 변경은 `4. 작업 파이프라인`을 따른다. 애매하면 파이프라인이
  기본값이다.

## 4. 작업 파이프라인

각 단계는 사람이 새 세션을 열어 시작하며, 이전 단계의 대화 맥락 없이 수행한다.
단계를 마친 AI는 산출물을 남기고 종료하며, 스스로 다음 단계로 진행하거나
단계를 생략하지 않는다. 사람은 단계 사이에 산출물을 확인한 뒤 다음 세션을
시작하고, 이때 이후 단계의 생략이나 조정을 지시할 수 있다. 단계 사이에 사람이
내린 결정(미확정 항목 판단, 생략·조정 지시)은 플랜 파일에 추기해 이후 단계가
참조하게 한다.

각 단계의 산출물(플랜, 테스트, diff, 리뷰 결과)은 다음 단계가 Jira 요구사항,
정본 문서, 저장소 상태와 함께 작업을 재현할 수 있을 정도로 작성한다.
동일 worktree를 여러 작업자가 동시에 수정하지 않는다.

1. **플랜**: 저장소 루트 `plans/<Jira-Key>.md`(커밋되지 않음)에 설계, 검증
   방법, 미확정 항목과 작업 시작 시점의 커밋되지 않은 기존 변경 목록(기준선)을
   작성한다. 이후 단계는 기준선을 기준으로 기존 변경을 보호한다.
   API 계약, DB 스키마 또는 공용 파일에 영향이 있으면 구현 전에 팀에 공유하고
   합의한다.
2. **테스트 선행**: 플랜을 기준으로 실패하는 테스트를 먼저 작성하고, 실행으로
   실패를 확인한 뒤 구현을 시작한다.
3. **구현**: 테스트를 통과시키는 최소 구현 후 정리한다. 테스트를 통과시키기
   위해 테스트를 약화하지 않는다. 플랜과 다르게 진행해야 하면 임의로 진행하지
   않고 사람에게 확인한 뒤 결정을 플랜 파일에 추기한다.
4. **리뷰**: 결과를 `plans/<Jira-Key>-review.md`(커밋되지 않음)에 남기고,
   다음 관점을 각각 검토한다.
   - 계약 정합성: `docs/api/`, `docs/erd.md`와 구현의 일치 여부
   - 정확성: 경계 조건과 실패 경로
   - 동시성과 트랜잭션 경계
   - 보안: 인증·인가, 입력 검증, Secret 노출
   - 테스트 실효성: 테스트가 실제 동작을 검증하는지

## 5. 플랜과 기록

- 플랜과 리뷰 결과는 커밋하지 않는다. MR 본문에 플랜 요약, 플랜 대비 변경점과
  리뷰 결과 요약을 남긴다.
- 플랜에서 프로젝트 수준 결정이 나오면 `docs/adr/`로 승격한다.
- 미래 작업에 필요한 사실을 플랜이나 MR 본문에만 남기지 않는다. 계약, 스키마와
  코드 규칙 변경은 반드시 정본 문서(`docs/api/`, `docs/erd.md`,
  `docs/backend-convention.md`, `docs/adr/`)에 반영한다.
