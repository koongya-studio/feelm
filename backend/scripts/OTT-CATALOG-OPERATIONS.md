# OTT 기준정보 초기화·점검과 실패 대응

S15P21E106-381의 현재 구현과 확정된 데이터 보존 규칙을 설명한다.
신규 환경은 승인 CSV 5종을 새 Flyway seed로 준비한다(2026-09-14 사용자 확정).
**서비스는 OTT 지원을 종료하지 않는다(2026-09-14 사용자 확정).** 승인된 지원 목록과 기존
구독·영화 관계·감상 이력을 유지하며 종료·비활성화 기능이나 별도 구독자 처리 절차를 두지 않는다.
API 계약은 [API-025~027](../../docs/api/onboarding-ott.md), 삭제·마이그레이션 정책은
[DB 규칙](../../docs/db-schema-convention.md)을 따른다.

## 사전 점검

1. 대상 환경·DB·실행자, 승인 CSV의 변경 이력과 5종 code/provider 쌍을 확인한다.
   provider `8,337,97,356,1883`은 TMDb 식별자다. 구독 API에는 조회된 **서비스 ottId**를 쓴다.
2. 구버전 적재가 실행 중이면 새 버전과 섞어 실행하지 않는다. 구버전은 code를 재매핑할 수 있다.
   승인 CSV에서 행을 제거하는 것도 지원 종료가 아니며, 임의의 수정 CSV를 운영에 적용하지 않는다.
3. 저장소 루트에서 아래 조회 명령을 실행한다. `OTT_POSTGRES_CONTAINER`는 실행자가 확인한
   대상 컨테이너 이름이며 접속 비밀은 출력하거나 명령 인자에 넣지 않는다.

```bash
docker exec -i "$OTT_POSTGRES_CONTAINER" sh -c \
  'exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < backend/scripts/inspect-ott-catalog.sql
```

조회는 읽기 전용 트랜잭션이다. 모든 OTT의 ID·code·provider·표시 정보와 구독/영화/감상 참조 수,
실제 FK 목록, 관련 테이블 잠금을 확인한다. FK가 추가되면 새 참조의 보존도 검토해야 한다.
이 스냅샷이나 잠금 목록은 이후 쓰기를 차단하지 않으므로, 조회 직후 참조가 0이라는 이유로
삭제해서는 안 된다. DB 규칙은 참조가 없어도 기준정보의 물리 삭제를 금지한다.

## Flyway 초기화

`V202609142240__seed_approved_ott_catalog.sql`이 승인 CSV 5종의 초기 스냅샷이다.
TMDb 인증·네트워크·영화 입력 없이 일반 애플리케이션 기동 시 Flyway가 적용한다.
운영자는 기존 배포 절차와 Secret 주입 방식을 사용한다. 로컬 또는 격리 환경의 실행 예시는
다음과 같다(Java 21, PostgreSQL/pgvector 및 README의 필수 환경변수 준비, `backend/`에서 실행).

```bash
java -jar build/libs/backend-0.0.1-SNAPSHOT.jar
```

JAR는 `./gradlew bootJar`(Windows: `.\gradlew.bat bootJar`)로 만든다. 이 명령은 계속 실행되는
서버이므로 성공은 프로세스 종료 코드가 아니라 기동 완료 로그와 아래 사후 점검으로 판정한다.
기존 DB의 Flyway 이력이 없는 상태에 임의로 baseline/repair를 적용하지 않는다.

1. **적용 전** 기존 DB는 위 읽기 전용 점검을 실행하고 스냅샷·백업 및 복구 가능 여부를 확인한다.
   점검의 승인 쌍 상태가 `CONFLICT`이면 기동/배포를 중단한다. `MISSING`은 추가 대상,
   `MATCH`는 같은 행 보존 대상이다. 빈 DB는 이전 마이그레이션부터 모두 적용하므로 테이블이
   없을 때 점검 SQL이 실패하는 것은 정상이며, DB가 정말 신규 환경인지 먼저 확인한다.
   구버전 적재 작업은 종료시킨 뒤 적용한다. 새 seed와 수정된 적재는 같은 테이블 잠금으로
   직렬화되지만, 오래된 적재는 이후 code를 재매핑할 수 있다.
2. **적용** 같은 code/provider 쌍은 ID·이름·로고를 포함해 행을 그대로 유지한다. 없는 쌍만
   INSERT하며, DB의 다른 OTT도 삭제하지 않는다. 서비스 ID는 identity sequence로 발급하며
   이미 점유된 번호는 건너뛴다. provider ID를 서비스 ID로 사용하거나 sequence를 되돌리지 않는다.
   기존 구독·영화 제공처·감상 이력은 변경하지 않는다.
3. **중단** code/provider 관계 충돌이나 SQL 오류가 발생하면 seed의 모든 행 변경이 롤백되고
   Flyway 및 애플리케이션 기동이 실패한다. 오래 걸리는 잠금 대기는 진행 중인 쓰기를 조사하고
   배포 시간 한도를 넘기면 적용 프로세스를 중단한다. 정상 완료 여부를 확인하기 전 트래픽을
   전환하지 않는다. 이미 성공한 이전 버전 마이그레이션은 이 seed 실패로 되돌아가지 않는다.
4. **검증** 위 조회 명령을 다시 실행해 승인 5쌍 모두 `MATCH`, 원래 행과 세 참조의 스냅샷 보존,
   seed 버전 이력 `success=true`를 확인한다. 신규 DB는 정확히 5행이며 기존 DB는 승인 외 행도
   남는다. `GET /api/v1/otts`는 `ottId` 오름차순이고, 기존 환경의 ID/표시 정보는 신규 환경과
   다를 수 있다. API-026/027은 인증 사용자로 조회→같은 목록 PUT→재조회하고 ID 보존을 확인한다.
5. **복구** 원인 확인 전 ID/code/provider와 참조를 강제로 변경하거나 삭제하지 않는다.
   충돌은 어느 식별쌍이 맞는지 담당자가 근거와 보정안을 확정해야 한다. SQL/권한 오류는 해당
   원인을 해결한 뒤 같은 버전으로 기동을 재시도한다. PostgreSQL의 실패한 seed는 성공 이력을
   남기지 않아 `repair`가 필요하지 않다. 적용된 Flyway 파일 또는 성공 이력은 수정하지 않는다.
   COMMIT 응답이 유실되면 성공 여부가 불명확하므로 DB 이력과 실제 행부터 재조회한다.
   이미 성공했다면 다음 기동은 seed를 건너뛴다. 시퀀스 소비는 롤백되지 않아 ID 공백은 생길 수 있다.

이 seed는 버전 마이그레이션이므로 매 기동마다 CSV와 재동기화하지 않는다. 이후 지원 목록 변경은
별도 합의 후 **새 버전**으로 처리하며 적용된 seed를 고치지 않는다. 콘텐츠 적재의 같은 쌍
메타데이터 갱신은 아래 규칙을 따른다. 초기화 seed나 CSV 삭제를 지원 종료 수단으로 쓰지 않는다.

## 현재 적재의 보장과 복구

기존 명령은 [backend README의 PostgreSQL 적재](../README.md)를 따른다.
이 명령은 영화 입력 또는 수집한 raw를 사용하는 콘텐츠 적재다. OTT만 필요한 신규 환경은
위 Flyway 초기화를 사용한다.

- CSV는 정확히 4열, 양수 int 범위 provider, 유효 code·로고 경로와 provider/code 각각의
  중복 여부를 전부 확인한다. 마지막 줄의 개행 유무는 결과에 영향을 주지 않는다.
- 같은 code/provider 쌍만 이름·로고를 갱신하고 없는 쌍은 추가한다. 기존 ID는 재할당하지 않는다.
  두 식별자가 서로 다른 행을 가리키거나 한쪽이 바뀌면 전체 카탈로그 적용이 실패한다.
- 카탈로그 검증·갱신·삽입은 하나의 트랜잭션이다. `otts` 쓰기를 직렬화하는 테이블 잠금을
  COMMIT까지 유지한다. 기존 ID의 구독·감상 FK 참조와 조회는 허용되며 관계 행을 건드리지 않는다.
- 카탈로그 단계의 입력/SQL 오류는 종료 코드 `2`다. SQL 오류·연결 종료가 COMMIT 전에 발생하면
  전체 카탈로그 변경이 롤백된다. **COMMIT 응답 유실이면 성공 여부가 불명확하다.** 위 조회로
  결과를 대조한 후 동일 승인 CSV로 재시도한다. 동일 쌍의 재적용은 기존 ID를 바꾸지 않는다.
- 원인 확인 전 ID/code/provider를 강제로 고치거나 행·참조를 삭제하지 않는다. 충돌이면 기존
  DB와 승인 CSV의 어느 쪽이 맞는지 담당자가 판단해야 한다. 해결 후 같은 명령을 재실행한다.
- 기존 ID를 수동으로 넣어 identity sequence가 뒤처진 DB는 새 행 INSERT가 PK 충돌로 실패할 수
  있다. 이 경우도 카탈로그 전체가 롤백된다. 스크립트는 sequence를 임의 보정하지 않는다.
  DB 담당자가 원인과 보정 범위를 확인해야 하며, 단순 오류를 기존 ID 재할당으로 해결하지 않는다.
  PostgreSQL sequence 값 소비는 트랜잭션 rollback 대상이 아니므로 실패 후 ID에 빈 번호가 생길 수 있다.
- 카탈로그 COMMIT 뒤에는 영화별로 별도 트랜잭션이 실행된다. 이후 영화/내보내기 실패의 코드 `3`은
  이미 성공한 카탈로그나 앞선 영화까지 되돌렸다는 뜻이 아니다. manifest·failure-report·checkpoint로
  실패 범위를 확인하고 기존 README의 재처리 절차를 따른다. 출력 manifest도 DB와 별도 파일이다.
- `--dry-run`은 CSV 형식/중복을 검증하지만 DB를 읽지 않아 기존 식별자 충돌을 보증하지 않는다.
  `--validate-only`는 영화 입력 검증 전용이다. 두 옵션 모두 초기화 성공의 증거가 아니다.

## 지원 목록과 기존 설정 보존

OTT 지원 종료는 서비스 운영 범위에 없다. 운영자가 OTT를 제거·비활성화하거나 기존 구독을
일괄 해제하지 않는다. 참조 유무와 무관하게 기준정보 물리 삭제 금지 규칙을 유지한다.

API-025는 모든 `otts` 행을 `ottId` 오름차순으로 반환하고, API-027은 존재하는 ottId의
선택·유지·사용자에 의한 해제를 계속 허용한다. 없는 ottId는 기존 계약대로
`400 VALIDATION_FAILED`이며 기존 구독 교체도 롤백된다. API-025의
`public, max-age=86400` 캐시에서 받은 기존 ottId에도 같은 규칙이 적용된다.

승인 CSV에서 행을 지워도 OTT 행은 삭제되지 않는다. 반면 그 CSV로 `--refresh`하면 영화별
제공처는 CSV의 provider만으로 다시 구성되므로, CSV 행 제거를 지원 종료 수단으로 사용하지 않는다.
기존 구독·영화 관계·감상 이력을 보존하는 초기화와 승인 매핑에 따른 적재만 수행한다.

## 임시 환경 검증

```bash
bash backend/scripts/tests/ott-catalog-regression-test.sh
bash backend/scripts/tests/initial-data-load-test.sh
```

첫 명령은 격리 PostgreSQL에서 카탈로그 실패·재시도·동시 적재·기존 참조 보존과 위 조회 SQL을
검증한다. 두 번째는 기존 적재 회귀를 포함한다. 실제 운영 DB·TMDb 네트워크 적용을 검증했다는
뜻은 아니다. 지원 종료는 범위 밖이며 별도 실행 명령을 두지 않는다. 실제 Flyway 초기화와 API 검증은
`OttCatalogSeedMigrationTest`, `OttBootstrapApiContractTest`에서 수행한다.
