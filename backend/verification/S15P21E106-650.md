2026-09-19, S15P21E106-614·630이 병합된 `develop` 기준으로 S15P21E106-650을 검증했다. DB 스키마·공개 API 필드는 바꾸지 않았다.

## 환경과 방법

- 로컬 격리 PostgreSQL 17 `feelm_search_eval`: 영화 237,817편, 인물 1,211,558명. 운영 DB는 변경하지 않았다.
- 백엔드 `local` 프로파일, mock 인증, Flyway 비활성화, `GET /api/v1/movies/search?size=20&q=...`를 사용했다.
- 필터 결합 측정에는 실제 필터 옵션의 로맨스 `TMDB_10749`, 드라마 `TMDB_18`을 사용했다.
- 각 검색어를 21회 연속 호출해 첫 호출을 제외한 20회의 중앙값(p50)과 95번째 백분위값(p95, 가까운 순위)을 계산했다. 로컬 단일 요청 측정이며 배포 환경·동시 사용자의 p95 보장은 아니다.
- PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`로 공백 보정 제목·인물명 후보가 기존 GIN trigram 인덱스를 쓰는지 확인했다. 읽기 전용 트랜잭션에서 설정한 후보 임계값이 COMMIT 뒤 기본값 0.6으로 돌아오는지도 확인했다.

## 실행 계획과 의미

- `노팅힐` 공백 보정 전체 검색 SQL의 재현 계획: `ix_movies_title_trgm`·`ix_movies_original_title_trgm` Bitmap Index Scan, 제목 인덱스 후보 473개, DB 실행 7.8ms. SQL 로그의 검색어 바인딩을 재현한 `EXPLAIN (ANALYZE, BUFFERS)` 결과이며 실제 API 시간은 위 표다.
- `크리스토퍼놀란` 공백 보정 인물 후보 조건: `ix_people_name_trgm` Bitmap Index Scan, 195명 후보, DB 실행 1.45ms. 단독 후보 조회의 실행 계획이므로 전체 검색 SQL·API 시간과 구분한다.
- 첫 구현의 동적 `generate_series` 오타 비교는 같은 `노팅힐` 전체 SQL 계획에서 JIT 컴파일 약 1.35초를 유발해 API p50 약 1.45초였다. 문자 배열 `unnest`로 바꾸자 SQL 비용 추정이 JIT 기준 아래로 내려가고, 같은 계획에서 JIT가 사라졌다. API도 위 표처럼 재측정했다.
- 두 계획 모두 `relaxed_setting` materialized CTE에서 트랜잭션 한정 `pg_trgm.word_similarity_threshold`를 설정했다. 같은 연결에서 트랜잭션 전 0.6, 검색 중 0.25, COMMIT 후 0.6을 확인했다.
- 완전 일치, 공백만 다른 제목·인물, 한 음절 치환 순으로 단계 점수를 부여한다. 제목·원제·감독·배우 및 장르·국가·OTT·연도 필터와 세 정렬의 계약 테스트를 실행했다.

## 남은 한계

- 공백을 제거한 표현식에 새 인덱스를 만들지 않았으므로 **저장된 제목·인물명의 모든 글자 사이에 공백이 들어간 경우**까지 빠르게 찾는 것을 보장하지 않는다. Jira -650의 DB 스키마 변경 금지 조건을 지킨 결과다. 보통의 단어 사이 공백 차이, 입력 쪽의 과도한 공백, 한 음절 치환을 검증했다.
- `해리포터`에서는 20주년 다큐멘터리가 극영화보다 먼저 나온다. 전 영화의 `movielens_id`와 서비스 `rating_count`가 비어 있는 격리 DB에서 같은 접두 단계가 ID와 유사도에 의존한 결과다. 공백 보정으로 검색 누락은 해결했지만 시리즈 전체의 인기 순위를 보장하지 않는다.
- `스`·`sp`의 짧은 검색어 지연은 -630 범위의 기존 경로다. 한 음절 치환 외 삽입·삭제 오타와 완전히 다른 표기의 검색은 이번 범위가 아니다.
