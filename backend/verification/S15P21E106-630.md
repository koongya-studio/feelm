# 짧은 영화 검색어 성능 검증

2026-09-19, S15P21E106-614가 병합된 최신 `develop` 위에서 S15P21E106-630을 측정했다. 배포 환경의 지연 시간을 뜻하지 않는다.

## 환경과 방법

- 로컬 격리 PostgreSQL 17 DB `feelm_search_eval`: 영화 237,817편, 인물 1,211,558명. 운영 DB를 변경하지 않았다.
- 변경 전후 동일 작업 트리·DB·`local` 프로파일·mock 인증을 사용했다. Flyway를 끄고 `GET /api/v1/movies/search?size=20&q=...`를 호출했다.
- 각 검색어를 연속 5회 호출했다. 첫 호출은 준비 호출로 보고 나머지 4회의 중앙값을 비교했다. 측정 간 DB 캐시와 다른 로컬 작업의 영향을 완전히 통제하지 못했다.
- 변경 전후 각 8개 조합의 첫 페이지 `totalCount`, 영화 ID 순서, `hasNext`, `nextCursor`를 그대로 비교했다. 조합은 `스`, `스파`, `sp`, `스파이`, `스파`의 평점순·최신순, 장르 필터 2개다.

## 원인과 수정

1·2글자 한글 음절의 부분 문자열 후보를 찾을 때 DB는 기존 GIN trigram 인덱스를 활용하지 못하고 전체 스캔한다. `movie_search_normalize(name)`로 인물명 121만 개를 비교한 `EXPLAIN (ANALYZE, BUFFERS)`는 `스`에서 307ms였다. 원문 `name LIKE '%스%'`는 같은 3,162명의 후보를 41ms에 찾았다. 영화 제목·원제의 `스파` 원문 검사도 정규화 검사보다 빨랐다.

한글 1·2음절 검색어에서는 제목·원제·인물명에 대한 문자 일치 후보 검사와 정확·접두 판정에 원문 `LIKE`/`=`를 쓴다. 소문자화와 그리스 시그마 통일은 한글 음절을 바꾸지 않으므로 후보 의미는 같다. 관련도 유사도·full-text 점수와 MovieLens·한국어·아랍 문자 신호는 기존 계산을 유지한다. 그 외 검색어·3글자 이상은 기존 SQL을 유지한다. 인덱스·migration·API 필드 변경은 없다.

## 정합성·남은 한계

- 변경 전후 실데이터 8개 조합의 결과 수·첫 페이지 영화 ID 순서·`hasNext`·`nextCursor`가 모두 같았다. `스파` 원문/정규화 제목·인물 후보를 양방향 `EXCEPT`로 비교한 차이도 0건이다.
- Testcontainers 검색 계약 테스트에서 짧은 한글의 제목·원제·감독, 필터, 관련도·평점·개봉일 정렬과 size=1 cursor를 확인한다.
- `sp` 같은 영문 2글자와 그리스 문자 검색은 기존 정규화 경로라 이번 개선 효과가 없다. 한 글자 `스`는 여전히 예열 중앙값 약 0.5초로, 38,519건 전체 건수·정렬 계산이 남는다. 동시 사용자·콜드 캐시·배포 DB p95는 별도 측정이 필요하다.
