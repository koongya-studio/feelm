# 계정 보안 기능 검증 기록

2026-09-11, `develop` `7b03c4a` 기준으로 로그인 시도 제한, 계정 메일 발송 제한과 전역 상한,
사용자 차단, 토큰 수명 관리를 실제로 돌려 본 결과입니다.

**이 기록은 로컬 확인 결과이며 배포 환경 검증 완료를 뜻하지 않습니다.** 배포에서 다시 봐야
하는 항목은 5장에 있습니다.

범위는 백엔드가 단독으로 확인할 수 있는 것까지입니다. 같은 회차에 프론트엔드 세션 거동과
가입부터 로그인까지의 화면 시나리오도 확인했으며, 그 결과는 각 변경을 만든 MR 본문에
있습니다(S15P21E106-364·373·366).

## 1. 왜 남기는가

이 기능들은 자동 테스트로 덮기가 어렵습니다.

| 기능 | 자동화가 어려운 이유 |
| --- | --- |
| IP 축 로그인 제한 | 한도가 10분 60회라 서로 다른 이메일로 예순 번 넘게 보내야 경계가 드러납니다 |
| 이메일 축 로그인 제한 | 창이 10분이라 창을 넘기려면 기다리거나 카운터를 직접 비워야 합니다 |
| 메일 IP 제한 | 세 경로가 카운터를 공유하는지 보려면 한 경로로 한도를 채우고 다른 경로를 불러야 합니다 |
| 전역 발송 상한 | 상한만큼 실제로 보내거나 설정을 낮춰야 합니다 |
| Access Token 만료 | 수명이 30분이라 낮추지 않으면 만료를 기다려야 합니다 |

모두 Redis 상태와 시간 창에 얽혀 있어, 시나리오 사이에 카운터를 비우지 않으면 앞 시나리오가
IP 예산을 태운 채로 다음이 돌아 결과가 섞입니다. 절차를 남기지 않으면 다음 사람이 처음부터
다시 만들어야 합니다.

결함과 후속 업무는 Jira에 있으므로 여기에 다시 적지 않고 가리키기만 합니다.

## 2. 사전 준비

저장소 루트에서 데이터 저장소를 띄웁니다. `infra/.env`가 필요합니다(`backend/README.md`).

```bash
docker compose --env-file infra/.env \
  -f infra/compose/service.yml -f infra/compose/local.yml \
  up -d postgres redis
```

`backend`를 작업 디렉터리로 백엔드를 띄웁니다. `MAIL_MODE=log`여야 발송 대신 링크가 로그에
남습니다.

```bash
./gradlew bootRun --args='--spring.profiles.active=local'
```

**시나리오 사이마다 카운터를 비웁니다.** 비우지 않으면 앞 시나리오가 쓴 IP 예산이 남아
결과가 달라집니다.

```bash
docker exec feelm-redis redis-cli -a <REDIS_PASSWORD> --no-auth-warning FLUSHALL
```

Access Token 만료를 확인할 때만 수명을 줄여 띄웁니다. 설정 파일을 고치지 않고 인자로 넘깁니다.

```bash
./gradlew bootRun --args='--spring.profiles.active=local --feelm.jwt.access-token-ttl=40s'
```

전역 발송 상한을 확인할 때만 `backend/.env`에 `MAIL_SEND_BUDGET_HOURLY_LIMIT=3`을 넣고
다시 띄운 뒤, 확인이 끝나면 지웁니다.

## 3. 확인한 것

기준은 `docs/api/users.md`의 API-001·003·004·020~022와 공통 규약입니다.

### 3.1 로그인 시도 제한 (API-004)

| 시나리오 | 절차 | 결과 |
| --- | --- | --- |
| 이메일 축 한도 | 같은 이메일로 틀린 비밀번호를 일곱 번 보냅니다 | 다섯 번째까지 `401 INVALID_CREDENTIALS`, 여섯 번째부터 `429 RATE_LIMITED` |
| 시도를 센다 | 한도를 넘긴 상태에서 **올바른** 비밀번호로 보냅니다 | `429`. 비밀번호를 대조하지 않습니다 |
| 성공 시 초기화 | 네 번 실패 후 로그인에 성공하고 다시 실패를 쌓습니다 | 다섯 번째까지 `401`로 돌아옵니다 |
| IP 축 한도 | 이메일을 매번 바꿔 예순다섯 번 보냅니다 | 예순 번째까지 `401`, **예순한 번째부터** `429` |
| 계정 잠금이 번지지 않음 | IP 한도를 넘긴 상태에서 처음 보는 이메일로 한 번 보냅니다 | `429`. Redis 키 수가 그대로여서 그 이메일의 카운터가 생기지 않았습니다 |
| 계정 존재 노출 | 가입된 이메일과 없는 이메일의 응답을 비교합니다 | 상태·코드·본문이 같고, 없는 이메일도 여섯 번째에 `429`가 됩니다 |

이메일을 매번 바꾸는 이유는 이메일 축이 먼저 걸리면 IP 축 경계를 볼 수 없기 때문입니다.
계약의 평가 순서가 IP → 이메일이라는 것이 다섯 번째 줄에서 드러납니다.

### 3.2 계정 메일 제한 (API-001·003·010)

| 시나리오 | 절차 | 결과 |
| --- | --- | --- |
| IP 단위 요청 제한 | 재설정 요청을 서른 번 보냅니다 | 서른 번째까지 `202`, 서른한 번째 `429 RATE_LIMITED` |
| 세 경로가 카운터 공유 | 위 상태에서 가입과 재발송을 부릅니다 | 둘 다 `429` |
| 제한이 중복 검사보다 먼저 | 위 상태에서 **이미 가입된** 이메일로 가입합니다 | `EMAIL_DUPLICATED`가 아니라 `429`. 한도가 이메일 사용 여부를 알려주지 않습니다 |
| 이메일 단위 간격 | 같은 이메일로 재발송을 연이어 두 번 보냅니다 | 두 번째 `429`, 다른 이메일은 `202` |
| 발송 낭비 방지 | 인증을 마친 계정과 없는 계정에 재발송을 부릅니다 | `202`를 주지만 발송 로그가 남지 않습니다. 미인증 계정만 실제로 나갑니다 |
| 전역 발송 상한 | 시간당 상한을 3으로 낮추고 다섯 번 가입합니다 | 다섯 번 모두 `201`이고 발송은 세 건에서 멈춥니다. 상한의 80% 도달과 초과에 각각 `WARN`이 남습니다 |

다섯 번째 줄은 대조군이 필요합니다. 발송 0건이 "차단됨"인지 "발송기 고장"인지 구분되지
않으므로, 미인증 계정으로 한 번 보내 로그가 남는 것을 함께 확인합니다.

여섯 번째 줄의 `201`은 계약대로입니다. 상한을 넘겨도 응답은 바뀌지 않고 메일만 나가지
않으며, 복구 경로는 재발송입니다.

### 3.3 사용자 차단 (API-020~022)

| 시나리오 | 결과 |
| --- | --- |
| 차단 | `201` + `blockedUserId`·`blockedAt` |
| 같은 사람 재차단 | `409 ALREADY_BLOCKED` |
| 자기 자신 차단 | `400 CANNOT_BLOCK_SELF` |
| 없는 사용자 차단 | `404 RESOURCE_NOT_FOUND` |
| 차단 해제와 재시도 | 둘 다 `204`. 차단 관계가 없어도 `204`입니다 |
| 차단 목록 | 공통 커서 페이지네이션 구조 |

공통 차단 필터도 확인했습니다. 차단한 상대가 파티 초대를 수락하려 하면 `404`로 막혀 두
사람이 같은 활성 파티에 남지 않습니다. 다만 **초대는 `PENDING`으로 남아** 양쪽 목록에
계속 보입니다. 차단 시 초대를 무효화하는 것은 S15P21E106-359 범위이며 아직 구현 전입니다.

### 3.4 토큰 수명 (API-004~006)

| 시나리오 | 결과 |
| --- | --- |
| 재발급 | 새 Access Token과 회전된 Refresh 쿠키 |
| 회전된 이전 토큰 재사용 | `401 REFRESH_TOKEN_INVALID` |
| 로그아웃 | `204` + `Max-Age=0` 쿠키 삭제. 이후 재발급 `401` |
| Access Token 만료 | `401 TOKEN_EXPIRED` |
| 토큰 없음·서명 위조 | `401 UNAUTHORIZED` |

마지막 두 줄이 갈리는 것이 중요합니다. 클라이언트는 `TOKEN_EXPIRED`를 재발급 신호로
씁니다(공통 규약).

재발급을 짧은 간격으로 두 번 부르면 같은 Access Token이 나올 수 있습니다. `iat`·`exp`가 초
단위라 같은 초에 발급되면 내용이 같아지는 것이며 결함이 아닙니다.

### 3.5 공통 오류 계약

없는 경로 `404 RESOURCE_NOT_FOUND`, 허용하지 않는 메서드 `405 METHOD_NOT_ALLOWED`,
잘못된 `Content-Type` `415 UNSUPPORTED_MEDIA_TYPE`, 토큰 없이 회원 API `401 UNAUTHORIZED`,
남의 비공개 리소스 `404`를 확인했습니다.

### 3.6 계약과 실제 응답 대조

앞으로 연동할 도메인의 응답을 `docs/api`와 하나씩 맞춰 봤습니다. 화면이 계약을 보고 타입을
만드므로, 어긋난 채로 연동하면 그 도메인 전체를 다시 손대게 됩니다.

| 대상 | 결과 |
| --- | --- |
| API-014 `/users/me` | 문서 예시의 필드가 모두 일치합니다 |
| API-020·022 차단 | 일치합니다 |
| API-050 `/parties` | 필드가 모두 일치합니다 |

**문서 쪽에 흠이 하나 있습니다.** `docs/api/party.md` API-050 응답 예시에 `nextCursor`와
`hasNext`가 빠져 있습니다. 실제 응답에는 있고 공통 규약도 커서 페이지네이션을 그렇게
정의하므로 구현이 옳지만, 예시만 보고 타입을 만들면 두 필드를 빠뜨립니다.

프론트엔드 쪽에도 차이가 있습니다. `frontend/src/types/party.ts`의 `Party`에 `owner`와
`pendingInvitations`가 없고 `PartyMember`에 `joinedAt`이 없습니다. 실제 응답에는 모두
있으므로, 파티를 연동할 때 화면이 그 정보를 그릴지 먼저 정해야 합니다.

## 5. 배포 환경에 남은 검증

로컬에서는 확인할 수 없어 서버에서 봐야 하는 것들입니다.

- **Nginx를 거칠 때 IP 축의 예산 주체.** 로컬은 모든 요청이 `127.0.0.1`이라 신뢰 프록시가
  보낸 `X-Real-IP`를 쓰는 경로가 실제로 동작하는지 드러나지 않습니다. 헤더로 예산 주체를
  바꿀 수 없어야 합니다(ADR-0019, S15P21E106-326)
- **실제 SMTP에서 전역 발송 상한.** 로컬은 `MAIL_MODE=log`라 발송 수단이 다릅니다
- **배포 `FRONTEND_BASE_URL` 기준 메일 링크.** 링크 경로는 S15P21E106-367에서 고쳤고
  로컬에서 화면이 열리는 것까지 확인했지만 배포 주소로는 확인하지 못했습니다
- **공유 NAT에서의 IP 한도.** 기본값은 캠퍼스망·시연 환경에서 로그인이 몰리는 구간을
  통과하도록 정한 값이며, 실제 시연 환경에서 정상 사용자가 `429`를 받지 않는지 봐야 합니다

## 6. 재현에 쓴 도구

모두 `curl`과 `docker exec`입니다. 저장소에 스크립트를 두지 않았습니다. 절차가 짧고,
스크립트를 두면 계약이 바뀔 때 함께 낡기 때문입니다. 한글이 들어간 요청은 셸 인코딩에 따라
`VALIDATION_FAILED`가 날 수 있으므로 아스키 값으로 확인하거나 브라우저를 씁니다.
