# Spring 테스트 Context 재사용 검증 기록

S15P21E106-695는 공유 PostgreSQL 기반 `@SpringBootTest`의 중복 설정을 공통 지원 클래스로
모아 Spring Test Context 재사용률을 높이는 작업이다. 테스트 범위, assertion, 병렬 실행 정책은
변경하지 않는다.

## 1. 변경 전 기준

S15P21E106-608에서 동일 SHA로 성공한 `backend-mr-test` 3회의 측정값이다.

| 항목 | 1회 | 2회 | 3회 | 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| Job | 8분 10초 | 8분 30초 | 8분 47초 | 8분 30초 |
| Gradle | 403.096초 | 408.162초 | 431.277초 | 408.162초 |
| `:test` | 283.907초 | 293.277초 | 312.203초 | 293.277초 |
| 테스트 클래스 lifecycle | 164.710초 | 166.234초 | 185.362초 | 166.234초 |

세 실행 모두 1,817개 테스트가 성공했고 cleanup도 완료됐다. 이 값은 `9b0f69e2` 기준이므로,
최신 `develop`의 같은 소스 집합으로 변경 전·후 3회를 다시 비교한다.

2026-09-20 추가 작업의 목표는 사용자가 지정한 lifecycle 중앙값 **198초 → 178초 이하**다.
이는 위 608의 과거 기준선과 구분한다. 198초의 원시 실행 자료는 이번 작업에서 재측정하지
않았으며, 아래 변경만으로 목표를 달성했다고 판정하지 않는다.

## 2. Context 분리 원인과 변경

공유 PostgreSQL 테스트는 테스트 프로필에서 이미 인증 mock을 비활성화하지만, 여섯 클래스가
`@SpringBootTest(properties=...)`에 같은 값을 반복해 Spring Context cache key를 갈랐다.

- `SharedPostgresContractTest`가 `feelm.auth.mock.enabled=false`를 공통 적용한다.
- 하위 여섯 클래스의 중복 속성을 제거한다.
- 정책 테스트가 공통 설정의 존재와 하위 클래스의 중복 재발을 검사한다.

정적 annotation 속성 집계에서 표준 공유 PostgreSQL 그룹은 29개에서 34개로, scheduling 비활성
그룹은 8개에서 9개로 합쳐졌다. 통합 전 두 그룹이던 테스트들이 각각 같은 Context 후보가 된
것이며, 실제 cache hit와 시간 개선은 CI 측정으로 확정한다.

### BackendApplicationTests 통합 시도와 원복

기본 H2·Hibernate create-drop 설정의 `BackendApplicationTests`를 기존 PostgreSQL 계약
테스트 Context에 합치는 시도를 했다. 테스트 메서드 `contextLoads()`는 유지하고 Flyway,
PostgreSQL, Redis와 MockMvc 구성을 `MovieFilterOptionsContractTest`에 맞췄다.

| Context 구성 | 시도한 구성 | 비교 대상 |
| --- | --- | --- |
| SpringBootTest 속성 | Flyway 활성화, Hibernate DDL none | `MovieFilterOptionsContractTest`와 동일 |
| Web environment | 기본 MOCK | 동일 |
| MockMvc | 기본 `@AutoConfigureMockMvc` | 동일 |
| PostgreSQL 동적 속성 | `SharedPostgresContractTest` 상속 | 같은 선언 메서드 |
| 인증 mock | 상위 클래스의 false 속성 상속 | 동일 |
| Redis ServiceConnection | `SharedRedisContainer.instance()` | 같은 컨테이너 객체 |
| 실행 격리 | 상위 클래스의 `@SharedTestRuntime` 상속 | 기존 resource lock 유지 |

동일 커밋의 성공 실행 3회에서 lifecycle 중앙값이 206.403초로 측정돼 178초 이하 목표를
충족하지 못했다. `BackendApplicationTests`에 귀속된 lifecycle도 중앙값 36.891초로 남았다.
이 값만으로 cache miss를 확정할 수는 없지만, 전체 lifecycle 개선 효과가 입증되지 않았고
해당 테스트를 단독 실행할 때 Docker가 새로 필요해지는 비용이 생겼다. 따라서 이 통합은
채택하지 않고 기존 H2 기동 테스트와 `@SharedTestRuntime` 구성으로 원복했다.

로컬에 설치된 Spring Boot 4.1.1 소스의 `ServiceConnectionContextCustomizer.CacheKey`는
필드 선언 클래스가 아니라 connection name, connection details types, container 객체,
SSL bundle source를 비교한다. 두 테스트의 Redis 필드가 서로 다른 클래스에 선언되어도
같은 singleton 객체와 기본 annotation 설정을 사용하므로 이 요인으로 key가 갈라지지 않는다.
트랜잭션 annotation은 테스트 실행 제어이며 Context 구성 차이가 아니다.
이는 통합을 시도할 당시의 소스 비교 근거이며 실제 cache hit 측정 결과는 아니다. 향후
진단 실행에서 cache hit/miss를 직접 확인하되, 그 실행은 성능 중앙값에 포함하지 않는다.

최종 변경에는 공유 PostgreSQL 테스트의 중복 인증 mock 설정 통합과 재발 방지 정책 테스트만
남는다. 운영 설정·API·DB schema·migration SQL·빌드 설정은 변경하지 않는다.

## 3. 로컬 검증

```powershell
.\gradlew.bat test --tests com.feelm.backend.support.SharedTestcontainerPolicyTest --tests com.feelm.backend.support.ParallelTestExecutionPolicyTest compileTestJava spotlessCheck
```

- 정책 테스트 6개 성공, failures/errors/skipped 0 (2026-09-20 추가 변경 후 실행)
- 테스트 소스 컴파일 성공
- Spotless 성공
- `git diff --check` 성공

PostgreSQL 기동 테스트 통합을 원복한 뒤 아래 명령으로 다시 확인했다.

```powershell
.\gradlew.bat test --tests com.feelm.backend.BackendApplicationTests --tests com.feelm.backend.support.SharedTestcontainerPolicyTest --tests com.feelm.backend.support.ParallelTestExecutionPolicyTest compileTestJava spotlessCheck
```

- `BackendApplicationTests`가 Docker 없이 H2 Context로 성공
- 공유 컨테이너·병렬 실행 정책 테스트 6개 성공
- 테스트 소스 컴파일과 Spotless 성공 (`BUILD SUCCESSFUL`, 1분 13초)

전체 `.\gradlew.bat build`도 실행했으나 1분 25초 후 테스트 단계에서 실패했다.
JUnit XML 합계는 tests 1,254 / failures 689 / errors 0 / skipped 0이다.
실패 trace에서 Docker 탐색 실패(`Could not find a valid Docker environment`)와
공유 컨테이너 초기화 실패의 연쇄 `ExceptionInInitializerError`/`NoClassDefFoundError`가
확인됐다. `BackendApplicationTests`도 Context 로드 이전에 초기화 실패했다.
따라서 이 테스트 수는 정상적으로 발견·실행되는 전체 테스트 수의 기준으로 사용할 수 없고,
Context 재사용과 성능 목표도 이 환경에서 검증할 수 없다.

로컬 진단 자료는 `backend/build/695-build.log`와 `backend/build/test-results/test/`에 있다.
Jira 요구사항·담당자·상태를 조회했으며, 상태는 변경하지 않았다. GitLab 열린 MR 조회는
API 401로 확인하지 못했다. 작업 시작 시 `HEAD...origin/develop`은 0/0이었다.
최종 확인 도중 develop에 프론트엔드 713의 2개 커밋(`479944dc`)이 추가되어 0/2가 됐으나,
변경 파일은 모두 frontend 아래이며 이번 변경 경로와 겹치지 않았다. 패치 적용 충돌과
`git diff --check` 오류는 없었다. 커밋·push·MR 생성은 수행하지 않았다.

## 4. 병합 전 CI 판정

동일한 최신 `develop` 소스 집합에서 이 테스트 변경의 적용 전·후 `backend-mr-test`를
각각 3회 실행한다. 두 버전의 차이는 이 작업의 테스트 변경으로 한정하고, 같은 runner,
캐시·이미지 준비 조건과 병렬 설정을 사용한다.

- 세 실행 모두 전체 테스트 성공, 누락 클래스 0, cleanup 성공
- 테스트 수와 테스트 범위에 의도하지 않은 감소 없음
- 변경 전·후 같은 소스 집합 3회 중앙값 비교
- 테스트 클래스 lifecycle 중앙값 10% 이상 감소하고 사용자 목표 178초 이하인지 확인
- Job, Gradle, `:test` 시간도 함께 기록

변동이 큰 단일 실행이나 소스 집합이 서로 다른 결과만으로 개선을 확정하지 않는다.
변경 전후 SHA는 달라도 되지만 기능 코드와 테스트 집합이 같은 통제된 비교여야 한다.

Context 재사용 확인용 실행에서는 Spring의 `org.springframework.test.context.cache` DEBUG
로그를 별도로 수집하고, `BackendApplicationTests`와 위 비교 대상이 같은 Context를 쓰는지
확인한다. 상세 로그를 켠 실행의 시간은 성능 중앙값 측정에 섞지 않는다.
시간은 기존 `infra/scripts/ci-job-io.py`의 `test_class_lifecycle_seconds`,
`test_task_seconds` 및 전체 Job 지표로 비교한다. lifecycle은 Context 시작뿐 아니라
클래스 fixture 등도 포함하므로, 기동 테스트의 약 30초가 모두 절약된다고 가정하지 않는다.
