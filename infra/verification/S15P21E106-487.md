# S15P21E106-487 검증 기록

## 범위

보호된 `main`에서 게시한 Fold-in Consumer 커밋 SHA 이미지를 J15E106A에 자동 배포하고,
Consumer 전용 런타임 검증 실패 시 직전 이미지를 복구한다. Spark 배치 실행, 추천 산출물 생성과
기존 사용자 후보 전체 재게시 자동화는 포함하지 않는다.

## 로컬 검증

- 최신 `origin/develop` (`cc0c9f2`) 기준으로 재배치했으며 변경 대상 파일 충돌이 없었다.
- Consumer Ruff와 전체 pytest는 `206 passed, 9 skipped`로 통과했다. skip은 실제 PostgreSQL·Redis
  통합 환경이 필요한 기존 테스트다.
- 배포·Redis E2E·CI 계약 unittest 50건과 최종 전체 infra config test 91건이 통과했다.
- GitLab CI YAML 파싱, Bash 구문 검사와 `git diff --check`가 통과했다.

- 후보 이미지 준비 전 Pull 실패와 Compose 설정 실패가 실행 중 Consumer를 변경하지 않음을
  모의 검증했다.
- 후보 Compose 교체 실패, 프로세스 종료·재시작 및 Kafka 파티션 미할당을 배포 실패로 처리하고
  직전 이미지를 복구함을 확인했다.
- 복구된 Consumer도 새 Kafka Consumer ID로 모든 대상 파티션을 할당받아야 성공하도록 검증했다.
- 상태 파일이 없는 자동 배포는 컨테이너 변경 전에 실패하며, 정상 실행·재시작 0·전체 파티션
  할당을 확인하는 명시적 `--initialize-state` 실행만 최초 LKG를 기록함을 모의 검증했다.
- CI 계약 테스트에서 보호된 `main` push, 불변 SHA 이미지, `consumer-image` 선행,
  `e106-distributed` 전용 Runner, 배포 직렬화와 비취소 조건을 확인했다.
- 배포 스크립트는 `consumer` 서비스만 `--no-deps --force-recreate`하며 `down` 또는 볼륨 작업을
  실행하지 않는다.
- Registry digest를 매번 pull하고, 마지막 검증 완료 digest를 서버 상태 파일에 원자적으로 기록해
  Runner 강제 종료 후 재시도에도 실패 후보를 롤백 기준으로 사용하지 않음을 모의 검증했다.
- 후보 교체 뒤 상태 기록 전에 Runner가 종료된 재시도는 실제 이미지와 LKG 불일치를 먼저 복구한
  뒤 후보 pull 또는 stale commit 판정으로 진행함을 모의 검증했다.
- 상태 변경 직전과 런타임 검증 완료 직전에 원격 `main` HEAD를 다시 확인하며, Registry 인증은
  Job별 Docker config에서 logout·삭제하도록 CI 계약을 검증했다.
- Consumer 진입점이 INFO 로그를 활성화하고 산출물 로딩, Kafka 파티션 할당·해제, Redis 게시와
  offset commit을 payload·접속정보·사용자·generation 식별자 없이 기록하도록 검증했다. 실패 시
  원문 컨테이너 로그도 CI로 복사하지 않는다.
- Redis E2E 검증기가 세 키를 한 번의 `MGET`으로 읽고 게시 순번 증가, Candidate v4와 동일
  generation, taste/discovery 배열을 확인하며 접속정보와 payload를 출력하지 않도록 검증했다.

## 서버 및 GitLab 남은 검증

- J15E106A에 프로젝트 전용 `e106-distributed` Runner를 등록하고 Protected·Locked·Run untagged
  비활성 상태를 확인한다.
- 현재 정상 Consumer를 확인한 뒤 Runner 계정으로 `deploy-consumer.sh --initialize-state`를 한 번
  실행하고, LKG 상태 파일이 현재 이미지 digest를 기록했는지 확인한다.
- `distributed` 환경 범위에 File 타입·Protected `CONSUMER_COMPOSE_ENV_FILE`을 등록하고 Job
  로그에 파일 내용과 Secret이 출력되지 않는지 확인한다.
- Consumer 변경이 포함된 보호된 `main` push에서 테스트, 이미지 게시와 자동 배포가 순서대로
  성공하는지 확인한다.
- 정상 배포 후 실행 이미지, 재시작 횟수 0, 새 Consumer ID의 전체 파티션 할당과 실제 이벤트의
  Redis 후보 세 키 갱신을 확인한다.
- 승인된 테스트 사용자로 offset commit, 정상 재시작·실제 group rebalance 후 재처리와 동일
  generation을 확인한다. 의도적 pause는 격리된 토픽·복구 offset이 승인된 경우에만 수행한다.
- 후보 실패 후 자동 롤백 성공과 롤백 실패 시 수동 복구 안내를 유지보수 시간에 검증한다.
- Candidate v4 Spring reader는 현재 `develop`에 없으므로 병합 전제조건을 충족하지 않는다.
  reader 업무 병합 후 서비스 조회 호환성을 별도로 검증한다.

위 실환경 항목을 수행하기 전에는 자동 배포 완료로 표시하지 않는다.
