# S15P21E106-847 GBT 분산 학습 성능 검증 기록

검증일: 2026-09-25. 발표용 합성 데이터에서 Spark Worker 1대와 2대의
`SparkXGBRegressor.fit()` 경과 시간을 비교했다. 운영 v26 모델의 학습이나 온라인 추천
응답 시간은 측정하지 않았다. 발표용 요약은
[Notion 검증 기록](https://app.notion.com/p/3e6a10dfbffa812888bcde3dc87771f0)에 있다.

## 결론

- 10만·30만·100만 행은 각 조건 1회 측정에서 1대가 더 빨랐다.
- 200만 행은 각 조건 3회 측정의 `training_seconds` 중앙값이 **1대 38.230초,
  2대 23.592초**였다. 같은 입력의 학습 시간이 14.638초, **38.3% 감소**했다
  (`38.229842921 / 23.591528018 = 1.6205`배 속도 향상).
- Spark History에서 200만 행의 `fit` stage task가 서로 다른 두 Worker 호스트에서
  각각 성공한 것을 확인했다. Worker가 단지 클러스터에 등록된 것만을 근거로 삼지 않았다.
- 이 결과는 이번 합성 데이터·모델 설정·서버 자원 조건에서의 관찰이다. 정확한 규모별
  손익 전환점이나 운영 추천 성능 개선률을 확정하지 않는다.

## 실험 조건

| 항목 | 조건 |
| --- | --- |
| 코드 revision | `5d21c24ea2497ee787296a69c4d14db395898f28` |
| 런타임 | Spark 4.1.3, XGBoost 2.1.4 CPU |
| 입력 | 고정 seed 42의 합성 label·feature 71개, 규모별 8 partitions |
| 모델 | `SparkXGBRegressor`, `reg:squarederror`, `n_estimators=30`, `max_depth=4`, `learning_rate=0.1`, seed 42 |
| Worker | 서로 다른 서버의 `spark-worker-1`, `spark-worker-2`; 각각 2 cores / 4 GiB 등록 |
| Executor | Worker당 2 cores / 2 GiB, `spark.task.cpus=2`; 1대는 총 2 executor cores, 2대는 총 4 executor cores |
| 저장 경로 | `hdfs://hdfs-namenode:8020/verification/S15P21E106-847/benchmark-20260925T072447Z` |

규모별 입력을 한 번 준비해 HDFS에 저장하고, **해당 규모의 1대·2대 실행에 동일한
입력 URI와 snapshot**을 사용했다. 입력 생성은 측정 대상이 아니다. 각 실행은 고유한
결과 URI를 사용했다. Worker 수 전환 시 서비스 서버의 Spark Worker 컨테이너만
중지·복구했으며 HDFS DataNode는 측정 대상으로 삼지 않았다.

`training_seconds`는 `fit()` 호출의 경과 시간이다. `total_seconds`에는 입력 무결성·행 수
확인과 Worker probe 등이 포함된다. 1대와 2대에서 총 CPU·메모리 자원도 함께 증가했으므로
**순수한 분산 프레임워크 효율만 분리한 비교는 아니다.**

실서버 `spark-submit`에는 Driver RPC `7079`, Driver BlockManager `7080`, Executor
BlockManager `7081`을 고정하고 `spark.port.maxRetries=0`을 설정했다. 기본 임의 Driver
포트로는 서비스 서버의 Executor가 등록되지 않았다. XGBoost tracker는 별도의 임시
포트를 사용해 두 서버 사이의 연결이 필요했다. 이 때문에 점검 중에만 두 서버의
사설 IP를 서로 출발지로 제한한 UFW 임시 규칙을 사용했다. 이 포트 조건은 아래의
운영 후속 확인과 함께 취급해야 한다.

## 규모별 첫 측정

| 입력 행 수 | 1대 `training_seconds` | 2대 `training_seconds` | 관찰 |
| ---: | ---: | ---: | --- |
| 100,000 | 11.115초 | 14.963초 | 1대가 빠름 |
| 300,000 | 13.898초 | 18.289초 | 1대가 빠름 |
| 1,000,000 | 24.148초 | 26.140초 | 1대가 소폭 빠름 |
| 2,000,000 | 37.994초 | 30.739초 | 2대가 빠름 |

10만·30만·100만 행은 **조건당 1회만** 실행했다. 작은 규모에서 2대가 느린 것은
분산 실행 비용이 작업량 대비 컸을 가능성을 시사하지만, 원인별 비용을 따로 계측하지
않았다. 100만~200만 행 사이의 정확한 전환점도 측정하지 않았다.

## 200만 행 반복 측정 원자료

같은 `input-2m` 저장본을 사용해 2대 → 1대 순서를 세 차례 반복했다. 아래 시간은
결과 JSON의 `training_seconds`다.

| 실행 순서 | Worker | 학습 시간 (초) | Spark application ID | HDFS 결과 디렉터리 |
| ---: | ---: | ---: | --- | --- |
| 7 | 2대 | 30.739379 | `app-20260925074926-0015` | `run-7-2m-workers-2` |
| 8 | 1대 | 37.993661 | `app-20260925075130-0016` | `run-8-2m-workers-1` |
| 9 | 2대 | 22.375206 | `app-20260925075410-0017` | `run-9-2m-workers-2` |
| 10 | 1대 | 38.463923 | `app-20260925075622-0018` | `run-10-2m-workers-1` |
| 11 | 2대 | 23.591528 | `app-20260925075921-0020` | `run-11-2m-workers-2` |
| 12 | 1대 | 38.229843 | `app-20260925080047-0021` | `run-12-2m-workers-1` |

- 1대 중앙값: **38.229842921초**; 2대 중앙값: **23.591528018초**.
- 중앙값 기준 감소율: `(38.229842921 - 23.591528018) / 38.229842921 × 100`
  = **38.29%**.
- 2대 측정값은 22.38~30.74초로 편차가 있다. 발표에는 중앙값과 3회 반복 사실을
  함께 표시하며, 매번 동일한 단축률을 보장한다고 해석하지 않는다.
- 참고로 200만 행 `total_seconds` 중앙값은 1대 약 54.23초, 2대 약 40.47초다.
  이는 입력 검증 등을 포함하므로 위의 학습 시간과 다른 지표다.

| Task | Executor | 실행 호스트 | 상태 |

## 해석 범위와 운영 확인

- 이 검증으로 말할 수 있는 것: **이번 환경에서 데이터 규모가 커지자 실제 두 Worker가
  학습을 나눠 수행했고, 200만 행의 3회 중앙값 기준 학습 시간이 줄었다.**
- 이 검증으로 말할 수 없는 것: 운영 v26 모델의 분산 재학습·정확도 개선, 실제 영화·평점
  데이터의 동일한 단축률, 추천 API 응답 속도 개선, 동시 사용자 처리량 개선.
- 최종 복구 상태는 대화에서 확인 출력을 받지 못했다. 서비스 서버의
  `feelm-spark-worker-1` 복구와 Spark Master의 Worker 2대 `ALIVE`를 확인해야 한다.
- XGBoost tracker 연결을 위해 양쪽 서버에 **서로의 사설 IP에서만**
  `32768:60999/tcp`를 임시 허용했다. 규칙 제거 확인 출력은 받지 못했다. 테스트를
  마쳤다면 양쪽 UFW에서 이 임시 규칙을 삭제하고 상태를 확인해야 한다.
