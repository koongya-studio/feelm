# S15P21E106-271 검증 기록

## 로컬 검증

- 캐시 CI context가 보호된 `develop` web pipeline과 정확한 MR 번호·40자리 SHA만 허용함을 확인했다.
- cache manager가 Job Token의 현재 Job 응답과 root 소유 운영자 허용 목록으로 실제 실행자를
  검증하고, Job·pipeline 식별 불일치와 미등록 사용자를 거부함을 단위 테스트로 확인했다.
- MR cache status Job이 고정된 Job·스크립트와 의존성 파일 변경만 허용하고 MR 코드를 실행하지
  않음을 단위 테스트로 확인했다.
- 후보 준비의 동적 revision·archive SHA가 cache manifest, server stage와 offline runtime까지
  전달됨을 확인했다.
- 전환 전 실행 중 작업 거부, 설정 원자 교체와 Runner 재시작 실패 시 이전 설정 복구를 확인했다.
- 기존 CI 격리 스크립트를 포함한 전체 `test_ci_*.py` 테스트 280개가 통과했고 18개 Linux 전용
  테스트는 Windows에서 건너뛰었다.
- Python 전체 구문 검사와 `git diff --check`가 통과했다.
- CI job token이 허용하지 않는 MR diff API 대신, 검증된 MR `diff_refs`를 Git으로 가져와
  의존성 파일과 선언 변경을 검사한다.
- GitLab CI Lint에서 현재 `.gitlab-ci.yml`의 `Syntax is correct` 결과를 확인했다.
- 최신 `origin/develop` `9ae4ab6`까지 반영했으며 271번 변경 파일과 겹치는 변경은
  없었다.

## 서버 및 GitLab 남은 검증

아래 항목은 아직 완료로 표시하지 않는다.

- 실제 pipeline 생성
- 실행자 검증 수정본의 서버 재설치와 root 소유 운영자 허용 목록 확인
- MR !98 HEAD의 온라인 캐시 생성과 독립 오프라인 전체 테스트
- 수동 promote 후 Runner 재시작·상태 확인과 MR !98 재실행
- 준비 실패·취소, 오래된 SHA 거부 및 실제 rollback 시나리오

## 병합 후 서버 확인

- 서비스 서버 프로세스에서 `e106-shell` Runner가 `--user gitlab-runner`로 실행됨을 확인했다.
- 최초 병합본의 cache manager sudoers 대상이 `ubuntu`여서 실제 Runner 계정과 불일치했다.
  서버 설치 전에 대상을 `gitlab-runner`로 수정하고 회귀 테스트를 추가했다.
- 업로드가 출력한 첫 stage 경로는 재접속한 서버에서 조회되지 않았다. 수정본을 새 stage로
  다시 업로드하고, 설치 전에 root 권한으로 stage 파일 존재를 확인한다.
- 새 stage `/var/tmp/ci222-server-id_hhvg6`에서 갱신 설치가 통과했고 MR Runner의 active 상태와
  `/etc/sudoers.d/feelm-ci222-gitlab` 구문을 확인했다.
- 현재 GitLab 프로젝트에는 Protected Environments 메뉴가 없고, 보호된 `develop`의 merge 허용
  대상은 Developers + Maintainers이다. environment 권한에 의존하지 않고 Job Token의 `GET /job`
  응답과 서버의 root 소유 운영자 허용 목록으로 실제 실행자를 제한하도록 보완했다.
- pipeline `#183378`의 첫 prepare 실행은 현재 Job 또는 운영자 검증에서 거부됐다. 민감한 응답
  값을 노출하지 않고 불일치한 필드 이름만 출력하도록 오류를 세분화해 재실행 진단이 가능하게 했다.
- 진단 재실행에서 `job_source` 불일치를 확인했다. Job `source`는 GitLab 버전에 따라 제공되지
  않으므로 서버 판정에서 제외하고, web pipeline 경계는 기존 CI 규칙과 고정 context 검증으로
  유지한다.
