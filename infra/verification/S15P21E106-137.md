## 실행 절차 및 정합성 기준

1. 팀과 사용 시간을 조율하고 Master의 `/json/`에서 `activeapps`, `activedrivers`가 비었는지 확인한다.
2. Compose 검사, 세 컨테이너의 HDFS 이름 조회, 두 Worker 등록을 확인한다.
3. `infra/spark/cluster-check.py`를 Master로 복사해 README의 고정 포트 명령으로 실행한다.
4. Master의 local mode에서 HDFS 목록을 조회하고, 별도 새 경로에 클러스터로 100건을 저장·조회한다.
5. Kafka 커넥터 접근·로딩을 확인하고 별도 테스트 토픽을 생성한다.
6. 아래 단계별 이벤트를 한 번씩 발행한다. Producer는 `acks=all`을 사용한다.
7. 같은 토픽을 Structured Streaming으로 읽고 Parquet append sink에 저장한다.
8. 정상 종료 후 동일 체크포인트로 재실행하고, 기존 행 보존과 추가 이벤트를 비교한다.
9. 조율된 시간에 구성요소를 하나씩 수동 중단·복구한다. 복구 확인 전 다음 중단 시험을 하지 않는다.

| 단계 | 발행 데이터 (`event_id`, `value`) | 결과 건수 |
| --- | --- | --- |
| 최초 | `initial-01`~`initial-10`, 1~10 | 10 |
| 신규 발행 없는 재실행 | 없음 | 10 → 10 |
| 정상 재개 | `resume-11`~`resume-15`, 11~15 | 10 → 15 |

### Spark 실행 계약

클러스터 시험은 `spark://spark-master:7077`, 총 4코어, Executor당 2코어·2 GiB를 사용했다.
Worker 1 중단 중 시험만 총 코어를 2로 제한하고 전후 Master 상태에서 Worker 2만 ALIVE임을 확인했다.

```text
spark.driver.host=spark-master
spark.driver.bindAddress=0.0.0.0
spark.driver.port=7079
spark.driver.blockManager.port=7080
spark.blockManager.port=7081
spark.port.maxRetries=0
spark.hadoop.dfs.client.use.datanode.hostname=true
```

고정 포트를 사용하는 작업은 동시에 실행하지 않는다. 필요한 서버 사이의 접근만 허용하고
인터넷 전체에 포트를 공개하지 않는다. 고정 포트 누락 시 Worker 1이 참여하지 못한 실행이 있었고,
기존 고정 포트와 Driver 주소를 지정한 후 두 Worker 실행이 성공했다.

Kafka source의 설정은 `subscribe=<테스트 토픽>`, `startingOffsets=earliest`,
`failOnDataLoss=true`이며 Bootstrap Server는 기존 분산 노드의 사설 주소와 9092 포트를 사용했다.
저장 열은 `topic`, `partition`, `offset`, 문자열 `payload`다.

```python
events = source.selectExpr(
    "topic", "partition", "offset", "CAST(value AS STRING) AS payload"
)
query = (
    events.writeStream.format("parquet").outputMode("append")
    .option("path", output)
    .option("checkpointLocation", checkpoint)
    .trigger(availableNow=True).start()
)
```

위 코드는 실행 계약 발췌이며 단독 실행용 전체 스크립트는 아니다. 검증은 대화에서 제공한
Python 명령을 Master 컨테이너의 `python3 -`로 실행했다. `/dev/stdin`을 `spark-submit`에
직접 전달하면 Python 파일로 인식되지 않는 오류가 있어 해당 방식은 사용하지 않았다.

재개 시험에서는 실행 전에 기존 `output`, `checkpoint/metadata`, `checkpoint/commits`의
존재를 확인했다. `availableNow` 쿼리 종료 대기는 120초로 두었고 종료 시 활성 쿼리와 Spark를
정리했다. 이는 패키지 로딩과 전체 애플리케이션 시간에 대한 제한은 아니다.

검증은 단순 count가 아니라 payload를 JSON으로 읽어 전체 `(event_id, value)` 목록을 기대값과
비교했다. `(topic, partition, offset)`의 고유 개수를 비교하고, 재개 전의 전체 행이 이후에도
그대로 포함되는지 확인했다. 신규 이벤트 없는 재실행은 전후 전체 행의 일치를 확인했다.
범위는 이 작은 테스트 데이터이며 Kafka에 대한 일반적인 업무 이벤트 중복 제거를 구현한 것은 아니다.

## 수동 중단·복구 절차와 로그

시험 전에 다른 사용자와 중단 범위를 합의한다. Kafka 중단은 단일 Broker의 모든 토픽에 영향을
준다. DataNode 시험은 검증 경로의 모든 블록이 두 노드에 복제된 것을 확인한 후 진행했다.
아래 명령은 절차 기록이며, 승인된 점검 시간 외에 그대로 실행하지 않는다.

| 대상 | 실행 서버 | 중단 | 복구 |
| --- | --- | --- | --- |
| Spark Worker 1 | 서비스 노드 | `docker stop feelm-spark-worker-1` | `docker start feelm-spark-worker-1` |
| Kafka | 분산 노드 | `docker stop --timeout 30 feelm-kafka` | `docker start feelm-kafka` |
| HDFS DataNode 1 | 서비스 노드 | `docker stop --timeout 30 feelm-hdfs-datanode-1` | `docker start feelm-hdfs-datanode-1` |

성공·실패에 관계없이 중단한 컨테이너를 복구하고 실제 등록·접속 상태까지 확인한다.
`docker compose down -v`, 볼륨 삭제, NameNode 재포맷은 수행하지 않는다.
DataNode 중단 직후에는 NameNode에 Live 2로 남아 있었으며, DEAD 전환까지 기다린 시험이 아니다.

- 컨테이너 상태: `docker inspect <이름> --format '{{.State.Status}}'`
- Spark 등록·작업: 분산 노드 `curl --fail http://127.0.0.1:8080/json/`
- Spark Master·Worker: `docker logs --tail 150 <해당 컨테이너>`
- Executor: Worker 컨테이너 `/opt/spark/work/<app-id>/<executor-id>/stderr` (정리 정책에 따라 삭제 가능)
- Driver: `spark-submit` 또는 Python 실행 터미널 출력. Master 데몬 로그와 구분한다.
- Kafka: `docker logs --tail 150 feelm-kafka`, `kafka-topics.sh --describe`, `kafka-get-offsets.sh --time -1`
- HDFS: `hdfs dfsadmin -report`, `hdfs fsck <검증 경로> -files -blocks -locations`
- DataNode: `docker logs --tail 150 feelm-hdfs-datanode-1` 및 대응 DataNode 2 로그

오류 발생 시 전체 환경변수·Secret을 출력하지 않는다. 부분 처리 가능성이 있으므로 Producer
재발행, 체크포인트 삭제, 새 체크포인트로 초기화하여 성공시키는 조치를 하지 않는다.
먼저 기존 출력·commits·offsets와 오류 로그를 보존하고 재개 기준을 확인한다.

## 복제 설정 차이와 보완 검증

기존 통합 경로의 18개 블록은 모두 실제 복제본 2개였다. 그중 Parquet 4개 파일은 목표가 3이고,
체크포인트·메타데이터는 목표가 2였다. 따라서 HEALTHY와 함께 복제 부족 4개가 표시됐다.
전체 HDFS 보고에는 복제 부족 8개가 있었으나 검증 경로 밖의 원인은 조사하지 않았다.

별도 새 Parquet 쓰기에 다음 설정을 추가했을 때 목표 2, 실제 2개 복제와 정합성 검증이 성공했다.

```python
.config("spark.hadoop.dfs.replication", "2")
```

이 설정은 해당 검증 실행에만 적용했다. 공유 Spark 설정·이미지에 영구 반영하지 않았고,
기존 파일에 `setrep`을 실행하지 않았다. 이후 저장본의 새 Kafka 스트리밍 출력·체크포인트에서
목표 2와 실제 복제본 2개를 확인했다 (아래 서버 재검증 결과). 기존 경고를 제거하기 위해 무단으로 전체 HDFS 설정이나 파일을
변경하지 않는다. 후속 실행 절차에는 2노드 복제 계약을 명시하고 적용 범위를 검토해야 한다.

Producer 종료 절차 후 토픽을 생성했고, 발행 전 각 파티션 오프셋 0을 확인했다.
최초 발행 종료 코드는 0, 마지막 오프셋은 0번=0 / 1번=10이었다. 추가 5건 발행도
종료 코드 0이며 0번=5 / 1번=10이었다. 오류 상태를 성공으로 간주하거나 메시지를 무조건 재발행하지 않았다.

| 최초 처리 (`init`) | 0 | 10 | 10 | 10 |

복제 부족 경고가 해결됐다는 의미는 아니다. 저장본으로 장애 주입 시험을 반복하지 않았으며,
앞선 수동 장애·복구 시험의 범위와 제한은 그대로 유지한다.

## 남은 작업과 완료 판단

- 전체 실행 코드를 [검증 스크립트 및 실행 안내](../spark/README.md)로 정리했다.
  해당 저장본의 최초 처리·무신규 재개·신규 재개 및 실제 복제 수 서버 검증도 통과했다.
- 검증 스크립트의 Spark 쓰기 복제 수 2가 새 스트리밍 파일에 실제 적용됨을 확인했다.
  공유 런타임 설정 및 기존 테스트 파일의 목표 복제 수 변경은 미적용이다.
- 실행 중 Worker 태스크 강제 종료·자동 재처리, Kafka 중단 중 실행 중인 Streaming의 오류·자동 재연결은 미검증이다.
- DataNode 중단 중 쓰기·체크포인트 커밋·Streaming 재개, NameNode의 DEAD 판정까지의 감지는 미검증이다.
- 서버 재부팅, 디스크·볼륨 손실, NameNode 장애, 장기 실행 및 부하 시험은 수행하지 않았다.
- 중단 시험은 수동 stop/start 기반이다. 운영 수준 고가용성이나 일반적인 exactly-once 보장으로 확대 해석하지 않는다.
- Jira 완료 조건의 장애·복구 요구를 이 시험 범위로 충족하는지는 팀 리뷰로 확정한다. 현재 문서만으로 완료 처리하지 않는다.
- 추천 도메인 로직, 성능 튜닝, 대규모 부하 시험과 운영 모니터링은 본 업무 범위 밖이다.
