## 사전 검사

- 두 서버의 후보 checkout이 동일한 commit을 가리키고 추적 변경이 없음을 확인했다.
- 서버별 현재 운영 commit을 별도 detached rollback worktree로 준비했다.
- 후보 이미지는 두 서버에서 각각 빌드했다. 독립 빌드의 이미지 ID는 서로 달랐지만 두 이미지
  모두 Linux amd64, 사용자 `spark`, Python 3.10.12, NumPy 2.2.6, Java 21.0.11,
  Spark 4.1.3을 사용했다.
- Spark Master에서 활성 Application과 Driver가 각각 0임을 확인했다.

## 정상 배포

1. 분산 서버에서 Spark Master와 Worker 2를 후보 이미지로 배포했다.
2. 서비스 서버에서 Worker 1을 후보 이미지로 배포했다.
3. Master 상태는 `ALIVE`, 두 Worker는 각각 분산·서비스 서버 주소에서 `ALIVE`였다.
4. 세 Spark 컨테이너가 후보 이미지 태그로 `running` 상태임을 확인했다.
5. 서비스 서버 Worker 1 컨테이너에서 NumPy 2.2.6을 확인했다.

첫 분산 서버 검증 중 터미널에 최종 완료 문구가 표시되지 않았지만 배포 프로세스가 종료됐고,
Master 로그의 두 Worker 등록, Master JSON의 Worker 2개 `ALIVE`, 컨테이너 이미지와 실행 상태를
별도로 확인했다. 서비스 서버에서는 Master Web UI 8080 접근이 차단되어 최초 시도가 컨테이너
변경 전에 거부됐다. 방화벽을 열지 않고 Worker의 로컬 로그로 Master 등록을 확인하도록
`a2ada34`에서 수정한 뒤 서비스 서버 배포가 성공했다.

## 롤백 및 재배포

1. 분산 서버의 Master·Worker 2를 이전 checkout과 이전 Spark 이미지로 롤백했다.
2. 서비스 서버의 Worker 1을 서버별 이전 checkout과 이전 Spark 이미지로 롤백했다.
3. 두 명령 모두 `Deployment completed`를 출력했다.
4. 같은 순서로 분산 서버와 서비스 서버를 후보 checkout·이미지에 다시 배포했다.
5. 최종 재배포도 두 서버 모두 `Deployment completed`를 출력했다.

롤백은 Compose 설정과 Spark 이미지를 이전 release로 되돌리는 시험이다. HDFS 파일,
Kafka 로그 및 Spark 체크포인트를 과거 상태로 되돌리는 작업은 수행하지 않았다.

## Kafka 배포·롤백

1. 분산 서버에서 Kafka를 후보 checkout으로 재배포했다.
2. 이전 checkout으로 롤백한 뒤 후보 checkout으로 다시 배포했다.
3. 각 단계에서 `apache/kafka:4.3.1` 이미지와 `compose_kafka_data` 볼륨을 유지했다.
4. Cluster ID `05O6aqKdTUG_BHuGGws83Q`와 기존 topic 목록이 보존됐다.
5. 최종 Metadata Quorum은 Leader ID 1, Max Follower Lag 0이었다.

재시작 직후 AdminClient의 일시적인 9092 연결 경고가 있었으나 같은 배포 명령 안에서
Quorum 검사가 회복되어 `Deployment completed`를 출력했다.

## HDFS 준비 지연 및 복구

분산 서버에서 후보 HDFS NameNode와 DataNode 2를 재생성한 직후 `dfsadmin -report`가
NameNode RPC 8020 연결 거부로 실패했다. 자동 롤백도 컨테이너 재생성에는 성공했지만 같은
단발 검증이 너무 일찍 실행되어 수동 복구 필요 상태로 보고됐다.

운영 로그에서 NameNode가 FSImage를 읽는 데 약 31초가 걸렸고 이후 RPC 8020이 열렸음을
확인했다. 별도 데이터 복구 없이 Safe mode가 해제됐으며 다음 기준값이 보존됐다.

- NameNode와 DataNode 2: `healthy`, 재시작 횟수 0
- Live DataNode: 2
- 디렉터리 174, 파일 479376, 블록 479305
- Missing block 0, Corrupt block 0, 파일시스템 `HEALTHY`
- 기존 Under-replicated block 2811

컨테이너 health 이후에도 HDFS RPC와 DataNode 등록 완료를 제한 시간 동안 재시도하도록
배포 검증을 보완했다.

## HDFS 배포·롤백

1. 보완된 후보 commit으로 분산 서버의 NameNode·DataNode 2를 배포했다.
2. 서비스 서버의 DataNode 1을 배포하고 두 DataNode 등록과 데이터 기준값을 확인했다.
3. 분산 서버와 서비스 서버를 각각의 이전 checkout으로 롤백했다.
4. 롤백 상태에서 두 DataNode 등록, 파일·블록 수와 파일시스템 상태가 보존됨을 확인했다.
5. 분산 서버와 서비스 서버를 후보 commit으로 다시 배포했다.
6. 최종 상태에서 Live DataNode 2, 디렉터리 174, 파일 479376, 블록 479305,
   콘텐츠 7734249133 bytes를 확인했다.
7. Missing block과 Corrupt block은 0이고 파일시스템은 `HEALTHY`였다.

모든 단계에서 `apache/hadoop:3.4.3` 이미지와 NameNode·DataNode 영구 볼륨을 유지했으며,
NameNode 포맷이나 볼륨 삭제는 수행하지 않았다. Under-replicated block 2811은 배포 전후
동일하게 유지됐다.
