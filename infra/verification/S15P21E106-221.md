# S15P21E106-221 운영 기본 안전성 점검

## 범위와 판단 기준

- 점검일: 2026-09-04. 용량 측정 시각은 서비스 09:44:05 UTC, 분산 09:44:11 UTC.
- 운영자가 제공한 서버 명령 결과와 GitLab 화면을 근거로 정리했다. AI가 서버에 직접 접속한 결과는 아니다.
- 설정 변경, 데이터 삭제, 서비스 재시작, 실제 백업·복원은 수행하지 않았다.
- 사용자는 현재 개발 데이터를 잃는 것은 감수할 수 있으나 실제 사용자 데이터는 보존해야 한다고 확인했다.
- 아래 우선순위는 후속 작업 제안이며 Jira 우선순위 변경이나 작업 생성 결과가 아니다.
- 미확인 항목을 정상 또는 백업 부재로 단정하지 않는다. 이 기록만으로 운영 안전성 전체를 보장하지 않는다.

호스트 logrotate 타이머는 있으나 Docker 로그를 대상으로 하는지 확인하지 않았다.
실제 로그 파일별 크기, 별도 외부 회전 정책, Spark 작업 파일·Kafka 데이터 보관 정책은 미확인이다.
Docker 로그 제한과 애플리케이션 데이터 보관 정책은 구분해야 한다.

## 2. 백업·복원 준비

- 두 서버의 systemd 타이머, `/etc/cron.d`, `/etc/cron.daily`, `/etc/cron.weekly` 목록에서
  서비스 데이터 백업 작업을 식별하지 못했다.
- `/var/spool/cron/crontabs`에는 두 서버 모두 사용자별 파일이 없었다.
- 두 서버의 `/etc/crontab` 작업 4개는 안전한 분류 명령 결과 19~22행에서 각각
  cron.hourly/daily/weekly/monthly 호출로 분류됐다. OTHER_REVIEW_NEEDED 출력은 없었다.
  이는 호출 유형 점검이며 명령 원문 전체를 수집·검토한 결과는 아니다.
- 두 서버의 `/etc/cron.hourly`, `/etc/cron.monthly`에는 `.placeholder`만 있었다.
  `/etc/anacrontab`은 없었다.
- `/var/backups`에는 apt/dpkg/alternatives 패키지 관리 정보만 확인됐다.
- 확인한 `/backup`, `/backups`, `/opt/backups`에서는 디렉터리 출력이 없었다.
- `dpkg-db-backup.timer`와 패키지 관리 파일은 PostgreSQL·HDFS·Kafka 백업 근거가 아니다.
- 사용자는 이전 백업 설정 여부를 기억하지 못하며, 현재 사용할 외부 저장소는 없다고 답했다.
- PostgreSQL 크기: `feelm` 9,262 kB, `postgres` 7,478 kB. 이는 실제 백업 파일 크기가 아니다.

판정은 **백업·복원 근거 미확인**이다. 외부 스냅샷, 다른 경로, 컨테이너 내부 작업,
외부 예약 작업, 백업 접근 권한·보관 기간·복원 이력은 확인하지 못했다.
AWS 콘솔을 사용할 수 없어 클라우드 백업 존재 여부도 미확인으로 남긴다.
HDFS·Kafka의 전체 데이터 목록과 재생성 가능 여부는 아직 분류하지 않았다.

현재 개발 단계에서는 백업 구축을 즉시 시작하지 않기로 했다. 실제 사용자 데이터나
재생성이 어려운 데이터를 받기 전에는 보존 대상, 서버 외부 저장 위치, 보관 기간,
실패 확인 방법을 정하고 별도 환경 복원 검증을 완료해야 한다.
PC 임시 보관은 제안만 했으며 실행하지 않았다. 백업이 존재한다고 가정한 볼륨 삭제는 금지한다.

## 3. GitLab Runner와 브랜치 보호

서비스 서버에서 GitLab Runner가 active였고 분산 서버에서는 inactive 및 사용자 부재였다.
실행 중인 Docker 컨테이너 이름·이미지에서 Runner 항목은 발견되지 않았다.

| 점검 항목 | 결과 |
| --- | --- |
| 실행 방식 | `executor="shell"`, `concurrent=1` |
| 계정 | `gitlab-runner`, docker 그룹 소속 |
| 서비스 User / Group | 둘 다 빈 값. 프로세스 소유자는 root:root |
| Runner 실행 인자 | `--user gitlab-runner`, 작업 디렉터리 `/home/gitlab-runner`. Job 사용자 설정은 확인했으나 실제 Job 안의 UID는 미측정 |
| Docker 소켓 | root:docker, `srw-rw----` |
| 소켓 접근 검사 | 사용자 제공 출력은 `...=ye`로 잘림. 그룹·소켓 권한과 함께 접근 가능 구성으로 판단 |
| 태그 | `e106-shell` |
| Run untagged jobs | 꺼짐 |
| Protected | 꺼짐 |
| Lock to current projects | 꺼짐 |
| Runner 최대 Job timeout | 미설정. 프로젝트 timeout은 미확인이므로 무제한으로 단정하지 않음 |
| Token expiry | Never expires. 토큰 원문은 수집하지 않음 |
| 연결 프로젝트 | 사용자 확인상 S15P21E106만 연결. 범위 유형·전체 연결 목록은 직접 확인하지 않음 |
| develop | 직접 Push No one, 병합 Developers + Maintainers, force push 꺼짐 |
| main | 직접 Push No one, 병합 Maintainers, force push 꺼짐 |

브랜치 보호는 적용돼 있지만, 운영 서버의 Docker 접근 권한과 CI 작업의 격리를 대신하지 않는다.
Docker 제어 권한으로 운영 컨테이너·볼륨에 영향을 줄 수 있는 구성이므로 CI 확장 전에
빌드·검증과 운영 배포 권한의 분리 방식을 검토한다. 실제 볼륨 접근이나 Secret 추출은 시험하지 않았다.

추가 GitLab 화면 점검 결과:

- 사용자가 프로젝트 공개 범위를 **Private**으로 확인했다.
- `DOCKERHUB_TOKEN`은 Masked이며 Protect variable은 꺼져 있었다.
  환경 범위는 All (default), Expand variable reference도 꺼짐이었다.
  토큰 값은 열람하지 않았고 설정을 저장·변경하지 않았다.
- `DOCKERHUB_NAMESPACE`, `DOCKERHUB_USERNAME`은 목록에서 환경 범위 All (default)를
  확인했다. 값의 점 표시만으로 마스킹·보호 여부를 판단하지 않는다.
- 멤버 목록에 Developer와 Maintainer가 표시됐고 일부 Source는 Private이었다.
  Source의 Private 표시는 프로젝트 공개 범위와 별개이며 해당 계정의 소속·필요 권한은 미확인이다.

Masked는 로그 노출 완화 설정이며 Job의 Secret 접근을 격리하는 근거가 아니다.
토큰 유출이 확인된 것은 아니며, Protect variable이 꺼졌다는 사실만으로 모든 외부 MR이
토큰을 받는다고 단정하지 않는다. 실제 MR·fork 실행 정책, 다른 프로젝트·그룹 변수,
실제 Job 실행 UID와 Docker 접속 대상은 추가 확인이 필요하다.

Protected를 바로 켜거나 docker 그룹 권한을 제거하면 기존 MR 검증·배포가 중단될 수 있다.
같은 Docker 데몬을 공유하는 Runner 이름만 추가해도 격리가 되는 것은 아니다.
프로젝트 잠금과 실행 대상 제한은 담당자 승인 후 후속 변경으로 다룬다.

## 4. SSH와 접근 범위

두 서버의 `sshd -T` 결과는 동일했다.

```text
maxauthtries 6
permitrootlogin without-password
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
permitemptypasswords no
authenticationmethods any
```

`/etc/ssh/sshd_config`와 `/etc/ssh/sshd_config.d/*.conf`에서 Match 검색 결과는 없었다.
비밀번호·키보드 대화형 인증은 차단돼 있다. `without-password`는 root 키 로그인을 허용할 수
있는 설정이며, 실제 root 키 등록·사용 여부는 확인하지 않았다. `any`는 무인증 허용을 뜻하지 않는다.
별도 Include 경로·서비스 실행 옵션·사용자별 실제 접속 조건 전체를 조사한 것은 아니다.

기존 137 점검에서 UFW는 두 서버 모두 활성, incoming 기본 deny였고 SSH 22는 IPv4/IPv6 전체
허용이었다. 서비스 80/443은 공개, 분산 통신은 사설 주소 또는 서브넷 허용이었다.
이것은 이전 결과를 인용한 것으로 221에서 방화벽·외부 접근을 재측정한 것은 아니다.
AWS 보안 그룹은 미확인이다. root 키 로그인과 SSH 출발지 제한은 접속 유지 방안을 확보한 후 검토한다.

## 정리 상태

이 문서는 **중간 점검 기록**이다. Related to S15P21E106-221로 연결하며, 문서 MR 병합만으로
Jira 업무를 완료 처리하지 않는다. 사용자의 지시에 따라 자동 완료 키워드는 사용하지 않는다.
확인한 근거와 미확인 항목을 문서화했다. 미확인 항목까지 검증 완료라고 표시하지 않는다.

남은 확인 항목은 다음과 같다.

- 보존 대상 데이터 분류, 다른 위치·외부 백업과 접근 권한·보관·복원 근거.
- Docker 로그별 크기와 호스트의 외부 회전 정책.
- 실제 CI Job 사용자·Docker 대상, 운영 볼륨·Secret 접근 범위 및 MR 실행 신뢰 경계.
- 멤버의 소속·권한 필요성, root 키 사용과 외부 방화벽 정책 등 접근 범위.

운영자가 확인할 수 없는 클라우드 설정·계정 소속은 관리 권한이 있는 담당자의 확인이 필요하다.
후속 구현은 별도 승인·업무로 분리하며 이 작업에서 설정을 바꾸지 않는다.
Jira 상태 전환과 후속 Jira 생성은 수행하지 않는다. MR 병합은 사람이 별도로 판단한다.
원본 증빙은 운영자 제공 대화·캡처이며 저장소에 업로드하지 않았다.
